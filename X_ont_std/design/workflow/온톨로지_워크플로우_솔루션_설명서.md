# 온톨로지/워크플로우 솔루션 설명서

작성일: 2026-06-13  
대상: ont_platform v5, Scenario 1 서비스 요청 자동댓글  
목적: 온톨로지와 워크플로우가 각각 무엇을 맡고, 화면에서 어떻게 보고 다루는지 설명한다.

## 1. 한 줄 설명

이 솔루션은 고객 문의나 현장 요청을 단순 로그로만 남기지 않고, 업무 객체와 관계로 저장한 뒤 워크플로우로 처리하는 시스템이다.

예를 들어 고객이 게시판에 문의를 남기면 다음 흐름이 만들어진다.

```text
고객 문의
  -> 워크플로우 실행
  -> 자동 답변 생성
  -> 고객사 게시판 댓글 등록
  -> 온톨로지 관계도로 저장
```

즉, 댓글을 다는 기능만 있는 것이 아니라,

```text
무슨 요청이 있었고
어떤 워크플로우가 처리했고
어떤 답변이 만들어졌고
외부 시스템에는 어떤 댓글로 등록됐는지
```

를 관계로 추적할 수 있게 한다.

## 2. 왜 온톨로지와 워크플로우를 같이 쓰는가

단순 자동댓글만 필요하면 DB와 API만으로도 구현할 수 있다.

하지만 실제 업무에서는 다음 질문이 따라온다.

- 같은 고객이 비슷한 요청을 반복했는가?
- 같은 공장, 같은 라인, 같은 장비에서 문제가 반복되는가?
- 이전에는 어떤 답변을 했는가?
- 자동 처리해도 되는 요청인가, 담당자 검토가 필요한가?
- 어떤 워크플로우가 어떤 근거로 실행됐는가?

이 질문들은 단순 게시글/댓글 테이블만 보면 매번 조인과 조건문으로 풀어야 한다.

온톨로지는 업무 대상을 객체와 관계로 저장한다.

워크플로우는 그 객체를 어떻게 처리할지 정의한다.

정리하면:

| 구분 | 역할 |
| --- | --- |
| 온톨로지 | 업무 세계를 객체와 관계로 저장 |
| 워크플로우 | 객체를 처리하는 절차와 판단 흐름 |
| RAG/LLM | 답변 초안 생성과 근거 보강 |
| MCP | 외부 고객사 시스템 호출 경계 |
| Audit | 실제 실행과 외부 호출 증거 |

## 3. 기본 예시: 서비스 요청 자동댓글

현재 구현된 기본 시나리오는 고객사 게시판 자동댓글이다.

### 처리 흐름

```text
customer_board 새 문의
  -> webhook 또는 batch
  -> ont_platform workflow 실행
  -> 답변 초안 생성
  -> customer_mcp comment.create 호출
  -> customer_board 댓글 등록
  -> 실행 결과를 온톨로지에 저장
```

### 온톨로지에 남는 객체

| 객체 | 쉬운 의미 |
| --- | --- |
| `ServiceRequest` | 고객 문의 또는 서비스 요청 |
| `WorkflowExecution` | 워크플로우 실행 기록 |
| `AutoReply` | 자동으로 생성한 답변 |
| `ExternalComment` | 고객사 게시판에 등록된 댓글 결과 |

### 온톨로지 관계도

```text
ServiceRequest
  -- handled_by --> WorkflowExecution

WorkflowExecution
  -- generated --> AutoReply

AutoReply
  -- posted_as --> ExternalComment

ServiceRequest
  -- has_reply --> AutoReply
```

이 관계 덕분에 사용자는 "댓글이 달렸다"에서 끝나지 않고, 어떤 요청이 어떤 실행을 거쳐 어떤 댓글로 이어졌는지 볼 수 있다.

## 4. 워크플로우와 온톨로지 매핑

워크플로우 노드와 온톨로지 객체는 직접 하드코딩으로만 연결하지 않는다.

중간에 매핑 템플릿을 둔다.

현재 기본 매핑 템플릿:

```text
ont_platform/v5/backend/app/config/workflow_ontology_mappings/scenario1_customer_question_auto_reply.json
```

매핑 예:

| 워크플로우 노드 | 온톨로지 객체 | 설명 |
| --- | --- | --- |
| `request-input` | `ServiceRequest` | 문의 객체 생성/갱신 |
| `draft-response` | `AutoReply` | 자동 답변 객체 생성 |
| `post-comment` | `ExternalComment` | 외부 댓글 등록 결과 저장 |
| `audit-write` | `WorkflowExecution` | 실행 이력 저장 |

매핑 템플릿이 필요한 이유:

- 회사/프로젝트별로 온톨로지 모델을 다르게 가져갈 수 있다.
- 워크플로우를 복제해도 어떤 객체와 관계를 만드는지 확인할 수 있다.
- 나중에 화면에서 매핑을 수정하거나 확장할 수 있다.

## 5. 주요 화면 역할

### Workflow Builder

워크플로우를 보고, 수정하고, 복제하고, 실행하는 화면이다.

할 수 있는 일:

- 시스템 템플릿으로 만든 워크플로우 불러오기
- 워크플로우 복제
- 노드 위치 조정
- 노드 추가
- 노드 연결
- 실행 모드 선택
- `dry_run` 또는 `post` 실행
- 워크플로우-온톨로지 매핑 확인
- 매핑 스키마 설치

`서비스 요청 자동댓글` 워크플로우에서는 `Run`을 누르면 실제 배치 실행으로 이어질 수 있다.

`post` 모드에서는 고객사 게시판에 실제 댓글 등록까지 수행한다.

### Workflow Trace

워크플로우 실행 1건이 온톨로지 객체와 관계로 어떻게 남았는지 한 화면에서 보는 화면이다.

할 수 있는 일:

- 워크플로우 선택
- 실행 회차 선택
- 실행 단계 상태 확인
- `ServiceRequest -> WorkflowExecution -> AutoReply -> ExternalComment` 흐름 확인
- 선택 객체 상세 속성 확인
- write-back 성공 여부와 질문 ID 확인

이 화면은 고객에게 "워크플로우와 온톨로지가 연결됐다"는 것을 가장 직관적으로 보여주는 시연 화면이다.

### 온톨로지 관리 > 스키마 정의

객체 타입과 관계 타입을 관리하는 화면이다.

할 수 있는 일:

- `ServiceRequest`, `AutoReply` 같은 객체 타입 확인
- `handled_by`, `generated` 같은 관계 타입 확인
- 새 도메인 타입 추가
- 새 관계 타입 추가
- 워크플로우 온톨로지 매핑 템플릿 설치

여기서의 "스키마"는 어떤 종류의 객체와 관계를 허용할지 정하는 틀이다.

### 온톨로지 관리 > 인스턴스 편집

실제 객체 데이터를 표/폼 방식으로 관리하는 화면이다.

할 수 있는 일:

- `service-requests` 문서 선택
- `ServiceRequest` 객체 확인
- `AutoReply` 객체 확인
- 객체 이름/속성 수정
- 객체 추가 또는 삭제
- 타입별 필터링

즉, 객체 자체를 정확히 보고 수정하는 화면이다.

### 온톨로지 관리 > 관계 그래프 편집

객체 사이 관계를 캔버스에서 보고 편집하는 화면이다.

할 수 있는 일:

- 객체 노드 이동
- 노드 위치 저장
- 타입 팔레트에서 새 객체 추가
- 노드 핸들 드래그로 관계 연결
- 관계 삭제
- 그래프 JSON 내보내기

`인스턴스 편집`이 표/폼 방식이라면, `관계 그래프 편집`은 그림으로 관계를 편집하는 화면이다.

둘은 같은 데이터를 바라본다.

따라서 한쪽에서 객체나 관계를 바꾸면 다른 화면에도 반영된다.

### 온톨로지 관리 > 온톨로지 그래프

저장된 객체와 관계를 보기 좋게 조회하는 화면이다.

할 수 있는 일:

- `service-requests` 문서 선택
- 요청, 실행, 답변, 댓글 관계 조회
- 노드 클릭 후 상세 속성 확인
- 임시로 노드 위치 이동

이 화면은 운영자 조회용이다.

객체 추가, 관계 추가, 위치 저장은 `관계 그래프 편집`에서 한다.

## 6. 세 화면의 차이

| 화면 | 목적 | 편집 대상 |
| --- | --- | --- |
| 인스턴스 편집 | 객체 자체를 만들고 수정 | 객체 이름, 타입, 속성 |
| 관계 그래프 편집 | 객체 사이 관계와 배치를 편집 | 관계, 노드 배치 |
| 온톨로지 그래프 | 저장된 흐름을 조회 | 조회 중심 |

예:

```text
인스턴스 편집:
  "AutoReply 객체의 message 속성을 확인한다."

관계 그래프 편집:
  "ServiceRequest와 AutoReply를 has_reply로 연결한다."

온톨로지 그래프:
  "이 요청이 어떤 실행과 댓글로 이어졌는지 본다."
```

## 7. 실행 모드

### webhook

고객사 게시판에 새 글이 등록될 때 자동으로 ont_platform을 호출한다.

장점:

- 실시간 처리에 가깝다.

주의:

- ont_platform backend가 꺼져 있으면 웹훅 호출이 실패한다.

### batch

미처리 문의를 모아서 한 번에 처리한다.

장점:

- 웹훅이 꺼져 있어도 미처리 글을 나중에 처리할 수 있다.
- 테스트할 때 게시글만 먼저 쌓아두고 나중에 실행하기 좋다.

### dry_run

실제 댓글 등록 없이 실행 흐름만 확인한다.

용도:

- 매핑과 워크플로우가 정상인지 먼저 확인한다.

### post

customer_mcp를 통해 고객사 게시판에 실제 댓글을 등록한다.

용도:

- 실제 자동댓글 시나리오 검증

## 8. 테넌트와 프로젝트 분리

워크플로우와 온톨로지 데이터는 회사와 프로젝트 단위로 분리된다.

예:

```text
company_id = demo-co
project_id = proj-01
```

같은 워크플로우 템플릿이라도 회사/프로젝트별로 복제해 별도 그래프로 운영할 수 있다.

저장 경로 개념:

```text
storage/{company_id}/{project_id}/workflow_graphs.json
storage/{company_id}/{project_id}/ontology/domain_schema.json
storage/{company_id}/{project_id}/ontology/service-requests.json
```

이 분리가 필요한 이유:

- 고객사별 워크플로우 수정 가능
- 프로젝트별 온톨로지 모델 분리
- 실행 이력과 감사 로그 분리
- 같은 템플릿을 복제해 테스트/운영을 나눌 수 있음

## 9. 실제 데모 진행 순서

### 1단계. 서버 기동

필요 서버:

| 서버 | 포트 |
| --- | ---: |
| ont_platform backend | 8001 |
| ont_platform frontend | 3002 |
| customer_mcp | 8080 |
| customer_board | 8090 |

### 2단계. 매핑 스키마 확인

화면:

```text
온톨로지 관리 > 스키마 정의
```

확인:

- `ServiceRequest`
- `WorkflowExecution`
- `AutoReply`
- `ExternalComment`
- `handled_by`
- `generated`
- `posted_as`
- `has_reply`

없으면 `워크플로우 온톨로지 매핑`에서 `스키마에 설치`를 누른다.

### 3단계. 게시글 준비

화면:

```text
http://127.0.0.1:8090
```

batch 테스트를 하려면 실시간 webhook을 끄고 새 문의를 작성한다.

### 4단계. 워크플로우 실행

화면:

```text
Workflow Builder
```

순서:

1. `서비스 요청 자동댓글` 워크플로우를 불러온다.
2. 필요하면 복제한다.
3. 실행 모드를 `post` 또는 `dry_run`으로 선택한다.
4. `Run`을 누른다.

### 5단계. Workflow Trace 확인

화면:

```text
Workflow Trace
```

확인:

```text
ServiceRequest
  -> WorkflowExecution
  -> AutoReply
  -> ExternalComment
```

### 6단계. 댓글 확인

화면:

```text
http://127.0.0.1:8090
```

작성한 문의에 자동 댓글이 달렸는지 확인한다.

### 7단계. 온톨로지 확인

화면:

```text
온톨로지 관리 > 온톨로지 그래프
```

문서:

```text
service-requests
```

확인:

```text
ServiceRequest
  -> WorkflowExecution
  -> AutoReply
  -> ExternalComment
```

## 10. 공장 반복 장애 예시로 확장

서비스 요청 자동댓글은 이해를 돕기 위한 첫 번째 예시다.

더 직관적인 확장 예시는 공장 반복 장애다.

예:

```text
세종 배터리팩 공장 3번 조립 라인에서
배터리 탭 용접기 압력이 낮다는 알림이
10시, 11시, 13시에 반복 발생
```

단순 게시판이면 글 3개가 따로 보인다.

온톨로지에서는 이렇게 묶을 수 있다.

```text
세종 배터리팩 공장
  -> 3번 조립 라인
  -> 배터리 탭 용접기
  -> 압력 낮음 문제
  -> 반복 장애 이벤트 3건
```

워크플로우는 반복 여부를 보고 처리 방식을 바꿀 수 있다.

```text
1회 발생:
  작업자에게 점검 안내

2회 반복:
  설비 담당자에게 알림

3회 이상 반복:
  생산 리더 승인 또는 라인 점검 워크플로우 실행
```

이 예시가 중요한 이유:

- 온톨로지가 같은 장비/라인/문제를 묶어준다.
- 워크플로우가 반복 횟수와 영향 범위에 따라 다르게 판단한다.
- 단순 자동댓글보다 업무적 가치가 더 직관적으로 보인다.

## 12. FAQ

### Q. 댓글 하나 달려고 온톨로지가 꼭 필요한가?

댓글 하나만 보면 꼭 필요하지 않다.

하지만 같은 요청이 반복되거나, 여러 시스템과 연결되거나, 처리 근거와 이력을 추적해야 하면 온톨로지가 필요해진다.

### Q. DB와 뭐가 다른가?

DB는 데이터를 저장한다.

온톨로지는 업무 객체와 관계의 의미를 함께 저장한다.

예를 들어 DB에서는 `question_id`, `comment_id`, `run_id`를 조인해야 하지만, 온톨로지에서는 `ServiceRequest -- handled_by --> WorkflowExecution`처럼 관계가 바로 드러난다.

### Q. Workflow Builder와 온톨로지 관리 화면은 왜 나뉘어 있나?

Workflow Builder는 처리 절차를 편집하는 곳이다.

온톨로지 관리는 처리 대상과 결과로 남는 업무 객체를 관리하는 곳이다.

### Q. 인스턴스 편집과 관계 그래프 편집은 같은 데이터인가?

같은 데이터다.

인스턴스 편집은 표/폼 방식이고, 관계 그래프 편집은 그림 방식이다.

### Q. `PERSON`, `ORGANIZATION` 같은 타입은 무엇인가?

기본 내장 타입이다.

일반적인 온톨로지 구축을 위해 제공되는 범용 타입이며, 서비스 요청 자동댓글에서는 주로 `ServiceRequest`, `WorkflowExecution`, `AutoReply`, `ExternalComment`를 사용한다.
