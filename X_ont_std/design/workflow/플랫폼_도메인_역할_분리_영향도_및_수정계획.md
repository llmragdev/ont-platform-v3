# 플랫폼 역할과 도메인 역할 분리 영향도 분석 및 수정 계획

작성일: 2026-06-14  
작성자: Codex  
대상: `ont_platform/v5`

## 1. 결론

현재 `FinanceManager`, `AccountManager` 같은 특정 업무 도메인 역할이 워크플로우 빌더, 온톨로지 편집, 실행 권한에 직접 사용되고 있다.

워크플로우 빌더는 특정 업무 도메인이 아니라 플랫폼 공통 기능이므로, 권한 모델을 다음처럼 분리하는 것이 맞다.

- 플랫폼 역할: 워크플로우/온톨로지/운영 콘솔 사용 권한
- 도메인 역할: 업무 노드, 승인 조건, 현업 액션 처리 권한

영향도는 **중간 이상**이다. 단순히 `FinanceManager` 문자열을 바꾸는 작업이 아니라, 프론트 사용자 프리셋, 백엔드 그래프 권한, API 헤더 계약, 화면 권한 훅, 문서, 테스트 시나리오가 함께 영향을 받는다.

다만 구조가 크게 꼬여 있지는 않다. 현재 권한 판단 지점이 비교적 적고, 대부분 `role` 문자열 기반이라 단계적으로 전환 가능하다.

## 2. 현재 문제

현재 역할은 다음 두 의미가 섞여 있다.

| 구분 | 현재 예시 | 문제 |
| --- | --- | --- |
| 플랫폼 관리자/편집자 | `Admin`, `FinanceManager`, `AccountManager` | 워크플로우 편집 권한에 도메인 역할이 직접 들어감 |
| 업무 도메인 담당자 | `FinanceManager`, `AccountManager`, `PaymentManager` | 금융/계정 업무 권한과 플랫폼 편집 권한이 구분되지 않음 |
| 조회자 | `Viewer`, `Analyst` | 비교적 자연스럽지만 플랫폼 역할 체계로 재정의 필요 |

예를 들어 `FinanceManager`가 워크플로우를 삭제할 수 있느냐는 질문은 이상하다. 올바른 질문은 다음이어야 한다.

- 이 사용자가 `WorkflowDesigner`인가?
- 이 사용자가 해당 프로젝트의 워크플로우를 삭제할 권한이 있는가?
- 특정 노드가 금융 승인 노드라면, 그 노드를 처리할 업무 역할이 `FinanceManager`인가?

## 3. 권장 역할 모델

### 3.1 플랫폼 역할

| 역할 | 의미 | 주요 권한 |
| --- | --- | --- |
| `PlatformAdmin` | 플랫폼 전체 관리자 | 모든 프로젝트/워크플로우/온톨로지 관리 |
| `WorkflowDesigner` | 워크플로우 설계자 | 템플릿 복제, 그래프 생성/수정/삭제, dry_run/post 실행 |
| `WorkflowOperator` | 운영 실행자 | 저장된 워크플로우 실행, 실행 이력 확인 |
| `OntologyManager` | 온톨로지 관리자 | 스키마/인스턴스/관계 편집 |
| `Analyst` | 분석 사용자 | 조회, Trace/대시보드 확인 |
| `Viewer` | 읽기 전용 사용자 | 조회만 가능 |

### 3.2 도메인 역할

| 역할 | 의미 | 사용 위치 |
| --- | --- | --- |
| `FinanceManager` | 재무/결제 승인 담당 | 금융 승인 노드, 결제 액션 |
| `AccountManager` | 계정/고객 응대 담당 | 계정 조치, 고객 문의 승인 |
| `MaintenanceManager` | 정비 담당 | 공장 정비 지시 승인/처리 |
| `QualityManager` | 품질 담당 | 품질 영향 판단/승인 |
| `FactoryOperator` | 현장 운영자 | 공장 현장 요청 등록/확인 |

### 3.3 사용자 컨텍스트 권장 구조

현재:

```json
{
  "user_id": "bob",
  "company_id": "demo-co",
  "project_id": "proj-01",
  "role": "FinanceManager"
}
```

권장:

```json
{
  "user_id": "bob",
  "company_id": "demo-co",
  "project_id": "proj-01",
  "platform_role": "WorkflowDesigner",
  "domain_roles": ["FinanceManager"]
}
```

단기 호환을 위해 `role`은 유지하되, 내부적으로는 `platform_role`과 `domain_roles`를 병행 도입하는 방식이 안전하다.

## 5. 변경 범위 판단

### 5.1 작게 고치는 경우

목표: 화면과 백엔드 그래프 권한에서만 도메인 역할 제거

작업:

- `FinanceManager` 프리셋을 `WorkflowDesigner`로 변경
- `AccountManager` 프리셋을 `WorkflowOperator` 또는 `WorkflowDesigner`로 변경
- `usePermission.ts` 권한표 수정
- `WorkflowGraphService` 그래프 권한표 수정
- `UserRole` 타입 수정
- API 헤더는 기존 `X-Role` 유지

장점:

- 빠르게 정리 가능
- 현재 API 계약을 거의 유지
- 회귀 위험 낮음

단점:

- 도메인 역할을 사용자에게 함께 부여하는 구조는 아직 없음
- 금융/공장/품질 노드별 업무 권한 분리는 다음 단계로 남음

### 5.2 제대로 고치는 경우

목표: 플랫폼 역할과 도메인 역할을 명시적으로 분리

작업:

- `TenantContext`에 `platform_role`, `domain_roles` 추가
- `X-Platform-Role`, `X-Domain-Roles` 헤더 추가
- 기존 `X-Role`은 하위 호환용으로 유지
- 그래프 권한은 `platform_role` 기준
- 업무 액션 권한은 `domain_roles` 기준
- audit 로그에 두 역할 모두 저장
- 프론트 사용자 프리셋도 두 역할을 표시

장점:

- 장기 구조가 명확해짐
- 공장/고객사/금융/계정 등 여러 도메인 확장에 유리
- 워크플로우 노드별 승인/처리 권한 모델로 확장 가능

단점:

- 영향도가 크고 테스트 범위가 넓음
- 기존 문서/테스트 명령/저장 이력과 호환성 고려 필요

## 6. 권장 수정 계획

### Phase 1. 플랫폼 역할 명칭 정리

목표: 워크플로우/온톨로지 화면 권한에서 도메인 역할 제거

변경 대상:

- `frontend/src/types/api.ts`
- `frontend/src/context/UserContext.tsx`
- `frontend/src/hooks/usePermission.ts`
- `backend/app/services/workflow.py`
- `scenarios/v1/scenario1/80_WORKFLOW_BUILDER_SCENARIO_GRAPH_DESIGN.md`

권장 권한:

| 기능 | 허용 플랫폼 역할 |
| --- | --- |
| 워크플로우 조회 | `PlatformAdmin`, `WorkflowDesigner`, `WorkflowOperator`, `Analyst`, `Viewer` |
| 워크플로우 생성/수정/복제 | `PlatformAdmin`, `WorkflowDesigner` |
| 워크플로우 실행 dry_run | `PlatformAdmin`, `WorkflowDesigner`, `WorkflowOperator` |
| 워크플로우 실행 post | `PlatformAdmin`, `WorkflowOperator` 또는 `WorkflowDesigner` |
| 워크플로우 삭제 | `PlatformAdmin`, `WorkflowDesigner` |
| 온톨로지 스키마/인스턴스 편집 | `PlatformAdmin`, `OntologyManager` |
| 감사 로그 조회 | `PlatformAdmin`, `Analyst` |

예상 영향도: 중간  
예상 작업량: 작음~중간  
권장 우선순위: 높음

### Phase 2. API 헤더 호환 계층 추가

목표: 기존 `X-Role` 기반 호출을 유지하면서 새 역할 모델 준비

변경 대상:

- `backend/app/models/tenant_context.py`
- `backend/app/dependencies.py`
- `backend/app/api/workflow.py`
- `frontend/src/lib/api.ts`

권장 헤더:

```text
X-Platform-Role: WorkflowDesigner
X-Domain-Roles: FinanceManager,MaintenanceManager
X-Role: WorkflowDesigner  # 하위 호환
```

예상 영향도: 중간~높음  
예상 작업량: 중간  
권장 우선순위: 중간

### Phase 3. 도메인 노드 권한 분리

목표: 워크플로우 그래프 편집 권한과 업무 처리 권한을 완전히 분리

예시:

- 그래프 수정 가능자: `WorkflowDesigner`
- 정비 지시 승인 가능자: `MaintenanceManager`
- 품질 영향 승인 가능자: `QualityManager`
- 고객 계정 조치 승인 가능자: `AccountManager`
- 결제/금융 승인 가능자: `FinanceManager`

변경 대상:

- `workflow.json`
- 워크플로우 노드 data/rule schema
- 실행 executor의 노드별 권한 체크
- Trace/audit 표시

예상 영향도: 높음  
예상 작업량: 중간~큼  
권장 우선순위: 중간

## 9. 최종 권고

바로 전체 역할 모델을 갈아엎기보다, 다음 순서가 안전하다.

1. Phase 1부터 진행한다.
2. 워크플로우/온톨로지 화면 권한에서 `FinanceManager`, `AccountManager`를 제거한다.
3. 데모 사용자를 `WorkflowDesigner`, `WorkflowOperator`, `OntologyManager` 중심으로 바꾼다.
4. 기존 도메인 역할은 업무 액션/노드 권한에만 남긴다.
5. 이후 `TenantContext`를 확장해 플랫폼 역할과 도메인 역할을 명시적으로 분리한다.

즉시 수정 범위는 **프론트 타입/프리셋/권한 훅 + 백엔드 그래프 권한표 + 문서 권한표**까지가 적절하다. 이 범위는 영향도를 통제하면서도 현재 문제를 바로 해결할 수 있다.
