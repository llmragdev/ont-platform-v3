## 2. 기본 실행 구조

솔루션의 실행 흐름은 다음 순서로 이해하면 된다.

```text
외부 업무 이벤트
  -> 워크플로우 실행
  -> 스킬 또는 전용 Executor 실행
  -> RAG/온톨로지 조회
  -> 외부 MCP 서버 호출
  -> 외부 시스템에 댓글/정비지시 등록
  -> 실행 이력과 온톨로지 관계 저장
```

여기서 중요한 점은 AI 답변을 만드는 것에서 끝나지 않는다는 것이다.  
워크플로우가 실제 업무 시스템에 결과를 남기고, 그 실행 결과를 다시 온톨로지와 실행 이력으로 추적할 수 있어야 한다.

## 4. 표준 실행 절차

### 4.1 템플릿 선택

1. 좌측 메뉴에서 `Template Gallery` 또는 `Builder and Run`으로 이동한다.
2. 실행할 템플릿을 선택한다.
3. 필요하면 `Clone`으로 복제해 테스트용 워크플로우를 만든다.
4. 워크플로우 이름에 날짜나 목적을 붙여 구분한다.

예:

```text
서비스 요청 자동댓글 - 0614
현장 고장 요청 정비 지시 자동화 - 개발
```

### 4.2 실행 조건 설정

Builder and Run 화면에서 실행 전 다음 값을 확인한다.

| 항목 | 설명 |
|---|---|
| 실행 모드 | `dry_run`은 모의 실행, `post`는 실제 외부 시스템 등록 |
| status | 보통 `open` 상태의 미처리 건을 대상으로 실행 |
| 처리 건수 | 데모에서는 `1`을 권장 |
| 이미 처리한 요청도 재수행 | 재시연이나 반복 테스트 시 체크 |

### 4.3 실행

1. `Run` 버튼을 누른다.
2. 캔버스의 블록 상태가 진행 중 또는 완료 상태로 바뀌는지 확인한다.
3. 우측 실행 패널에서 진행률, 완료 단계, 오류 수를 확인한다.
4. `입출력` 탭에서 선택한 노드의 입력과 출력을 확인한다.

### 4.4 결과 확인

실행 후에는 세 군데를 확인한다.

| 확인 위치 | 확인 내용 |
|---|---|
| 외부 모의 게시판 | 댓글, 정비지시, 처리 결과가 실제 등록되었는지 |
| Workflow Trace | 실행 단계, 성공/실패, 입출력 이력이 남았는지 |
| Ontology Explorer | 요청, 답변, 설비, 정비지시 등의 관계가 저장되었는지 |

## 7. 데모 시 설명 포인트

시연자는 기능 하나하나보다 흐름을 강조해야 한다.

```text
이 화면은 AI 답변을 만드는 화면이 아니라,
업무 요청을 받아서 워크플로우로 처리하고,
처리 결과를 외부 시스템과 온톨로지에 동시에 남기는 화면입니다.
```

강조할 차별점은 다음과 같다.

| 차별점 | 설명 |
|---|---|
| RAG 단독이 아님 | 검색과 답변 생성 이후 실제 업무 실행까지 연결 |
| 워크플로우 기반 | 어떤 단계에서 어떤 판단과 실행이 일어났는지 추적 가능 |
| 온톨로지 기반 | 요청, 대상, 원인, 조치, 결과가 관계로 저장 |
| MCP 중계 | 외부 시스템 직접 호출이 아니라 표준 중계 계층을 통해 등록 |
| 멀티테넌트 지향 | company_id, project_id 기준으로 분리 가능 |

---

## 8. 운영 주의 사항

- 데모 중에는 처리 건수를 `1`로 두는 것이 안전하다.
- 실제 등록을 원하지 않으면 `dry_run`으로 먼저 실행한다.
- 이미 댓글이 달린 건을 다시 테스트하려면 `이미 처리한 요청도 재수행`을 체크한다.
- 외부 게시판의 Webhook 자동 트리거가 켜져 있으면 수동 배치 실행 전에 이미 처리될 수 있다.
- 실패한 경우 즉시 같은 버튼을 여러 번 누르기보다 Workflow Trace와 외부 게시판 로그를 먼저 확인한다.
