# 데이터 워크플로우/라인리지 화면 설계서

**문서 번호**: 01  
**작성자**: Codex  
**작성일**: 2026-06-14  
**대상 시스템**: ont_platform v5  
**목적**: 현재 온톨로지+워크플로우+RAG 통합 솔루션에 “데이터가 어디서 와서, 어떻게 처리되고, 어떤 업무 결과와 온톨로지 관계로 남는지”를 한눈에 보여주는 데이터 워크플로우/라인리지 화면을 설계한다.

---

## 1. 설계 배경

현재 v5 솔루션은 다음 기능을 이미 갖추고 있다.

- 워크플로우 템플릿 복제/수정/실행
- 고객사 문의 자동댓글 시나리오
- 공장 자동화 정비지시 시나리오
- 온톨로지 객체/관계 탐색
- RAG/온톨로지 질의
- 스킬 관리
- 실행 이력/입출력 확인
- 외부 MCP writeback

하지만 시연 관점에서는 아직 다음 질문에 대한 설명이 한 화면에서 충분히 보이지 않는다.

```text
이 데이터는 어디서 들어왔는가?
어떤 처리 단계를 거쳤는가?
어떤 워크플로우와 연결되었는가?
어떤 RAG/온톨로지 근거를 사용했는가?
어떤 외부 시스템에 결과를 남겼는가?
최종적으로 어떤 온톨로지 객체와 관계가 생성되었는가?
```

따라서 **데이터 흐름 + 워크플로우 실행 + 온톨로지 관계 + 외부 등록 결과**를 연결해 보여주는 화면이 필요하다.

---

## 2. 목표

### 2.1 1차 목표

1차 목표는 Palantir Foundry 전체를 구현하는 것이 아니다.  
현재 솔루션의 시연 설득력을 높이기 위해, 다음을 시각화하는 것이다.

```text
외부 데이터/이벤트
  -> 수집
  -> 분류/정제
  -> RAG/온톨로지 조회
  -> 워크플로우 실행
  -> 외부 시스템 writeback
  -> 온톨로지 객체/관계 저장
  -> 감사/실행 이력 저장
```

### 2.2 기대 효과

| 효과 | 설명 |
|---|---|
| 시연 설득력 증가 | 단순 워크플로우 그림이 아니라 데이터가 흘러가는 전체 구조를 보여준다. |
| Palantir식 구조 설명 | 데이터, 객체, 액션, 업무 결과가 연결되는 구조를 직관적으로 설명한다. |
| 장애 분석 강화 | 댓글/정비지시가 안 달렸을 때 어느 단계에서 끊겼는지 확인한다. |
| 온톨로지 가치 설명 | 왜 DB 로그가 아니라 관계형 업무 맥락 저장이 필요한지 보여준다. |
| 제품화 방향 제시 | 향후 데이터 파이프라인, 품질검사, 스케줄러, 계보 관리로 확장 가능하다. |

## 3. 범위

### 3.1 이번 설계에 포함

- 데이터 워크플로우 화면 신설
- 고객사 문의 자동댓글 데이터 흐름 표시
- 공장 자동화 정비지시 데이터 흐름 표시
- 워크플로우 실행과 데이터 흐름 연결
- 온톨로지 객체/관계 저장 결과 연결
- 외부 MCP 호출 결과 표시
- 실행 이력/감사 로그 연결
- 향후 기능 로드맵 정의

### 3.2 이번 설계에서 제외

아래는 Palantir Foundry급 데이터 플랫폼에 가까운 영역이므로, 이번 1차 구현 범위에서는 제외한다.

- 범용 ETL 파이프라인 엔진
- 대용량 분산 처리
- 데이터셋 버전 브랜칭
- 복잡한 데이터 품질 규칙 엔진
- 데이터 카탈로그 전체 기능
- 세밀한 행/열 수준 권한
- 배포 파이프라인
- 운영 스케줄러 전체 구현

## 4. 메뉴 배치 제안

### 4.1 권장 메뉴 위치

좌측 메뉴에 다음 메뉴를 추가한다.

```text
워크플로우
  - 데이터 흐름
```

또는 온톨로지 그룹에 둘 수도 있지만, 현재 화면 목적상 “워크플로우 실행과 데이터 흐름 연결”이 핵심이므로 **워크플로우 그룹 하위**가 더 적합하다.

### 4.2 메뉴명 후보

| 후보 | 장점 | 단점 |
|---|---|---|
| 데이터 흐름 | 쉽고 직관적 | lineange 의미가 약함 |
| 데이터 워크플로우 | 현재 기능과 잘 맞음 | 다소 기술적 |
| 실행 데이터 흐름 | 실행 결과와 연결됨 | 이름이 조금 김 |
| 데이터 라인리지 | 전문적 | 일반 사용자에게 어려움 |

권장 메뉴명:

```text
데이터 흐름
```

보조 설명:

```text
데이터 수집부터 온톨로지 저장까지 흐름 추적
```

## 5. 화면 개념

### 5.1 기본 화면 구조

```text
┌──────────────────────────────────────────────────────────────┐
│ 데이터 흐름                                                   │
│ 외부 데이터가 업무 결과와 온톨로지 관계로 이어지는 과정을 봅니다. │
├──────────────────────────────────────────────────────────────┤
│ [시나리오 선택] [워크플로우 선택] [최근 실행 선택] [새로고침]     │
├──────────────────────────────────────────────────────────────┤
│ 요약 카드                                                     │
│ - 데이터 소스 수                                               │
│ - 처리 단계 수                                                 │
│ - 생성 객체 수                                                 │
│ - 외부 등록 결과                                               │
├──────────────────────────────────────────────────────────────┤
│ 데이터 흐름 캔버스                                             │
│                                                              │
│ [외부 게시판] -> [이벤트 수집] -> [분류/정제]                  │
│       -> [RAG/온톨로지 조회] -> [워크플로우 실행]              │
│       -> [MCP 등록] -> [온톨로지 저장] -> [감사 로그]          │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│ 우측 상세 패널                                                 │
│ - 선택 단계 상세                                               │
│ - 입력/출력 데이터                                             │
│ - 관련 워크플로우 노드                                         │
│ - 관련 온톨로지 객체/관계                                      │
│ - 외부 호출 결과                                               │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 화면 탭 구성

우측 패널은 다음 탭으로 구성한다.

| 탭 | 설명 |
|---|---|
| 단계 상세 | 선택한 데이터 흐름 단계의 설명과 상태 |
| 입출력 | 해당 단계의 입력/출력 JSON 또는 요약 |
| 온톨로지 | 생성/참조된 객체와 관계 |
| 외부 호출 | MCP/API 호출 결과 |
| 이력 | 관련 workflow run, audit log, writeback log |

## 6. 데이터 흐름 타입

### 6.1 공통 흐름 타입

| 타입 | 설명 | 예 |
|---|---|---|
| source | 외부 데이터 또는 이벤트 발생 지점 | 고객사 게시판, 공장 게시판 |
| ingest | 이벤트 수집 또는 API 수신 | Webhook, Batch polling |
| transform | 분류, 정제, 추출 | 요청 분류, 자산 매핑 |
| retrieve | 지식/온톨로지 조회 | RAG 검색, 설비 이력 조회 |
| execute | 워크플로우/스킬 실행 | 답변 생성, 반복 고장 확인 |
| writeback | 외부 시스템 등록 | 댓글 등록, 정비지시 생성 |
| persist | 내부 저장 | 온톨로지 객체/관계 저장 |
| audit | 감사/실행 이력 | Workflow Trace, Audit Log |

### 6.2 노드 상태

| 상태 | 의미 | 화면 표시 |
|---|---|---|
| ready | 실행 전 | 회색 |
| running | 실행 중 | 파란색/진행 애니메이션 |
| success | 성공 | 녹색 |
| failed | 실패 | 빨간색 |
| skipped | 분기로 인해 미실행 | 연한 회색 |
| warning | 처리됐지만 주의 필요 | 주황색 |

## 7. 시나리오별 데이터 흐름

### 7.1 고객사 문의 자동댓글

```text
[고객사 게시판]
  -> [문의 이벤트 수신]
  -> [문의 분류]
  -> [RAG/온톨로지 근거 조회]
  -> [답변 초안 생성]
  -> [customer MCP 댓글 등록]
  -> [ExternalComment 저장]
  -> [ServiceRequest - has_reply - AutoReply 관계 저장]
  -> [감사 로그 기록]
```

화면에서 강조할 것:

- Webhook과 Batch가 같은 데이터 흐름으로 합류한다.
- 답변은 단순 LLM 출력이 아니라 워크플로우 실행 결과다.
- 외부 댓글 등록 결과가 온톨로지 관계로 남는다.

### 7.2 공장 자동화 정비지시

```text
[공장 현장 요청]
  -> [요청 이벤트 수집]
  -> [고장/품질 분류]
  -> [공장/라인/공정/설비 매핑]
  -> [고장 이력 조회]
  -> [반복 고장 판단]
  -> [정비지시/현장 안내 생성]
  -> [factory MCP 등록]
  -> [FaultEvent/MaintenanceTask/QualityIssue 관계 저장]
  -> [감사 로그 기록]
```

화면에서 강조할 것:

- 현장 요청이 설비와 생산 라인으로 연결된다.
- 같은 설비의 반복 이력을 확인한다.
- 정비지시가 단순 댓글이 아니라 고장 이벤트와 관계로 저장된다.

## 8. 온톨로지와의 연결

데이터 워크플로우 화면은 온톨로지 화면과 분리된 별도 기능이 아니라, 온톨로지 저장 결과를 설명하기 위한 중간 다리 역할을 한다.

### 8.1 연결 방식

| 데이터 흐름 단계 | 온톨로지 연결 |
|---|---|
| 문의/현장 요청 수집 | ServiceRequest 객체 생성/조회 |
| 자산 매핑 | Factory, ProductionLine, ProcessStep, Equipment 참조 |
| 반복 고장 판단 | FaultEvent 조회/생성 |
| 답변 생성 | AutoReply 객체 생성 |
| 정비지시 생성 | MaintenanceTask 객체 생성 |
| 외부 등록 | ExternalComment 또는 ExternalWorkOrder 객체 생성 |
| 감사 기록 | WorkflowExecution과 관련 객체 연결 |

### 8.2 화면 이동

데이터 흐름 노드에서 다음 화면으로 이동할 수 있어야 한다.

| 클릭 대상 | 이동 화면 |
|---|---|
| ServiceRequest | 객체 탐색 또는 관계 탐색 |
| FaultEvent | 관계 탐색 |
| MaintenanceTask | 인스턴스 편집 또는 관계 탐색 |
| WorkflowExecution | 실행 추적 |
| MCP 호출 | 감사 로그 또는 Writeback DLQ |
| RAG 검색 결과 | 문서 RAG 질의 또는 통합 질의 |

## 9. 워크플로우와의 연결

### 9.1 관계

워크플로우는 “업무 처리 절차”이고, 데이터 워크플로우는 “데이터가 그 절차를 따라 어떻게 이동했는지”를 보여준다.

```text
Workflow Node
  -> Data Flow Step
  -> Ontology Object/Link
  -> Audit/Trace Record
```

### 9.2 Builder and Run 화면과 연동

Builder and Run 화면에서 특정 노드를 선택하면, 데이터 흐름 화면에서 해당 단계가 하이라이트되어야 한다.

예:

| 워크플로우 노드 | 데이터 흐름 단계 |
|---|---|
| Request Input | source/ingest |
| Intent Classify | transform |
| Asset Map | transform/persist |
| Repeat Check | retrieve/execute |
| Draft Response | execute |
| MCP Comment | writeback |
| Ontology Write | persist/audit |

## 11. API 설계 제안

### 11.1 데이터 흐름 정의 목록

```http
GET /api/data-flows
```

응답:

```json
{
  "items": [
    {
      "flow_id": "scenario1-customer-question",
      "name": "고객사 문의 자동댓글 데이터 흐름",
      "scenario_id": "scenario1"
    }
  ]
}
```

### 11.2 데이터 흐름 상세

```http
GET /api/data-flows/{flow_id}
```

### 11.3 실행 결과와 결합된 데이터 흐름 조회

```http
GET /api/data-flows/{flow_id}/runs/{workflow_run_id}
```

또는 최근 실행 기준:

```http
GET /api/data-flows/{flow_id}/latest
```

### 11.4 워크플로우 기준 데이터 흐름 조회

```http
GET /api/workflows/{workflow_id}/data-flow
```

### 11.5 시나리오 기준 데이터 흐름 조회

```http
GET /api/scenarios/{scenario_id}/data-flow
```

## 17. Palantir식 표현과의 관계

Palantir Foundry/AIP 관점으로 보면 이 화면은 다음 개념을 경량화한 것이다.

| Palantir식 개념 | 우리 솔루션의 대응 |
|---|---|
| Ontology object/link | 온톨로지 객체/관계 |
| Action type / Function | 워크플로우 노드, 스킬, MCP 호출 |
| Operational workflow | Builder and Run |
| Data lineage | 데이터 흐름 화면 |
| Object Explorer | 관계 탐색, 객체 탐색 |
| AIP Logic/RAG/OAG | RAG/온톨로지 질의, 통합 질의 |
| Audit/Governance | 감사 로그, 실행 추적, DLQ |

외부 설명 시에는 다음처럼 말하는 것이 적절하다.

```text
Palantir 전체 플랫폼을 구현한 것이 아니라,
Palantir식 온톨로지 기반 업무 실행 구조의 핵심 흐름을
경량 PoC 형태로 구현하고 있습니다.
이번 데이터 흐름 화면은 데이터가 업무 실행과 온톨로지 관계로 이어지는 과정을
시각적으로 설명하기 위한 화면입니다.
```

## 18. 우선 구현 권고

현재 시연 완성도를 높이는 목적이라면 다음 순서가 가장 좋다.

1. `데이터 흐름` 메뉴 추가
2. 공장 자동화 시나리오 정적 데이터 흐름 표시
3. 워크플로우 실행 결과와 단계 상태 연결
4. 노드 클릭 시 관련 온톨로지 객체/관계 링크 표시
5. 고객사 자동댓글 시나리오 추가
6. 감사 로그/MCP 호출 결과 연결

가장 먼저 만들 화면은 **공장 자동화 데이터 흐름**이다.  
공장, 라인, 공정, 설비, 고장, 정비지시가 연결되기 때문에 온톨로지의 장점이 가장 직관적으로 드러난다.

## 19. 결론

데이터 워크플로우/라인리지 화면은 현재 v5 솔루션의 부족한 설명력을 보완하는 핵심 화면이다.

현재 화면은 워크플로우 실행과 온톨로지 관계를 각각 보여줄 수 있지만,  
외부 시연자가 보기에 “데이터가 어디서 와서 어떤 업무 결과로 이어졌는지”는 한눈에 보이지 않는다.

따라서 이 화면을 추가하면 다음 메시지를 훨씬 강하게 전달할 수 있다.

```text
이 솔루션은 AI가 답변만 만드는 챗봇이 아니라,
데이터가 업무 절차를 따라 흐르고,
외부 시스템에 결과를 남기며,
그 결과가 온톨로지 관계로 저장되는 업무 실행형 AI 플랫폼입니다.
```
