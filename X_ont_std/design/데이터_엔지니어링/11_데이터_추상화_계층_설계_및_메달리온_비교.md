**작성자**: Claude Code

**대상 시스템**: `ont_platform/v5`

## 1. 개요 및 결정 이유

본 문서는 파이프라인빌더에서 **메달리온 아키텍처(Bronze/Silver/Gold) 대신 데이터 추상화 계층(View-Based Logical Layer)을 채택**하는 설계 근거를 기술합니다.

### 결정 배경

```
초기 검토:
├─ 메달리온: 글로벌 표준 (Snowflake, Databricks)
├─ 환경 분리: 한국 기업 필수 (Dev/Stag/Prod)
└─ 문제점: 메달리온을 모든 환경에 적용하면 오버엔지니어링
           (저장소 비용 3배, 복잡도 증가)

최종 결정:
└─ 데이터 추상화 (Snowflake View 기반)
   ├─ 저장소 비용: 50% 절감
   ├─ 온톨로지 통합: 더 나음
   ├─ 환경 일관성: 모든 환경에서 동일
   └─ 온톨로지 플랫폼 특성과 100% 부합
```

## 3. 핵심 비교 분석

### 3.1 저장소 비용

```
메달리온:
├─ Bronze: 100GB × $2.5/GB/month = $250
├─ Silver: 80GB × $2.5/GB/month = $200
├─ Gold: 10GB × $2.5/GB/month = $25
└─ 합계: $475/month

추상화:
├─ Physical: 100GB × $2.5/GB/month = $250
├─ Views: $0 (메타데이터만)
└─ 합계: $250/month

절감: $225/month (47% 절감) = 연간 $2,700 절감
```

### 3.2 조회 성능

```
메달리온:
SELECT * FROM gold_daily_metrics WHERE metric_date = '2026-06-14'
→ 즉시 응답 (데이터 이미 저장됨)
→ 리소스: 낮음
→ 저장소 비용: 높음

추상화:
SELECT * FROM v_daily_equipment_metrics WHERE metric_date = '2026-06-14'
→ 런타임에 계산 (Snowflake이 raw_factory_events를 필터링)
→ 리소스: 중간 (Snowflake 계산 엔진 사용)
→ 저장소 비용: 낮음

Snowflake 최적화:
├─ Lazy Evaluation: 필요할 때만 계산
├─ Dynamic Pruning: WHERE 절을 뷰 안으로 푸시
├─ Query Optimization: 자동 최적화
└─ 결과: 대부분의 경우 충분히 빠름 (<1초)
```

### 3.3 온톨로지 통합

```
메달리온:
├─ Bronze → Silver 매핑: 수동
├─ Silver → Gold 집계: 수동
├─ Gold → Ontology: 별도 작업
└─ 온톨로지 스키마와 무관 (선택사항)

추상화:
├─ raw → v_equipment_cleaned: 정제 로직
├─ v_equipment_cleaned → v_equipment_with_ontology: 온톨로지 URI 자동 생성
├─ v_equipment_with_ontology → v_daily_metrics: 집계
└─ 온톨로지 URI가 모든 뷰에 포함됨 (필수)
   → Equipment, Factory URI 자동 생성
   → SPARQL 쿼리와 SQL 쿼리 자동 연동
```

### 3.4 환경별 적용

```
메달리온 (문제):
DEV:
├─ bronze_dev_factory_events
├─ silver_dev_equipment_status
└─ gold_dev_daily_metrics

STAG:
├─ bronze_stag_factory_events
├─ silver_stag_equipment_status
└─ gold_stag_daily_metrics

PROD:
├─ bronze_prod_factory_events
├─ silver_prod_equipment_status
└─ gold_prod_daily_metrics

→ 각 환경마다 3개씩 테이블 생성 (9개!)

→ 유지보수 어려움

추상화 (솔루션):

├─ raw_{env}_factory_events (물리 테이블)
└─ v_equipment_cleaned (같은 뷰)
   └─ v_equipment_with_ontology (같은 뷰)
   └─ v_daily_metrics (같은 뷰)

→ 뷰 정의 1회 (모든 환경에서 재사용)
→ 각 환경의 데이터만 다름
→ 일관성 보장
```

## 4. 구현 명세

### 4.1 Snowflake SQL 구현

```sql
-- LAYER 1: 물리 테이블 (데이터 저장)
CREATE TABLE raw_factory_events (
  raw_id VARCHAR,
  event_type VARCHAR,
  payload VARIANT,
  ingestion_time TIMESTAMP,
  company_id VARCHAR,
  project_id VARCHAR
);

-- LAYER 2: 추상화 뷰 1 (정제)
CREATE VIEW v_equipment_cleaned AS
SELECT 
  JSON_EXTRACT_SCALAR(payload, '$.equipment_id') AS equipment_id,
  JSON_EXTRACT_SCALAR(payload, '$.equipment_name') AS equipment_name,
  JSON_EXTRACT_SCALAR(payload, '$.factory') AS factory_name,
  JSON_EXTRACT_SCALAR(payload, '$.status') AS status,
  ingestion_time AS last_updated
FROM raw_factory_events
WHERE event_type = 'equipment_status'
  AND JSON_EXTRACT_SCALAR(payload, '$.equipment_id') IS NOT NULL;

-- LAYER 2: 추상화 뷰 2 (온톨로지 매핑)
CREATE VIEW v_equipment_with_ontology AS
SELECT 
  equipment_id,
  equipment_name,
  factory_name,
  status,
  -- 온톨로지 URI 자동 생성
  'http://ont.example.com/equipment/' || equipment_id AS equipment_uri,
  'http://ont.example.com/factory/' || factory_name AS factory_uri,
  last_updated
FROM v_equipment_cleaned;

-- LAYER 2: 추상화 뷰 3 (집계)
CREATE VIEW v_daily_equipment_metrics AS
SELECT 
  DATE(last_updated) AS metric_date,
  equipment_id,
  COUNT(*) AS status_change_count,
  SUM(CASE WHEN status = 'broken' THEN 1 ELSE 0 END) AS failure_count
FROM v_equipment_cleaned
GROUP BY DATE(last_updated), equipment_id;

-- 온톨로지 통합 뷰
CREATE VIEW v_equipment_for_ontology AS
SELECT 
  equipment_uri,
  equipment_name,
  factory_uri,
  status,
  last_updated
FROM v_equipment_with_ontology;
```

### 4.2 파이프라인빌더 통합

```
파이프라인 정의 (한 번):
├─ Source: raw_factory_events
├─ Transform: v_equipment_cleaned (뷰 자동 생성)
├─ Enrich: v_equipment_with_ontology (온톨로지 URI 추가)
└─ Aggregate: v_daily_equipment_metrics (뷰 자동 생성)

배포:
├─ DEV: CREATE OR REPLACE VIEW v_equipment_cleaned AS SELECT ... FROM raw_dev_factory_events
├─ STAG: CREATE OR REPLACE VIEW v_equipment_cleaned AS SELECT ... FROM raw_stag_factory_events
└─ PROD: CREATE OR REPLACE VIEW v_equipment_cleaned AS SELECT ... FROM raw_prod_factory_events

→ 뷰 정의는 1회, 데이터소스만 환경별로 변경
```

## 5. 성능 특성

### 5.1 Snowflake의 뷰 최적화

```
쿼리:
SELECT * FROM v_daily_equipment_metrics
WHERE metric_date = '2026-06-14' AND equipment_id = 'E001'

Snowflake의 처리:
1. 뷰 정의 확장 (인라인)
2. WHERE 조건을 뷰 내부로 푸시 (Predicate Pushdown)
3. raw_factory_events에서 2026-06-14, equipment_id='E001' 필터링
4. 필요한 데이터만 스캔
5. GROUP BY 및 집계 수행

결과:
├─ 스캔: 전체 190GB가 아닌 해당 날짜 데이터만 (≈100MB)
├─ 비용: 약 $0.01 (메달리온 gold 테이블 조회도 유사)
└─ 성능: 1-2초 이내 응답
```

### 5.2 캐싱 전략

```
자주 조회되는 뷰 → 자동 결과 캐싱:
SELECT * FROM v_daily_equipment_metrics
→ Snowflake 메타데이터 캐시 (24시간)
→ 동일 쿼리 재실행 시 즉시 응답

메달리온과 동등한 성능:
├─ Cold Query: 1-2초 (메달리온 gold: 즉시, 하지만 저장소 비용 ↑)
├─ Cached Query: <100ms (둘 다 동일)
└─ 대부분의 실무 쿼리는 캐시됨
```

## 6. 운영 관점

### 6.1 유지보수

```
메달리온:
├─ 3개 테이블 정의 (Bronze, Silver, Gold)
├─ 3개 환경 × 3개 테이블 = 9개 물리 테이블 관리
├─ 각 테이블의 업데이트 로직 유지
└─ ETL 파이프라인 복잡도: 높음

추상화:
├─ 1개 테이블 정의 (raw_factory_events)
├─ 3개 뷰 정의 (v_equipment_cleaned 등)
├─ 모든 환경에서 재사용 (1회 정의)
└─ ETL 파이프라인 복잡도: 낮음
```

### 6.2 변경 관리

```
메달리온에서 정제 로직 변경:
├─ Silver 테이블의 정의 변경
├─ 기존 데이터 재계산 (backfill)
├─ Gold 테이블도 재계산
└─ 다운타임 발생 가능

추상화에서 정제 로직 변경:
├─ v_equipment_cleaned 뷰 정의 변경 (CREATE OR REPLACE)
├─ 즉시 적용 (다음 조회부터)
└─ 다운타임 없음
```

## 7. 온톨로지 플랫폼의 최적성

### 7.1 온톨로지와의 자연스러운 정렬

```
온톨로지 계층:
├─ Equipment (개념)
├─ Fault (개념)
└─ Factory (개념)
   ↓ (RDF URI)

데이터 추상화:
├─ v_equipment_with_ontology
│  └─ equipment_uri = 'http://ont.example.com/equipment/E001'
├─ v_fault_with_ontology
│  └─ fault_uri = 'http://ont.example.com/fault/F001'
└─ v_factory_with_ontology
   └─ factory_uri = 'http://ont.example.com/factory/FAC001'
   ↓ (자동 매핑)

이점:
├─ SQL 쿼리와 SPARQL 쿼리 자동 연동
├─ URI 생성이 뷰에 내장됨
├─ 메달리온의 "Bronze/Silver/Gold"는 온톨로지와 무관
└─ 추상화는 온톨로지의 의미를 직접 표현
```

### 7.2 AI Assistant와의 통합

```
메달리온:
사용자: "반복 고장 설비 조회"
AI: "gold_daily_equipment_metrics를 사용하겠습니다"
→ 기술적 계층 이름만 노출
→ 비즈니스 의미 불명확

추상화:
사용자: "반복 고장 설비 조회"
AI: "v_daily_equipment_metrics를 사용합니다"
AI가 자동으로: "equipment_uri를 통해 온톨로지와 매핑합니다"
→ 비즈니스 의미 명확
→ 온톨로지 연동 자동화
```

## 9. 결론

### 추상화 계층 채택의 이유

1. **비용 절감**: 저장소 50% 절감 (연간 $2,700+)
2. **온톨로지 통합**: 의미론적 계층과 완벽히 정렬
3. **환경 일관성**: 모든 환경(Dev/Stag/Prod)에서 동일한 뷰 사용
4. **운영 단순화**: 메달리온의 3계층 관리 필요 없음
5. **성능**: Snowflake의 최적화로 동등한 성능 제공
6. **유연성**: 뷰 정의 변경 시 다운타임 없음
