## 1. 최종 판정

다른 에이전트 보고서의 방향성은 대체로 타당하다.

하지만 현재 코드 기준으로 보면 **"UI와 백엔드 양쪽 모두 구현 완료"라는 판정은 아직 성급하다.**

현재 상태는 다음과 같이 보는 것이 정확하다.

```text
백엔드 adaptive_query.py: 기본 정책 분기 구조 존재
프론트 AdaptiveQueryInterface.tsx: 생성됨
프론트 api.queryStream: 옵션 전달 일부 구현됨

그러나:
- 옵션 파라미터 이름 일부 불일치
- SSE sources 이벤트가 store에 반영되지 않음
- complete 이벤트 메타데이터 이름 불일치
- UI가 라디오가 아니라 select 형태
- 24문항 모드별 평가는 아직 실행 완료로 보기 어려움
```

따라서 현 단계는 **설계 승인 + 구현 진행 중 + 계약 정합성 보완 필요** 상태다.

## 3. Antigravity 보고서 검토

### 3.1 타당한 부분

Antigravity의 향후 로드맵은 큰 방향에서 적절하다.

특히 다음 제안은 유지할 가치가 있다.

1. LLM 프롬프트에 체크박스 상태를 동적으로 주입
2. 단순 키워드 검사를 넘어 semantic relevance judge 도입
3. citation highlighting으로 답변-출처 연결 강화
4. Graph-RAG, NL2SPARQL, rules 계층으로 장기 확장
5. 사용자 피드백 루프를 평가 시스템에 반영

이 방향은 현재 사용자가 지적한 "관련 없음과 설명 가능을 분리하라"는 요구와 잘 맞는다.

### 3.2 정정이 필요한 부분

Antigravity 보고서에는 다음 표현이 있다.

```text
Phase 2 완료
UI/UX 세밀화 완료
Relevance Guardrail 백엔드 구축
```

이 표현은 현재 코드 기준으로는 정정이 필요하다.

실제 확인 결과:

- `AdaptiveQueryInterface.tsx`는 현재 생성되어 있으나 구현 정합성 점검이 필요하다.
- `api.queryStream()`은 옵션을 보내지만 백엔드 파라미터명과 일부 다르다.
- `sources` 이벤트를 받아도 store에 저장하지 않는다.
- `complete` 이벤트에서 백엔드가 보내는 필드명과 프론트가 기대하는 필드명이 다르다.

따라서 표현은 다음이 더 정확하다.

```text
Phase 2 옵션 시스템은 설계 완료 및 일부 구현 상태.
UI-백엔드 계약 정합성 보완 후 완료 판정 가능.
```

## 5. PM 정정보고서 검토

PM의 `0620-18` 보고서는 현재도 기준 문서로 삼을 만하다.

핵심 장점:

1. RAG를 성공/실패로 단순 판정하지 않고 "부분 성공"으로 분리했다.
2. 온톨로지 0개의 1차 원인을 검색 로직이 아니라 데이터 부재로 정정했다.
3. 질의 확장, 메타데이터 활용, 하이브리드 청킹을 RAG 개선 방향으로 제시했다.
4. 추정 점수와 검증된 사실을 구분하려는 태도가 있다.

현재 Phase 2 옵션 시스템도 이 관점을 따라야 한다.

즉:

```text
검색 결과가 있다 = 답변 가능
```

이 아니라,

```text
검색 결과가 질문 주제와 관련 있다 = 문서 기반 답변 가능
검색 결과가 있지만 질문 주제와 무관하다 = 관련 없음 또는 일반 설명 분리
```

로 판정해야 한다.

## 6. 현재 코드 동기화 점검

### 6.1 백엔드

파일:

`backend/app/api/adaptive_query.py`

현재 확인:

- `hide_irrelevant` 수신
- `allow_partial` 수신
- `separate_sources` 수신
- `allow_general` 수신
- `document_only`, `document_with_limits`, `expert_mode` 모드 분기 존재
- `python -m py_compile app\api\adaptive_query.py app\main.py` 통과

주의:

백엔드 파라미터명은 `separate_sources`다.

### 6.2 프론트 API

파일:

`frontend/src/lib/api.ts`

현재 확인:

- `hide_irrelevant` 전달
- `allow_partial` 전달
- `allow_general` 전달
- `separate_general` 전달

문제:

백엔드는 `separate_sources`를 받는데, 프론트는 `separate_general`을 보낸다.

결과:

프론트에서 "출처 없는 일반 설명 분리" 체크박스를 바꿔도 백엔드의 `separate_sources`에는 반영되지 않는다.

해결:

프론트 파라미터명을 다음처럼 바꿔야 한다.

```ts
separate_sources: (options?.separate_sources ?? true).toString()
```

또는 백엔드가 `separate_general` alias를 추가로 받아야 한다.

권장:

백엔드 표준명 `separate_sources`로 통일한다.

### 6.3 프론트 질의 UI

파일:

`frontend/src/components/query/AdaptiveQueryInterface.tsx`

현재 확인:

- 질문 입력 있음
- 모드 선택 있음
- 체크박스 4개 있음
- 모드 변경 시 기본값 변경 로직 있음
- `api.queryStream()` 호출 있음

문제:

1. PM 설계는 라디오 버튼이었으나 현재 UI는 select다.
2. 옵션 이름 `separateGeneral`이 백엔드 의미인 `separate_sources`와 다르다.
3. `sources` 이벤트를 store에 반영하지 않는다.
4. `complete` 이벤트 처리에서 백엔드 필드명과 프론트 기대 필드명이 다르다.

## 7. SSE 이벤트 계약 불일치

### 7.1 백엔드가 보내는 것

백엔드 `complete` 이벤트 예:

```json
{
  "confidence": 0.92,
  "level": 4,
  "mode": "expert_mode",
  "policy": {},
  "evidence": {},
  "source_counts": {}
}
```

백엔드는 출처를 별도 `sources` 이벤트로 보낸다.

### 7.2 프론트가 기대하는 것

프론트 `AdaptiveQueryInterface.tsx`는 `complete`에서 다음을 기대한다.

```ts
coverage_level: meta.relevance_level || 3,
confidence_score: meta.confidence_score || 0.85,
sources: meta.sources || { rag: [], ontology: [], expert_opinions: [] },
limitations: meta.limitations || [],
follow_up_suggestions: meta.follow_up_suggestions || []
```

문제:

| 항목 | 백엔드 | 프론트 기대 | 결과 |
---|---|---|---|
| 신뢰도 | `confidence` | `confidence_score` | 프론트가 fallback 85% 사용 가능 |
| 레벨 | `level` | `relevance_level` | 프론트가 fallback 3 사용 가능 |
| 출처 | `sources` 이벤트 | `complete.meta.sources` | 출처가 store에 저장되지 않을 수 있음 |
| 분리 옵션 | `separate_sources` | `separate_general` | 체크박스 값 미반영 |

이 상태에서는 UI에서 실제 RAG/Ontology 탭이 비거나, 신뢰도/레벨이 백엔드 판정과 다르게 보일 수 있다.

## 8. 즉시 수정 권장 사항

### 8.1 프론트 파라미터명 통일

`api.ts`와 `AdaptiveQueryInterface.tsx`에서:

```ts
separate_general
```

을

```ts
separate_sources
```

로 변경한다.

### 8.2 sources 이벤트 store 반영

현재 `api.ts`는 `sources` 이벤트를 console.log만 한다.

수정 방향:

1. `queryStream` callbacks에 `onSources` 추가
2. `sources` 이벤트 수신 시 `callbacks.onSources(data)` 호출
3. store에 `updateSources(sources)` 액션 추가
4. `AdaptiveQueryInterface.tsx`에서 `onSources` 연결

### 8.3 complete 메타 필드명 보정

프론트에서 다음처럼 처리한다.

```ts
finishQuery({
  coverage_level: meta.level ?? meta.relevance_level ?? 1,
  confidence_score: meta.confidence ?? meta.confidence_score ?? 0,
  limitations: meta.limitations || [],
  follow_up_suggestions: meta.follow_up_suggestions || []
});
```

또는 백엔드가 호환 필드를 함께 내려준다.

권장:

백엔드도 다음 필드를 추가로 내려서 기존 프론트와 호환한다.

```json
{
  "confidence": 0.92,
  "confidence_score": 0.92,
  "level": 4,
  "relevance_level": 4
}
```

### 8.4 UI 모드 선택을 라디오로 변경

PM 설계에 맞추려면 select보다 radio가 적합하다.

현재 select도 기능상 큰 문제는 아니지만, "라디오 구현 완료"라고 보고하려면 UI를 실제 라디오로 바꿔야 한다.

## 10. 최종 권고

다른 에이전트 보고서는 폐기할 필요가 없다.

다만 공식 상태 문구는 다음처럼 정정하는 것이 안전하다.

```text
Phase 2 평가 옵션 시스템은 설계 완료 및 구현 진행 중이다.
백엔드는 모드/옵션 파라미터를 수신할 수 있고, 프론트에는 질의 UI와 체크박스가 생성되었다.
그러나 파라미터명, SSE sources 저장, complete 메타 필드명이 아직 완전히 일치하지 않아
최종 완료 판정 전 UI-백엔드 계약 보정과 수동 테스트가 필요하다.
```

다음 작업 순서:

1. `separate_general` → `separate_sources` 통일
2. `sources` 이벤트 store 저장
3. `confidence/level` 필드 프론트 매핑 보정
4. select를 라디오로 바꿀지 결정
5. Snowflake 질문으로 3개 모드 수동 테스트
6. 모드별 24문항 평가 실행
