## 2. 파이프라인 추적 결과

### 2.1 업로드와 벡터화 트리거

`app/main.py` 확인 결과:

- `/api/documents/upload`는 문서를 업로드하고 상태를 `uploaded`로 기록한다.
- `/api/documents/{doc_id}/vectorize`는 `trigger_ontology_extraction()`을 백그라운드 태스크로 등록한다.
- `trigger_ontology_extraction()`은 `scripts/generate_ontology_from_pdf.py`를 subprocess로 실행한다.

따라서 트리거 구조 자체는 존재한다.

### 2.2 직접 실행 검증

대상 문서:

```text
doc-75349dc3
국방 - [02] 해외 온톨로지 현황과 한국군 온톨로지 개발방안_202306.pdf
```

직접 실행 명령:

```powershell
python scripts\generate_ontology_from_pdf.py "<pdf_path>" doc-75349dc3 --company demo-co --project proj-deafe1fe --user codex-pipeline-check
```

초기 실행 결과:

```text
LLM generate ok chars=2227
JSON 파싱 실패: Unterminated string ...
온톨로지 생성 완료!
저장된 엔티티: 0개
저장된 관계: 0개
```

핵심 문제:

```text
LLM JSON 파싱 실패가 발생했는데도 스크립트가 complete 상태로 종료됨.
```

즉, 실제 근본 원인은 다음과 같다.

```text
LLM 응답 JSON 절단/파싱 실패
→ entities=[], relationships=[] 반환
→ 0개 저장
→ 그래도 문서 상태 complete 처리
→ ontology 폴더가 비어 있는 상태로 정상 완료처럼 보임
```

## 3. 적용 조치

적용 파일:

```text
E:\ontology_edu\X_ont_std\ont_platform\v5\backend\scripts\generate_ontology_from_pdf.py
```

조치 내용:

1. LLM 입력 텍스트 길이 축소
   - 5000자 → 4000자

2. LLM 출력 토큰 증가
   - 기본 1024 → 4096

3. 추출 개수 제한
   - entities 최대 5개
   - relationships 최대 5개
   - description 80자 이내

4. JSON 파싱 함수 추가
   - Markdown code fence 제거
   - 앞뒤 불필요 텍스트 제거
   - root object/list 타입 검증

5. 실패 처리 강화
   - LLM 응답 없음 → 예외
   - JSON 파싱 실패 → 예외
   - 저장 엔티티 0개 → 예외
   - 더 이상 0개 저장을 `complete`로 위장하지 않음

6. 엔티티 ID 처리 개선
   - LLM이 `id`를 준 경우만 보존
   - 없으면 `OntologyService.upsert_entity()`의 UUID 생성 로직 사용
