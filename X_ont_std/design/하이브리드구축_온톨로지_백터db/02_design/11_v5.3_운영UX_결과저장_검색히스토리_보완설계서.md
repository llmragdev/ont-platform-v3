- 작성일: 2026-06-24

- 대상 구현: `ont_platform/v5`
- 관련 기준 설계: `10_v5.3_RAG_Ontology_환각차단_정식설계서.md`

## 1. 배경

v5.3 Phase 1 구현과 UI smoke 과정에서 다음 운영 요구가 추가 확인되었다.

1. Snowflake 등 외부 도메인 질문은 문서 제한 모드에서 `NO_ANSWER / 0%`로 차단되어야 한다.
2. 전문가 모드는 일반 설명을 허용하되 `GENERAL_ONLY / 55%`로 과신을 낮춰야 한다.
3. 질의 시작 직후 `관련 정보 없음` 메시지가 먼저 보이면 사용자가 오류로 오해한다.
4. 평가 결과를 매번 수동 캡처하지 않고 Word 파일로 저장해야 한다.
5. 같은 질문을 반복 검색하지 않고 검색 히스토리에서 즉시 다시 볼 수 있어야 한다.
6. 재조회 시 답변뿐 아니라 RAG source, ontology source, ontology graph도 함께 복원되어야 한다.

본 문서는 위 요구를 기존 v5.3 설계에 보완 반영한다.

## 2. 현재 구현 기준

### 2.1 Answerability Gate

현재 확인된 정책:

| answer_status | confidence_score | 의미 |
|---|---:|---|
| `NO_ANSWER` | `0.0` | 문서/온톨로지 직접 근거 부족으로 답변 차단 |
| `GENERAL_ONLY` | `0.55` | 전문가 모드에서 일반 설명 허용, 문서 근거 부족 경고 |
| `PARTIAL` | `0.75` | 제한적 근거 기반 부분 답변 |
| 정상 근거 충분 | `0.95` | 문서/온톨로지 근거 기반 답변 |

### 2.2 모드별 기대 동작

| 모드 | allow_general | 기대 동작 |
|---|---:|---|
| `document_only` | false | 직접 근거 없으면 `NO_ANSWER` |
| `document_with_limits` | false | 직접 근거 부족 시 `NO_ANSWER`, 일부 근거면 `PARTIAL` |
| `expert_mode` | true | 직접 근거 부족해도 `GENERAL_ONLY` 가능 |

Snowflake smoke 결과:

- `expert_mode`: `GENERAL_ONLY / 55%`
- `document_with_limits`: `NO_ANSWER / 0%`

이 결과는 설계상 정상으로 본다. 단, 전문가 모드 화면에는 “문서 근거 없음 / 일반 설명” 경고를 더 명확히 표시해야 한다.

## 3. 운영 UX 보완 설계

### 3.1 초기 검색 상태

문제:

- 질의 시작 직후 임시 `coverage_level=0` 상태가 Level 1처럼 렌더링되어 `관련 정보 없음` 메시지가 먼저 보였다.

설계:

- `isStreaming === true`이고 `answer`가 비어 있으면 별도 `검색 중` 상태로 렌더링한다.
- 이 상태에서는 `NO_ANSWER`, `관련 정보 없음`, `0%` 등 최종 판정 UI를 노출하지 않는다.

표시 문구:

```text
검색 중
문서, 온톨로지, 전문가 근거를 확인하고 있습니다.
```

완료 조건:

- SSE `complete` 이벤트 수신 후 `answer_status` 기준으로 최종 UI를 렌더링한다.

### 3.2 Word 저장

문제:

- UI smoke와 성능 평가에서 매번 화면 캡처와 문서 정리가 필요했다.

현재 최소 구현:

- 답변 완료 후 `Word 저장` 버튼 표시
- `html2canvas`로 답변/근거 패널 캡처
- Word 호환 HTML `.doc` 파일로 다운로드

저장 항목:

- 생성 시각
- 질문
- 답변 모드
- v5.3 판정
- gate decision
- confidence
- coverage level
- 답변 본문
- 제한사항
- 답변/근거 패널 캡처 이미지

보완 사항:

- 캡처 이미지는 문서 폭에 맞게 `width=680px`, `max-width=100%`로 삽입한다.
- `.doc` 방식은 Word 보호 보기/편집 모드 이슈가 남을 수 있다.

Phase 2 개선:

- 정식 `.docx` 생성으로 전환한다.
- `docx` 패키지 또는 백엔드 `python-docx` 기반 생성 중 선택한다.
- 이미지, 표, source, graph를 구조화된 Word 섹션으로 저장한다.

## 4. 검색 히스토리 및 결과 캐시 설계

### 4.1 목표

한 번 검색한 결과는 다시 API를 호출하지 않고 리스트에서 즉시 재열람할 수 있어야 한다.

핵심 목표:

```text
질문 재클릭
→ 이전 답변 즉시 표시
→ RAG/ontology/expert source 즉시 표시
→ ontology graph 즉시 복원
→ 필요 시에만 재검색 버튼으로 갱신
```

### 4.2 저장 단위

검색 히스토리는 단순 질문 문자열이 아니라 “완료된 Query Snapshot” 단위로 저장한다.

필수 필드:

```ts
interface QuerySnapshot {
  query_id: string;
  question: string;
  normalized_question: string;
  mode: 'document_only' | 'document_with_limits' | 'expert_mode';
  options: {
    hide_irrelevant: boolean;
    allow_partial: boolean;
    separate_sources: boolean;
    allow_general: boolean;
  };
  answer: string;
  coverage_level: number;
  confidence_score: number;
  v5_3: {
    answer_status: string;
    gate_status?: string;
    gate?: Record<string, unknown>;
    entity_gate?: Record<string, unknown>;
    thresholds?: Record<string, unknown>;
  };
  sources: {
    rag: unknown[];
    ontology: unknown[];
    expert_opinions: unknown[];
    ontology_graph?: OntologyGraphSnapshot;
  };
  limitations: unknown[];
  follow_up_suggestions: unknown[];
  created_at: string;
  updated_at?: string;
  source_counts: {
    rag_total: number;
    rag_used: number;
    rag_filtered: number;
    ontology_total: number;
    expert_total: number;
  };
}
```

### 4.3 온톨로지 그래프 처리

질문:

> 히스토리에서 바로 볼 때 온톨로지 그래프는 어떻게 처리해야 하는가?

답:

온톨로지 그래프는 재계산하지 않고, 최초 검색 결과의 `ontology_graph` payload를 snapshot으로 저장해 그대로 복원한다.

권장 구조:

```ts
interface OntologyGraphSnapshot {
  version: 'v2';
  nodes: Array<{
    id: string;
    label: string;
    type?: string;
    rank?: number;
    score?: number;
    status?: 'USED' | 'FILTERED';
  }>;
  edges: Array<{
    id?: string;
    source: string;
    target: string;
    label?: string;
    type?: string;
    status?: 'USED' | 'FILTERED';
  }>;
  layout?: {
    algorithm?: 'dagre' | 'force' | 'preset';
    positions?: Record<string, { x: number; y: number }>;
  };
  captured_at: string;
}
```

정책:

- 히스토리 재열람: snapshot graph를 즉시 렌더링한다.
- 재검색: backend에 다시 요청해 새 graph를 생성한다.
- 문서/온톨로지 데이터가 변경되었을 가능성이 있으면 “이전 검색 결과” 배지를 표시한다.
- 그래프가 너무 큰 경우 top-N node/edge만 저장하고 `truncated=true`를 기록한다.

### 4.4 중복 검색 방지

동일 검색 판정 키:

```text
cache_key = hash(normalized_question + mode + options + project_id + index_version)
```

`index_version`이 필요한 이유:

- 문서 업로드, 벡터 재색인, 온톨로지 재구축 후에는 같은 질문이라도 결과가 달라질 수 있다.

Phase 1.5 최소 구현:

- 프론트 Zustand `previousQueries`에 full snapshot 저장
- 히스토리 클릭 시 `currentQuery`를 해당 snapshot으로 교체
- API 재호출 없음

Phase 2 정식 구현:

- backend DB에 `query_snapshots` 테이블 추가
- project/session/user 기준으로 조회
- localStorage fallback 제공

### 4.5 히스토리 리스트 UI

리스트 표시 항목:

- 질문 첫 줄
- mode
- v5.3 status
- confidence
- 검색 시각
- RAG/Ontology/Expert count
- `이전 결과` 또는 `최신 결과` 배지

액션:

- `보기`: snapshot 즉시 복원
- `재검색`: 동일 질문/모드/options로 API 재호출
- `Word 저장`: snapshot을 현재 화면으로 복원한 뒤 저장
- `삭제`: 히스토리에서 제거

## 5. 전문가 의견 등록 기능 설계

현재 전문가 모드에는 `Expert (0)` 탭과 expert source 표시 구조는 있으나, 전문가 의견 등록 UI가 없다.

Phase 2-1 개발 항목:

### 5.1 전문가 의견 등록 UI

필드:

- 제목
- 도메인/태그
- 관련 온톨로지 개념
- 의견 본문
- 근거 문서/페이지
- 신뢰 등급
- 작성자
- 작성일

### 5.2 Backend API

예상 API:

```http
POST /api/expert-opinions
GET /api/expert-opinions?project_id=...&query=...
PUT /api/expert-opinions/{id}
DELETE /api/expert-opinions/{id}
```

### 5.3 답변 통합

- expert source는 `sources.expert_opinions`에 포함한다.
- 전문가 의견이 직접 매칭되면 `Expert (n)` 탭에 표시한다.
- 전문가 의견만 있고 문서 근거가 없으면 `GENERAL_ONLY` 또는 별도 `EXPERT_ONLY` 상태를 검토한다.

## 8. 설계 판정

현재 v5.3은 단순 QA봇이 아니라 다음 특성을 가진다.

- 검색 결과가 있어도 답변 가능성 gate를 통과해야 답변한다.
- 모드별 답변 허용 범위를 분리한다.
- 차단 결과를 `NO_ANSWER / 0% / FILTERED`로 명확히 표시한다.
- 평가 결과를 Word로 저장할 수 있다.
- 다음 단계에서는 query snapshot 기반 히스토리로 반복 검색 비용을 줄인다.

따라서 Phase 1은 answerability gate 중심, Phase 1.5는 운영 UX/히스토리 중심, Phase 2는 전문가 지식 등록 중심으로 분리한다.
