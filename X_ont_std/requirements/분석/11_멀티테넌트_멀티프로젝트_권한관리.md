# 멀티테넌트 · 멀티프로젝트 · 권한 관리 설계

> **버전**: v2 (2026-05-13)
> **변경 이력**: v1 → v2 — role/permissions 충돌 해소, 기존 데이터 company_id 태깅 방법 명확화, 문서 업로드 프로젝트 귀속 흐름 추가, Phase 1 보안 범위 명시

---

## 1. 목표

현재 단일 사용자 데모 방식으로 동작하는 온톨로지 교육 플랫폼을 멀티테넌트(회사별 데이터 격리), 멀티프로젝트(프로젝트 단위 문서·온톨로지 분리), 권한 기반 UI 제어가 가능한 구조로 발전시킨다.

**핵심 원칙**

- 로그인 화면 없이 시작한다. 사용자 목록 드롭다운에서 선택하면 세션이 바뀐다.
- 로그인 없이도 데이터 격리와 권한 제어는 백엔드에서 실제로 적용한다.
- 나중에 JWT 로그인을 붙일 때 API 구조와 권한 모델을 수정하지 않아도 되도록 설계한다.
- Phase 1은 데모 목적이므로 `?user=` 파라미터 직접 변경을 허용한다. 이 범위를 문서에 명시하고, Phase 2에서 토큰 기반으로 교체한다.

## 2. 핵심 개념

### 2.1 테넌트 (Tenant = Company)

데이터 격리의 최상위 단위. 모든 프로젝트, 문서, 온톨로지, 사용자는 반드시 하나의 테넌트에 속한다.

```
Tenant (Company)
  ├── Users[]
  └── Projects[]
        ├── Documents[]          ← docs_registry에 company_id + project_id 태그
        └── OntologyEntities[]   ← ontology_db에 company_id + project_id 태그
```

테넌트 A 사용자는 테넌트 B의 데이터를 API 레벨에서 조회할 수 없다.

### 2.2 프로젝트 (Project)

테넌트 내에서 문서와 온톨로지를 묶는 업무 단위. 같은 회사에서도 "Snowflake 분석"과 "고객사 A 온보딩"은 분리된다.

### 2.3 역할 (Role)과 권한 플래그 (Permission Flags)

**역할은 UI 표시·그룹핑용이고, 실제 접근 제어는 권한 플래그만으로 수행한다.**

역할이 권한 플래그의 기본값(default)을 결정하지만, 개별 사용자에게 override 가능하다.

```
role → 권한 플래그 기본값 derive
     → 개별 override 명시 시 override 값 우선
```

역할 기본값 매트릭스:

| 플래그 | 설명 | admin | editor | viewer |
| --- | --- | :---: | :---: | :---: |
| `can_edit_diagram` | 다이어그램 노드/엣지 편집 | ✅ | ✅ | ❌ |
| `can_edit_ontology` | 온톨로지 엔티티/관계 편집 | ✅ | ✅ | ❌ |
| `can_upload_doc` | 문서 업로드 | ✅ | ✅ | ❌ |
| `can_delete_doc` | 문서 삭제 | ✅ | ❌ | ❌ |
| `can_manage_users` | 사용자 목록 관리 | ✅ | ❌ | ❌ |
| `can_view_audit_log` | 감사 로그 조회 | ✅ | ❌ | ❌ |

**서버 side 권한 resolve 로직:**

```python
def resolve_permissions(user: dict) -> dict:
    base = ROLE_DEFAULTS[user["role"]]        # role 기본값
    override = user.get("permission_override", {})  # 개별 override
    return {**base, **override}               # override가 base를 덮어씀
```

users.json에 `permissions` 필드를 직접 저장하지 않는다. 런타임에 role + override로 계산한다.

## 3. 데이터 모델

### 3.1 파일 기반 저장소 (Phase 1)

```
backend/app/config/
├── role_defaults.json    ← role → 권한 플래그 기본값
├── companies.json        ← 테넌트 목록
├── users.json            ← 사용자 목록 (role + permission_override만 저장)
└── projects.json         ← 프로젝트 목록
```

### 3.2 role_defaults.json

```json
{
  "admin":  { "can_edit_diagram": true,  "can_edit_ontology": true,
              "can_upload_doc": true,    "can_delete_doc": true,
              "can_manage_users": true,  "can_view_audit_log": true },
  "editor": { "can_edit_diagram": true,  "can_edit_ontology": true,
              "can_upload_doc": true,    "can_delete_doc": false,
              "can_manage_users": false, "can_view_audit_log": false },
  "viewer": { "can_edit_diagram": false, "can_edit_ontology": false,
              "can_upload_doc": false,   "can_delete_doc": false,
              "can_manage_users": false, "can_view_audit_log": false }
}
```

### 3.3 companies.json

```json
[
  { "id": "default", "name": "Default",    "description": "기존 호환용 기본 테넌트" },
  { "id": "acme",    "name": "ACME Corp",  "description": "데모 기업 A" },
  { "id": "globex",  "name": "Globex Corp","description": "데모 기업 B" }
]
```

### 3.4 users.json

`permissions` 필드 없음. `permission_override`만 필요한 경우에만 명시.

```json
[
  { "id": "analyst", "name": "Analyst", "company_id": "default",
    "role": "editor", "project_ids": ["proj-default"] },

  { "id": "alice",   "name": "Alice",   "company_id": "acme",
    "role": "editor", "project_ids": ["proj-001"] },

  { "id": "bob",     "name": "Bob",     "company_id": "acme",
    "role": "viewer", "project_ids": ["proj-001"] },

  { "id": "carol",   "name": "Carol",   "company_id": "globex",
    "role": "admin",  "project_ids": ["proj-002"] },

  { "id": "dave",    "name": "Dave",    "company_id": "globex",
    "role": "viewer",
    "project_ids": ["proj-002"],
    "permission_override": { "can_upload_doc": true } }
]
```

> `dave`는 viewer이지만 문서 업로드만 허용하는 override 예시.

### 3.5 projects.json

```json
[
  { "id": "proj-default", "company_id": "default",
    "name": "기본 프로젝트", "description": "기존 데이터 귀속 프로젝트",
    "created_by": "analyst", "created_at": "2026-01-01" },

  { "id": "proj-001", "company_id": "acme",
    "name": "Snowflake 분석 프로젝트",
    "description": "Snowflake 소개서 기반 온톨로지 분석",
    "created_by": "alice", "created_at": "2026-05-13" },

  { "id": "proj-002", "company_id": "globex",
    "name": "Globex 내부 분석",
    "created_by": "carol", "created_at": "2026-05-13" }
]
```

> 프로젝트에 `doc_ids`를 두지 않는다. 대신 **문서 쪽에 `project_id` 태그**를 붙인다. (역방향 참조 — 문서가 프로젝트를 바라봄)

### 3.6 기존 데이터 company_id 태깅

기존 `docs_registry.json`의 각 문서에 `company_id`와 `project_id` 필드를 추가한다.

```json
{
  "doc_id": "doc-ff68a066",
  "filename": "Snowflake_소개서_HDC.pdf",
  "company_id": "default",
  "project_id": "proj-default"
}
```

필드가 없는 기존 레코드는 서버에서 `"default"` / `"proj-default"` 로 fallback 처리한다. 별도 마이그레이션 스크립트는 불필요하다.

## 4. API 설계

### 4.1 Phase 1 보안 범위 명시

```
Phase 1은 데모 목적이므로 ?user=alice 를 URL에 직접 입력하면 alice 세션이 된다.
즉, 클라이언트 신뢰 모델을 사용한다. 인증은 없고 식별만 있다.
Phase 2에서 JWT Bearer 토큰으로 교체 시 ?user= 파라미터를 제거한다.
```

### 4.2 신규 엔드포인트

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| `GET` | `/api/companies` | 테넌트 목록 |
| `GET` | `/api/users` | 전체 사용자 목록 (UserSwitcher용) |
| `GET` | `/api/users/{id}` | 사용자 상세 + 런타임 권한 (role + override 계산 결과) |
| `GET` | `/api/users/{id}/permissions` | 권한 플래그만 반환 |
| `GET` | `/api/projects?user={id}` | 현재 사용자 소속 프로젝트 목록 |
| `GET` | `/api/projects/{id}` | 프로젝트 상세 |

### 4.3 기존 엔드포인트 변경 사항

`?user=` 파라미터는 유지. 다음 동작이 추가된다.

- 사용자 조회 → company_id 확인 → 해당 company_id 데이터만 반환
- 존재하지 않는 user_id → `404 user_not_found`
- company_id 불일치 데이터 접근 → `403 permission_denied`

### 4.4 문서 업로드 흐름 변경

```
기존: POST /api/documents/upload?user=alice
변경: POST /api/documents/upload?user=alice&project_id=proj-001
```

- `project_id` 파라미터 없으면 사용자의 첫 번째 프로젝트에 자동 귀속
- 사용자가 해당 프로젝트에 속하지 않으면 `403`

### 4.5 권한 위반 응답

```json
HTTP 403
{
  "error": "permission_denied",
  "required": "can_edit_diagram",
  "user": "bob",
  "role": "viewer",
  "resolved_permissions": { "can_edit_diagram": false, "..." : "..." }
}
```

## 5. 프론트엔드 설계

### 5.1 UserContext

```typescript
interface UserContextValue {
  user: User | null;
  permissions: Record<string, boolean>;   // 런타임 resolve된 플래그
  company: Company | null;
  projects: Project[];
  currentProject: Project | null;
  switchUser: (userId: string) => Promise<void>;
  switchProject: (projectId: string) => void;
}
```

- 초기 로드: localStorage → `GET /api/users/{id}` → context 설정
- `switchUser`: API 호출 후 company·projects·permissions 일괄 갱신

### 5.2 UserSwitcher 컴포넌트 (헤더 우측 드롭다운)

```
┌─────────────────────────────────────────────────────┐
│  Ontology Workbench          [proj-001 ▼]  [Alice ▼] │
│                                            ┌─────────┤
│                                            │ ACME Corp│
│                                            │ ──────  │
│                                            │✓ Alice  │  ← 현재 선택
│                                            │  Bob    │
│                                            │ ──────  │
│                                            │ Globex  │
│                                            │  Carol  │
│                                            │  Dave   │
│                                            └─────────┘
└─────────────────────────────────────────────────────┘
```

- 회사별 그룹핑, 현재 사용자 체크 표시
- 역할 뱃지 표시 (admin / editor / viewer)
- 전환 중 로딩 스피너

### 5.3 권한 게이트 (2가지 방식)

**훅 방식** — 조건부 렌더링이나 disabled 처리에 사용:

```typescript
const canEdit = usePermission('can_edit_diagram');
<button disabled={!canEdit}>편집</button>
```

**래퍼 컴포넌트 방식** — 아예 렌더링을 막을 때 사용:

```tsx
<PermissionGate required="can_delete_doc">
  <DeleteButton />      {/* viewer에게는 이 버튼 자체가 DOM에 없음 */}
</PermissionGate>
```

두 방식의 차이: `disabled` vs 아예 미렌더링. 삭제/관리 버튼은 미렌더링, 편집 버튼은 disabled 처리를 기본으로 한다.

### 5.4 ProjectSelector

헤더 중앙에 배치. 현재 프로젝트 전환 시 문서 목록·온톨로지 컨텍스트가 해당 프로젝트 범위로 한정된다.

## 6. 구현 순서 (Phase 1)

```
[백엔드]
  1. role_defaults.json, companies.json, users.json, projects.json 작성
  2. docs_registry.json 기존 레코드에 company_id/project_id 추가 (fallback 포함)
  3. GET /api/users, /api/users/{id}/permissions 구현 (role+override resolve 포함)
  4. GET /api/projects?user={id} 구현
  5. 기존 문서/온톨로지 API에 company_id 필터 미들웨어 추가
  6. 문서 업로드 API에 project_id 파라미터 추가

[프론트엔드]
  7. UserContext + UserProvider 구현
  8. UserSwitcher 컴포넌트 + 헤더 배치
  9. usePermission 훅 + PermissionGate 컴포넌트
  10. OntologyGraphEditor 편집 버튼 권한 게이트
  11. 문서 업로드/삭제 버튼 권한 게이트
  12. ProjectSelector 컴포넌트
```

## 7. 비기능 요구사항

| 항목 | 기준 |
| --- | --- |
| 권한 resolve 오버헤드 | 요청당 1ms 이하 (JSON 메모리 연산) |
| 사용자 전환 응답 | 500ms 이하 (API 1회 + context 재설정) |
| 기존 API 하위 호환 | `?user=analyst` 기존 요청 정상 동작 유지 |
| 데이터 격리 | company_id 불일치는 API 레벨에서 차단 (화면 숨김만으로 처리 금지) |
| Phase 1 보안 한계 | `?user=` 직접 변경 허용 — 데모 환경 전용임을 운영 문서에 명시 |
