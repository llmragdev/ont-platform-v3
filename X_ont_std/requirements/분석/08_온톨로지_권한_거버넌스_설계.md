# 온톨로지 권한과 거버넌스 설계

## 1. 목표

온톨로지 기반 시스템은 단순히 데이터를 잘 연결하는 것만으로는 충분하지 않습니다. 사용자가 어떤 객체를 볼 수 있는지, 어떤 속성을 볼 수 있는지, 어떤 액션을 실행할 수 있는지까지 함께 설계해야 합니다.

이 문서는 객체, 속성, 관계, 액션, 문서, AI 컨텍스트에 대한 권한과 거버넌스 설계를 정리합니다.

## 2. 권한 설계의 기본 단위

온톨로지 권한은 다음 단위로 나누어 설계합니다.

| 단위 | 예시 |
| --- | --- |
| 객체 타입 | Customer, Order, Product |
| 객체 인스턴스 | C001, O001 |
| 속성 | 고객명, 주문 금액, 위험 등급 |
| 관계 | Customer -> Order |
| 액션 | ApproveOrder, RejectOrder |
| 문서 | 계약서, 정책 문서, 매뉴얼 |
| AI 컨텍스트 | RAG 프롬프트에 포함되는 정보 |

핵심은 “화면 접근 권한”만 보는 것이 아니라, 객체와 액션 중심으로 권한을 설계하는 것입니다.

## 3. 역할 모델

예제 역할은 다음과 같이 정의할 수 있습니다.

| 역할 | 설명 |
| --- | --- |
| Viewer | 객체와 문서를 조회 |
| Analyst | 객체 탐색과 AI 질의 가능 |
| AccountManager | 일반 주문 승인 가능 |
| FinanceManager | 고액 주문 승인 가능 |
| Admin | 온톨로지 모델과 권한 관리 |

## 4. 객체 권한

객체 타입별로 읽기, 생성, 수정, 삭제 권한을 정의합니다.

```text
Customer
- Viewer: read
- Analyst: read
- AccountManager: read
- Admin: read, create, update, delete

Order
- Viewer: read
- AccountManager: read, update
- FinanceManager: read, update
- Admin: read, create, update, delete
```

실무에서는 객체 타입 권한만으로 부족할 수 있습니다. 지역, 담당자, 고객 등급에 따라 인스턴스 단위 권한도 필요합니다.

예시:

```text
AccountManager는 자신이 담당하는 Customer의 Order만 조회할 수 있다.
FinanceManager는 금액 5000 이상 Order를 조회하고 승인할 수 있다.
```

## 5. 속성 권한과 마스킹

모든 사용자가 모든 속성을 볼 수 있으면 위험합니다.

예시:

| 속성 | Viewer | Analyst | Manager |
| --- | --- | --- | --- |
| customer_name | 보기 가능 | 보기 가능 | 보기 가능 |
| region | 보기 가능 | 보기 가능 | 보기 가능 |
| risk_tier | 숨김 | 보기 가능 | 보기 가능 |
| contract_terms | 숨김 | 일부 마스킹 | 보기 가능 |

마스킹 예:

```text
contract_terms: "Custom discount rate: 12%"
Viewer 표시값: "Restricted"
Analyst 표시값: "Custom discount rate: ***"
Manager 표시값: "Custom discount rate: 12%"
```

## 6. 관계 권한

관계도 권한 대상입니다.

예를 들어 고객 객체는 볼 수 있지만, 그 고객의 주문 목록은 볼 수 없어야 하는 경우가 있습니다.

```text
Customer C001 조회 가능
Customer C001 -> Order 관계 조회 불가
```

관계 권한은 RAG 컨텍스트 구성에도 영향을 줍니다. 사용자가 볼 수 없는 관계를 통해 가져온 문서는 AI 답변에 포함하면 안 됩니다.

## 7. 액션 권한

워크플로우 액션은 반드시 권한 검사를 거쳐야 합니다.

예시:

| 액션 | 실행 가능 역할 | 조건 |
| --- | --- | --- |
| ApproveOrder | AccountManager | amount < 5000 |
| ApproveOrder | FinanceManager | amount >= 5000 |
| RejectOrder | AccountManager, FinanceManager | Submitted 상태 |
| FulfillOrder | Operations | Approved 상태 |

액션 실행 전 검사 순서:

1. 사용자가 대상 객체를 볼 수 있는가
2. 사용자가 해당 액션을 실행할 수 있는가
3. 현재 상태에서 액션이 가능한가
4. 업무 조건을 만족하는가
5. 실행 이력을 남길 수 있는가

## 8. 문서 권한

RAG 시스템에서는 문서 권한이 특히 중요합니다.

문서 권한 예:

```text
Order Approval Policy: 모든 업무 사용자 조회 가능
Enterprise Contract: AccountManager 이상 조회 가능
Custom Pricing Agreement: FinanceManager 이상 조회 가능
```

검색 결과에는 권한이 없는 문서가 포함되면 안 됩니다. LLM 프롬프트에도 권한이 없는 문서 내용을 넣으면 안 됩니다.

## 9. AI 컨텍스트 권한

AI 답변은 사용자가 볼 수 있는 정보만 사용해야 합니다.

금지 패턴:

```text
사용자에게는 risk_tier가 숨김 처리되어 있는데,
RAG 프롬프트에는 risk_tier: High를 포함한다.
```

올바른 패턴:

```text
권한 필터링
  -> 객체 컨텍스트 생성
  -> 문서 컨텍스트 생성
  -> RAG 프롬프트 생성
```

## 10. 감사 로그

다음 이벤트는 반드시 기록하는 것이 좋습니다.

- 객체 조회
- 민감 속성 조회
- 문서 검색
- AI 질의
- RAG 프롬프트 생성
- 액션 실행
- 권한 거부
- 데이터 마스킹 적용

감사 로그 예:

```json
{
  "event_type": "ACTION_EXECUTED",
  "actor": "manager@example.com",
  "object_type": "Order",
  "object_id": "O001",
  "action": "ApproveOrder",
  "result": "SUCCESS",
  "occurred_at": "2026-05-07T10:30:00"
}
```

## 11. 정책 설계 예시

```python
def can_approve_order(user, order):
    if order["status"] != "Submitted":
        return False

    if order["amount"] < 5000:
        return user["role"] in ["AccountManager", "FinanceManager", "Admin"]

    return user["role"] in ["FinanceManager", "Admin"]
```

이런 정책은 화면, API, 워크플로우 엔진에서 같은 기준으로 사용되어야 합니다.

## 12. 요약

온톨로지 권한 설계는 화면 메뉴 권한보다 더 세밀해야 합니다. 객체, 속성, 관계, 액션, 문서, AI 컨텍스트까지 권한을 일관되게 적용해야 운영 가능한 시스템이 됩니다.

## 13. 실전 권한 관리 및 보안 표준 (Best Practice)

설계된 권한 모델을 실제 클라우드 데이터 플랫폼 및 인프라 환경에서 안전하게 구현하기 위해 다음 보안 표준을 적용합니다.

### 1) 인증 및 접속 표준
- **서비스 계정(Service Account) 사용**: 개인 계정이 아닌 기능별 서비스 전용 계정을 생성하여 권한을 최소화하여 부여합니다.
- **키 기반 인증(Key-based Auth)**: 일반 비밀번호 방식보다 보안성이 높은 키 기반 인증 방식을 권장하며, 인증 키는 정기적으로 갱신(Rotation)합니다.
- **네트워크 보안 정책**: 허용된 네트워크 대역이나 특정 게이트웨이를 통해서만 접속할 수 있도록 접근 제어 정책을 설정합니다.

### 2) 시크릿 관리 (Secret Management)
- **자격 증명 노출 방지**: 소스 코드나 설정 파일 내에 인증 정보를 직접 입력(Hardcoding)하지 않습니다.
- **환경별 관리**: 로컬 개발 시에는 암호화된 로컬 설정 파일을 사용하고, 운영 환경에서는 플랫폼 내장 시크릿 관리 서비스나 전용 Key Vault 도구와 연계합니다.

### 3) 권한 부여 최소화 원칙 (Least Privilege)
- **직무 중심 역할(RBAC) 분리**: 업무 단위로 세분화된 역할을 정의하고 상속 구조를 설계하여 관리 효율성을 높입니다.
- **객체 단위 권한 제어**: 데이터베이스 전체 권한이 아닌, 서비스 운영에 꼭 필요한 특정 객체(Table, View, API 등)에 대해서만 정밀하게 권한을 제어합니다.
