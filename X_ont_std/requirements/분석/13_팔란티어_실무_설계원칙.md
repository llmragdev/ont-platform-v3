## 1. Materialize + Write-back 메커니즘

### 1-1. 온톨로지는 영구 저장소가 아니다

팔란티어 온톨로지는 **논리 모델(Logical Layer)** 이다.  
그 자체로는 쿼리할 때마다 원천 데이터를 재연산하므로, 대용량 쿼리에 비용과 성능 문제가 생긴다.

```
온톨로지 (논리 레이어 — 의미 모델)
        ↓ Materialize
물리 데이터셋 (영구 저장 — 쿼리 성능 확보)
        → 다른 파이프라인 입력으로 재활용 가능
        → 대용량 분석 가능
```

**설계 시 결정 사항**: 어떤 객체를 Materialize할지는 비용과 직결된다. 자주 조회되는 객체부터 우선 적용한다.

### 1-2. 액션과 Write-back

온톨로지 Action으로 데이터를 수정하면 **원천 데이터셋(Oracle, SAP 등)에 직접 반영되지 않는다**.

```
사용자 → Action 실행 (예: WC일자 변경)
        ↓
별도 스토리지에 변경 이력 저장
        ↓
원천 데이터 + 변경 이력 합산 → 화면에 최신 상태 표시

원천 DB 반영이 필요한 경우 → Write-back 기능 별도 설정 필요
```

**실무 함의**: 팔란티어 화면에서 수정한 내용이 ERP에 반영되길 원하면 Write-back 설계가 반드시 있어야 한다. 이를 모르면 "수정했는데 ERP에는 안 보인다"는 혼선이 발생한다.

## 2. 온톨로지 설계 실패 패턴과 역방향 설계

### 2-1. 흔한 실패 패턴

```
[잘못된 접근]
1. 기존 DB 테이블 구조를 그대로 온톨로지로 옮김
2. 객체 간 관계(Link) 모델링 없이 속성(Property)만 나열
3. Action 없이 데이터 조회·시각화만 구현

결과:
- 비싼 Snowflake처럼 쓰게 됨
- 팔란티어의 차별점(워크플로우·자동화)이 전혀 발현되지 않음
- 도입 비용 대비 ROI 없음
```

### 2-2. 역방향 설계 방법론

올바른 방향은 **Action(행위)부터 역방향으로 설계**하는 것이다.

```
[역방향 설계 순서]

1단계: 업무 행동 식별
  → 조직이 매일 실행하는 핵심 행동은 무엇인가?
  → 예: "WC일자 변경", "자재 발주 승인", "공정 지연 알림"

2단계: 행동의 대상 객체 식별
  → 그 행동을 수행할 때 다루는 핵심 명사는?
  → 예: Ship, Block, Material, Worker

3단계: 필요한 속성과 관계 도출
  → 그 행동을 실행하려면 어떤 정보가 필요한가?
  → 예: WC일자 변경 → Ship의 일정 속성 + 연관 Block 상태

4단계: 데이터 소스 연결
  → 필요한 속성이 어느 원천 시스템에 있는가?
  → 예: Oracle ERP, 설계 PDF, IoT 센서
```

**핵심 원칙**: 먼저 데이터가 어디 있는지 보지 말고, **어떤 의사결정과 행동을 자동화하고 싶은지**를 먼저 정의한다.

### 2-3. MVP 설계 권장

```
처음부터 전체 도메인을 온톨로지화하려 하지 않는다.

MVP 접근:
- 핵심 객체 3~5개만 시작
- 가장 반복 빈도가 높은 Action 1~2개 구현
- 성과 확인 후 점진적 확장

설계 실패의 가장 큰 원인: 초반에 너무 많은 객체를 한번에 모델링
```

## 3. LLM–온톨로지 Tool 통합 패턴 (AIP 방식)

### 3-1. 일반 LLM 챗봇과의 차이

```
[일반 LLM 챗봇]
사용자 질문 → LLM 응답
한계: LLM이 사내 실시간 데이터를 모름 / 할루시네이션 / 액션 불가

[AIP 방식 — LLM + Ontology Tool]
사용자 질문
  → LLM이 질문 의도 분류
  → Tool 호출: 온톨로지에서 실시간 데이터 조회
  → 실제 데이터 기반 응답 생성
  → 필요 시 Action 실행 (워크플로우 트리거)
```

### 3-2. 온톨로지가 LLM의 컨텍스트가 되는 구조

```
질문: "지연 위험이 높은 선박 3척과 주요 원인은?"

일반 LLM: "모름" (학습 데이터에 사내 데이터 없음)

AIP + Ontology:
  1. LLM → Tool 호출: Ship 객체에서 지연 지표 조회
  2. Block, Material, Worker 관계 데이터 자동 결합
  3. 지연 원인 분석 후 응답 생성
  4. "자재 긴급 발주 요청하시겠습니까?" → 사용자 승인 → Action 실행
```

### 3-3. 구현 아키텍처 (ont_platform v3 방식)

```
사용자 질문
  ↓
Intent Classifier (LLM) — filter / descriptive / hybrid 분류
  ↓
QueryPlanV3 생성
  ├── ONTOLOGY step: find_by_name / filter_by_property
  └── VECTOR step: 문서 PDF 검색
  ↓
HybridSynthesizer — 온톨로지 결과 + 벡터 결과 + LLM 합성
  ↓
최종 응답 (근거 포함)
```

**핵심**: LLM이 단독으로 답하는 게 아니라, **온톨로지를 검색 도구(Tool)로 사용**하여 실시간 사실 기반 응답을 생성하는 구조.

### 3-4. 보안 고려사항

| 구분 | 설명 |
|---|---|
| 온프레미스/VPC 모델 | 데이터가 외부 LLM 서버로 전송되지 않음 — 보안 최우선 |
| 외부 LLM API 연동 | 조회 데이터가 API 요청에 포함되어 전송됨 → 보안 정책 필수 |
| 권장 방향 | 민감 데이터는 온톨로지 권한으로 LLM 접근 범위 제한 + 내부 모델 우선 검토 |

## 4. 비용 구조와 관리 부채

### 4-1. 실제 비용 구조

팔란티어 도입 비용은 **라이선스 비용과 컴퓨팅 비용이 분리**된다.

| 비용 항목 | 내용 | 주의 |
|---|---|---|
| 라이선스 | 플랫폼 기본 사용료 | 계약 조건에 따라 다름 |
| 데이터 커넥션 에이전트 | 원천 DB 동기화 실행 시 | 동기화 빈도에 따라 증가 |
| Materialize 비용 | 온톨로지 객체를 물리화할 때 | 객체 수에 비례 |
| 파이프라인 실행 | Sync / AI 처리 / Agent 운영 | 사용량 비례 과금 |
| 온톨로지 유지 | 객체 재계산, 관계 갱신 | 규모 커질수록 증가 |

**실무 교훈**: Materialize 대상을 최소화하고, 동기화 주기를 업무 필요 최소한으로 설계한다.

### 4-2. 관리 부채 — 설계하지 않으면 반드시 발생

팔란티어는 Pipeline, Code Repository, Workshop이 모두 **파일 형태**로 공존한다.

```
문제 현상:
- 어떤 Workshop이 어떤 Dataset을 쓰는지 추적 어려움
- Dataset 삭제 시 → 연결된 Workshop 에러 발생, 추적 난이
- 네이밍 혼재 → "이 파이프라인이 어디서 사용되는가" 파악 불가

해결 방향:
- 도메인별 폴더 구조 표준화: /구매/, /생산/, /설계/ ...
- 네이밍 컨벤션 강제: [부서]_[주제]_[버전]
- 의존 관계 문서화 → Workflow 탭 활용
- 분기별 미사용 객체 정리 주기 운영
```

**핵심**: 거버넌스 체계를 처음부터 설계하지 않으면 6개월 후 아무도 손대기 어려운 상태가 된다.

## 5. 조선·제조 도메인 시나리오

### 5-1. 온톨로지 모델 예시 (현대중공업 맥락)

```
Ship (선박 객체)
  ├─ 선박번호 (Property)
  ├─ WC일자 — 예정/실제 (Property)
  ├─ 공정 상태 (Property)
  └─ 블록 구성 (Property)
      ↕ Link
  ↔ Block (블록 객체) — 공정 단위
  ↔ Worker (담당자 객체)
  ↔ Material (자재 객체)
  ↔ Sensor (IoT 센서 객체)

Action:
  - WC일자 변경
  - 공정 지연 알림 발송
  - 자재 긴급 발주 요청
  - ERP 자동 업데이트 (Write-back)
```

### 5-2. 시나리오 A — 공정 지연 대응

```
1. 온톨로지에서 특정 Block의 WC일자 지연 감지
   (조건: 예정 대비 3일 이상 초과)

2. 담당 공무팀장에게 자동 알림 발송

3. 팔란티어 화면에서 조치 유형 선택
   - 일정 조정
   - 자재 긴급 요청
   - 협력사 통보

4. 승인 클릭
   → SAP/ERP 자동 업데이트 (Write-back)
   → 관련 부서 동시 통보
   → 전체 이력 온톨로지에 기록

5. 기록된 이력 → 이후 유사 상황 분석 기반 데이터로 활용
```

### 5-3. 시나리오 B — 자재 발주 의사결정

```
1. 자재 재고 데이터 + 공정 계획 + 시장 철강 가격 결합

2. AI가 발주 최적 시점 시뮬레이션
   (온톨로지 Tool 조회 + LLM 분석)

3. 구매 담당자에게 추천 제시
   - "지금 발주 권장" / "2주 후 권장"
   - 근거 데이터 함께 표시

4. 담당자 승인 → 발주 시스템 자동 연동

핵심: 분석 → 의사결정 → 실행이 하나의 화면에서 완결
```

### 5-4. 기존 방식과 비교

| 구분 | 기존 방식 | 팔란티어 온톨로지 |
|---|---|---|
| 데이터 구조 | 선박정보 테이블 JOIN 공정테이블 JOIN 자재테이블 | Ship ↔ Block ↔ Material 객체 관계 |
| 접근 방법 | SQL 작성 필요 | 비즈니스 언어로 직접 접근 |
| 해석 일관성 | 부서마다 다른 해석 가능 | 모든 앱이 동일 모델 공유 |
| 변경 영향 | 연관 쿼리 전체 수정 | 한 곳 수정 → 전체 자동 반영 |
| 실행 연결 | 분석 후 이메일/전화 → 수작업 | 분석 → 승인 클릭 → ERP 자동 반영 |

## 6. 플랫폼 선택 기준과 도입 단계 로드맵

### 6-1. 언제 팔란티어를 선택해야 하는가

| 상황 | 적합한 플랫폼 |
|---|---|
| 데이터 분석·BI가 주목적, 운영 연동 불필요 | Snowflake + Tableau/Power BI |
| 대용량 데이터 처리, 데이터 과학 중심 | Databricks |
| 업무 프로세스 자동화 + 데이터 통합이 동시에 필요 | **팔란티어** |
| 실시간 운영 데이터 기반 AI 의사결정 자동화 | **팔란티어** |
| 폐쇄적 데이터 환경 + 강력한 거버넌스 필요 | **팔란티어** |
| 외부 데이터 마켓플레이스, 파트너사 데이터 공유 | Snowflake |

**팔란티어를 선택하면 안 되는 경우:**
- 단순 데이터 시각화만 필요한 경우 → 과대투자
- 온톨로지 설계를 담당할 도메인 전문가가 내부에 없는 경우
- 빠른 PoC가 목적인 경우 (온톨로지 설계 초기 비용이 큼)
- 데이터 파이프라인만 필요한 경우 (Airflow + dbt로 충분)

### 6-2. 도입 단계 로드맵

```
1단계: 데이터 연결·통합 (대부분의 국내 기업 현재 위치)
  - 원천 시스템(ERP, MES, DB) 연결
  - 파이프라인 구성, 데이터 정제
  - 기본 시각화 화면 (Contour, Workshop)

2단계: 온톨로지 모델링 (팔란티어 고유 가치 시작)
  - 핵심 업무 객체·관계 정의
  - 현업 사용자가 업무 언어로 데이터 접근
  - 권한 거버넌스 자동 전파 적용

3단계: 워크플로우 + AIP (실제 ROI 발생 구간)
  - 업무 자동화: 감지 → 알림 → 승인 → ERP 반영
  - LLM + 온톨로지 Tool 통합 (AIP 방식)
  - 의사결정 속도·정확도 향상 → 투자 회수
```

**팔란티어의 ROI는 3단계에서 발생한다.** 1단계만 쓰면 "비싼 Tableau"가 된다.

### 6-3. 현대중공업 현재 위치

```
현황: 1단계 완료, 2단계 진행 중
  - 구매 기획부 등 현업이 Workshop 화면 직접 제작
  - 온톨로지 기본 구성 완료
  - 워크플로우 권한 미제공 (현대미포는 사용 중)
  - AWS 클라우드 기반 운영

다음 단계 과제:
  - 워크플로우 권한 확보 → 업무 자동화 구현
  - AIP 연동 → LLM 기반 온톨로지 조회 구현
  - 핵심 도메인 Action 설계 (공정 지연 대응 등)

전체 역량 대비 현재 수준: 약 1/3
진짜 투자 회수 구간인 3단계까지 나아가는 것이 목표
```

## 7. 요약

| 항목 | 핵심 메시지 |
|---|---|
| Materialize | 온톨로지는 논리 모델 — 성능·비용을 위해 물리화 필요 |
| Write-back | Action 수정은 ERP에 자동 반영 안 됨 — 별도 설계 필요 |
| 설계 방향 | DB 구조 복사 금지 — Action부터 역방향 설계 |
| LLM 통합 | LLM이 온톨로지를 Tool로 조회 → 실시간 데이터 기반 응답 + Action 연결 |
| 비용 | 라이선스 + 컴퓨팅 분리 — Materialize 대상 최소화 |
| 관리 부채 | 네이밍·폴더 거버넌스를 처음부터 설계하지 않으면 6개월 후 레거시 |
| ROI 구간 | 1단계(데이터 연결)가 아닌 3단계(워크플로우+AIP)에서 발생 |
