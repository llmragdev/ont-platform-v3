# 06 온톨로지 AI 업무화면 기획 추적도

## 1. 원문 문서

- `req_doc_hub/분석/06_온톨로지_AI_업무화면_기획.md`

## 2. 핵심 요구/설계

기획서 §4 메뉴 7종 + §13 우측 컨텍스트 패널 + §6 3컬럼 레이아웃 + §11 액션-상태 전이를 모두 추적합니다.

- 대시보드 (MVP)
- 객체 탐색 (MVP)
- AI 질의 (MVP)
- 문서 검색 (MVP 일부 / 후속)
- 승인 워크플로우 (MVP)
- 온톨로지 관리 (후속)
- 설정 (후속)
- 우측 컨텍스트 패널 (MVP, §13 핵심 요구)
- 업무형 3컬럼 레이아웃 (§6)
- 실행 이력/감사 로그
- 권한 거부 시나리오 (§3 시나리오4, 08과 연결)

## 3. 구현 추적

### 3.1 화면 구조(3컬럼 레이아웃)

`src_codex`:
- `src_codex/index.html` (`<aside class="nav-pane">`, `<main class="workbench">`, `<aside class="context-pane">`)
- `src_codex/app.js`
- `src_codex/style.css`

`src_anti`:
- `src_anti/index.html` (`<aside class="sidebar">`, `<main class="content">`, `<aside class="context">`)
- `src_anti/app.js`의 `views`, `setupMenu()`, `updateView()`
- `src_anti/style.css`

판단:
- `src_codex`: 3컬럼 레이아웃 구현됨, 메뉴 5개(ask/workflow/objects/audit/architecture)로 기획 7개 중 일부만 매핑
- `src_anti`: 3컬럼 레이아웃 구현됨, 메뉴 5개(dashboard/explorer/ai-query/workflow/audit)

### 3.2 대시보드

`src_codex`:
- 별도 대시보드 메뉴/뷰 **미구현** (메뉴에 `dashboard` 항목 없음)
- 단, `view-architecture`가 시스템 상태 시각화를 일부 대신함

`src_anti`:
- 메뉴: `data-menu="dashboard"`
- KPI 카드: `count-pending`, 그 외 카드 4종(`index.html` 대시보드 영역)
- 데이터: 목 데이터 기반(`refreshData()`에서 큐/주문 재조회)
- 이벤트 타임라인: 별도 위젯 없음(감사 로그 메뉴로 대체)

판단:
- `src_codex`: 대시보드 **미구현**(기획 §7 미충족)
- `src_anti`: KPI 카드 구현, 이벤트 타임라인은 미흡

### 3.3 객체 탐색

`src_codex`:
- API: `server.py`의 `GET /api/objects/customers`, `GET /api/objects/orders`, `GET /api/objects/orders/:id`, `GET /api/objects/orders/:id/context`, `GET /api/ontology/object-types`
- 데이터 조회: `OntologyService.customers()`, `OntologyService.orders()`, `AppContext.order_context()`
- 화면: `view-objects` 뷰의 `order-table`, `ontology-context`

`src_anti`:
- 화면: `data-menu="explorer"`의 `all-orders-table`
- 함수: `renderAllOrders()`, `selectOrder()`
- API: `GET /api/objects/customers`, `GET /api/objects/orders`, `GET /api/objects/orders/{id}` (`backend/main.py`)

판단:
- `src_codex`: 주문/고객/관계 매핑 풍부, 다만 객체 타입 탭(Customer/Order/**Product**) UI 분리는 부분 구현
- `src_anti`: 주문 중심 구현, Customer/Product 별도 탭 미흡

### 3.4 AI 질의

`src_codex`:
- 백엔드 파이프라인:
  - `AppContext.ask()` (오케스트레이션, `_step` 헬퍼로 단계화)
  - `extract_object_ids()` 객체 식별
  - `OntologyService.get_order_context()` 객체 조회 + 관계 검증
  - `RAGService.build_search_query()` 검색 쿼리 빌드
  - `SearchService.search()` 문서 검색
  - `RAGService.build_prompt()` RAG 컨텍스트
  - `LLMGateway.generate_rule_based_answer()` 답변 생성
- 화면: `view-ask`의 `question-input`, `answer-text`, `evidence-list`, `pipeline-list`(단계 시각화)

`src_anti`:
- `handleAsk()` (app.js)
- 백엔드 RAG: `RAGService.generate_answer()` 단일 메서드(검색 쿼리/프롬프트 빌드 단계가 분리되어 있지 않음)

판단:
- 백엔드 질의 흐름: `src_codex`는 §9 표준 파이프라인을 단계 단위로 매핑(추상화 강함). `src_anti`는 단일 메서드로 단순화.
- 화면 질의 경험: `src_anti`는 입력→답변 흐름이 직관적, `src_codex`는 단계 시각화(`pipeline-list`)가 추가 강점.

### 3.5 문서 근거

`src_codex`:
- `AppContext._present_search_results()` 근거 정제
- `SearchService.search()` (정책 검사 포함)
- 화면: `evidence-list`

`src_anti`:
- `handleAsk()` 내 `evidenceList.innerHTML` 렌더링
- `SearchService.search()` (`backend/search.py`)
- 별도 `POST /api/search` 엔드포인트는 **미구현**

판단:
- `src_codex`: 검색 + 정책 + 근거 정제까지 매핑됨
- `src_anti`: 답변과 함께 근거를 동시 렌더링하나 검색 전용 화면/엔드포인트는 없음

### 3.6 문서 검색 메뉴(§10)

- `src_codex`: 별도 메뉴/뷰 **미구현**(검색은 AI 질의 내부에만 사용)
- `src_anti`: 별도 메뉴/뷰 **미구현**

판단: 기획 §10의 독립 메뉴는 두 구현 모두 후속 과제로 남아 있음. MVP 범위(§18)와 일치.

### 3.7 승인 워크플로우와 실행 이력

`src_codex`:
- `WorkflowService.queue()` 큐 조회
- `WorkflowService.execute()` 액션 실행(상태 전이 + 정책 + 감사)
- `WorkflowEngine.get_available_actions()` 가용 액션 산출
- `AuditService.list_events()` 실행 이력
- API: `POST /api/workflow/execute`, `GET /api/workflow/queue`, `GET /api/audit/events`
- 화면: `view-workflow`, `view-audit`

`src_anti`:
- 화면: `executeAction()` (app.js), `refreshAuditLogs()`, `data-menu="workflow"`/`audit`
- 백엔드: `WorkflowService.get_available_actions()`, `WorkflowService.validate_and_execute()`
- `AuditService.log_event()` 기록
- API: `POST /api/workflow/execute`, `GET /api/audit/events`

판단:
- `src_codex`: 백엔드 정책/전이/감사 분리 구현이 강함
- `src_anti`: 화면에서 액션 실행 → 즉시 이력 갱신까지의 UX가 매끄러움
- 두 구현 모두 §11 액션-상태 전이표(ApproveOrder/RejectOrder/HoldOrder/RequestMoreInfo/FulfillOrder/CloseOrder)는 부분 매핑이며 `OnHold`, `PendingInfo` 상태 명시는 코드 측에서 보강 필요

### 3.8 우측 컨텍스트 패널(§13, 핵심 요구)

`src_codex`:
- `<aside class="context-pane">` 컨테이너
- `ctx-order-id`, 컨텍스트 카드 영역
- 갱신: `app.js`의 컨텍스트 렌더 로직

`src_anti`:
- `<aside class="context">` 컨테이너
- `ctx-order-id`, `ctx-order-status`, `ctx-order-amount`, `ctx-cust-name`, `ctx-cust-risk`, `ctx-products`
- 갱신: `updateContext()` (선택 객체 변경 시 호출)

판단:
- 두 구현 모두 우측 패널 구현됨
- `src_anti`가 표시 항목(객체/고객/제품/위험)이 더 풍부
- "최근 이벤트", "검색 근거 문서"의 우측 패널 표시는 두 구현 모두 부분 구현

### 3.9 온톨로지 관리(§12)

- `src_codex`: 별도 메뉴 없음. `view-objects`의 `ontology-context`/`object-table`이 객체 타입 메타를 일부 노출
- `src_anti`: **미구현**

판단: 두 구현 모두 후속 과제. 기획 §12의 "초기 읽기 전용 → 이후 편집"과 일치.

### 3.10 설정(§5)

- `src_codex`, `src_anti` 모두 **미구현**

판단: 후속 과제.

## 4. 요약

기획서 §4 메뉴 7종 기준으로 보면:

- `src_anti`는 대시보드/객체 탐색/AI 질의/워크플로우/감사 로그 + 우측 컨텍스트 패널을 갖춰 **사용자 경험 측면 MVP**(§18)에 가깝습니다.
- `src_codex`는 대시보드와 객체 탐색의 일부가 미구현이지만, AI 질의 파이프라인 단계화·정책/감사 분리·`POST /api/search` 같은 **백엔드 추상화 측면**이 더 체계적입니다.
- 두 구현 공통으로 문서 검색 메뉴, 온톨로지 관리, 설정은 후속 과제로 남아 있으며, §11 액션-상태 전이표의 `OnHold`/`PendingInfo` 상태와 `FulfillOrder`/`CloseOrder` 액션은 코드 측에서 보강이 필요합니다.
- §13 우측 컨텍스트 패널은 두 구현 모두 골격을 갖췄으나 "최근 이벤트", "검색 근거 문서"의 패널 내 표시는 보강 여지가 있습니다.
