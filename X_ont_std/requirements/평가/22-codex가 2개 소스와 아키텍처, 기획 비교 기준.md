# codex가 2개 소스와 아키텍처, 기획 비교 기준

## 1. 문서 목적

이 문서는 이후 작성할 `23-codex가 2개 소스 비교.md`의 평가 기준을 미리 합의하기 위한 문서입니다.

비교 대상은 다음 네 가지입니다.

- `src_codex`
- `src_anti`
- `06_온톨로지_AI_업무화면_기획.md`
- `10_운영형_아키텍처_확장.md`

`23` 문서에서는 이 기준을 사용해 두 소스가 기획과 아키텍처 요구를 얼마나 충족하는지 비교합니다.

## 2. 비교의 기본 관점

비교는 “어느 코드가 더 좋아 보이는가”가 아니라, 다음 질문에 답하는 방식으로 진행합니다.

1. 기획 문서가 요구한 업무 화면 흐름을 얼마나 구현했는가?
2. 운영형 아키텍처 문서가 요구한 서비스 경계를 얼마나 구현했는가?
3. 온톨로지, RAG, 워크플로우, 권한, 감사 로그가 실제 코드 구조로 드러나는가?
4. 교육용 샘플로서 이해하기 쉬운가?
5. 운영형 구현으로 확장하기 쉬운가?

즉, 단순 기능 수가 아니라 **업무 흐름, 구조적 명확성, 운영 확장성**을 함께 봅니다.

## 3. 비교 대상 문서의 역할

주요 기준:

- 업무 담당자가 이해하기 쉬운 화면 흐름

`23` 문서에서는 두 소스가 이 기획 흐름을 얼마나 구현했는지 비교합니다.

### 3.2 `10_운영형_아키텍처_확장.md`

이 문서는 운영형 시스템 구조 기준입니다.

주요 기준:

- Data Repository

- 운영 확장성

`23` 문서에서는 두 소스가 이 아키텍처 경계를 얼마나 코드로 분리했는지 비교합니다.

## 4. 평가 등급

각 항목은 다음 등급으로 판단합니다.

### 4.1 충족

요구사항이 실제 코드와 화면 흐름에 명확히 구현되어 있습니다.

예:
- 별도 서비스 파일 또는 클래스가 있음
- API 응답에 필요한 정보가 포함됨
- 권한, 관계, 상태 전이 등이 실제 로직으로 검증됨
- 화면에서 사용자가 결과를 확인할 수 있음

### 4.2 부분 충족

요구사항의 방향은 반영되었지만 구현이 단순하거나 일부만 존재합니다.

예:
- 서비스 파일은 있으나 내부 로직이 얇음
- BM25라고 되어 있지만 실제로는 단순 토큰 매칭임
- RBAC 골격은 있으나 사용자 컨텍스트가 하드코딩됨
- 감사 로그는 있으나 모든 단계가 구조적으로 기록되지는 않음

### 4.3 미충족

요구사항이 코드나 화면에 거의 드러나지 않습니다.

예:
- 관련 API가 없음
- 데이터 모델이 없음
- 화면 메뉴가 없음
- 오류나 권한 처리가 없음

### 4.4 과장 표현 주의

문서나 주석에는 구현되었다고 되어 있지만, 실제 소스 기준으로는 구현 수준이 낮은 경우입니다.

예:
- “BM25”라고 표현했지만 IDF와 문서 길이 보정이 없음
- “RAG”라고 표현했지만 프롬프트 생성이나 LLM 호출이 없음
- “RBAC”라고 표현했지만 모든 요청이 동일 사용자로 처리됨

이 경우 `23` 문서에서는 “부분 충족”으로 분류하고, 과장된 표현을 별도로 적습니다.

## 8. 예상 비교 방향

현재까지의 검토를 바탕으로 보면, `23` 문서의 비교 방향은 대략 다음과 같을 가능성이 높습니다.

- `src_anti`: 화면 MVP와 FastAPI 데모 흐름을 보여주는 데 적합
- `src_codex`: 운영형 서비스 경계, 권한, 감사, RAG 흐름을 설명하는 데 적합
- `src_anti`: 프론트엔드 경험이 더 직관적일 수 있음
- `src_codex`: 백엔드 아키텍처와 운영 요구 반영이 더 강함
- 최종적으로는 `src_anti`의 화면성과 `src_codex`의 운영형 백엔드 구조를 결합하는 방향이 바람직함

단, 위 내용은 아직 최종 비교 결론이 아닙니다. `23` 문서에서 실제 소스 기준으로 다시 확인해 확정합니다.

## 9. 합의가 필요한 부분

`23` 문서를 작성하기 전에 다음 기준을 확정하면 좋습니다.

1. 비교의 중심을 화면 기획에 둘지, 운영형 아키텍처에 둘지
2. `src_anti`를 “MVP 구현”으로 볼지, “운영형 개선판”으로 볼지
3. `src_codex`를 “운영형 참조 구현”으로 볼지, “교육용 백엔드 샘플”로 볼지
4. 점수화를 할지, 등급형 서술로 할지
5. 최종 결론에서 승자를 정할지, 용도별 적합성을 나눌지

추천 기준:
- 승자 결정이 아니라 **용도별 적합성 비교**로 정리한다.
- 점수보다 **충족 / 부분 충족 / 미충족** 등급을 사용한다.
- 기획 충족도와 운영 아키텍처 충족도를 분리해서 판단한다.
