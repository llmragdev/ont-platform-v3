# Scenario 1 Trigger Design

작성일: 2026-06-12

## 1. 문서 역할

이 문서는 요구사항 정의서가 아니라 Scenario 1의 트리거 방식 상세 설계 문서다.

요구사항 기준 문서:

- `10_REQUIREMENTS_OVERALL.md`
- `11_REQUIREMENTS_ONT_PLATFORM.md`
- `12_REQUIREMENTS_CUSTOMER_MCP.md`

문서 간 충돌이 있을 경우 요구사항 정의서를 우선하고, 이 문서는 그 요구사항을 만족시키는 설계 설명으로 본다.

## 2. 목적

Scenario 1은 고객사 게시판에 문의가 올라왔을 때 `ont_platform v5`가 댓글 생성/등록 workflow를 시작하는 방식을 검증한다.

트리거 방식은 2개로 나눈다.

- Scenario 1-1: 5분 배치 polling
- Scenario 1-2: 고객사 webhook/API trigger

권장 운영 순서:

```text
Primary: Scenario 1-2 고객사 webhook/API trigger
Fallback: Scenario 1-1 5분 배치 polling
```

## 3. 공통 처리 흐름

두 시나리오는 시작 방식만 다르고 이후 처리 흐름은 동일하다.

```text
question event detected
  -> ont_platform event/workflow starts
  -> reply draft generated by LLM path
  -> ont_platform calls customer_mcp /mcp/tools/comment.create
  -> customer_mcp calls customer_board
  -> result and audit saved in ont_platform
```

공통 idempotency key:

- `event_id`: 이벤트 중복 방지
- `question_id`: 문의 단위 처리 중복 방지
- `request_id`: end-to-end 추적

## 4. Scenario 1-1: 5분 배치 Polling

`ont_platform`가 일정 주기로 customer_mcp를 통해 미처리 문의 목록을 조회한다.

```text
ont_platform scheduler
  -> customer_mcp question.list
  -> unprocessed question found
  -> generate-and-post
```

장점:

- 고객사 시스템이 event/webhook을 지원하지 않아도 된다.
- 누락 이벤트를 복구할 수 있다.
- 시연 환경에서 단순하다.

단점:

- 실시간성이 떨어진다.
- 주기마다 조회 부하가 생긴다.
- 이미 처리한 문의 중복 방지가 필요하다.

권장 역할:

- fallback
- missed-event reconciliation

P1 후보 API:

```http
GET /mcp/tools/question.list?status=open
GET /mcp/tools/question.get?question_id=q-001
```

## 5. Scenario 1-2: 고객사 Webhook/API Trigger

고객사 게시판에 질문이 등록되면 고객사 측 연동 서버가 `ont_platform` trigger API를 호출한다.

```text
customer_board question created
  -> customer_mcp or customer integration server calls ont_platform trigger API
  -> ont_platform generate-and-post
```

장점:

- 거의 실시간으로 처리된다.
- polling 부하가 없다.
- 이벤트 단위 audit이 명확하다.
- 고객사 시스템이 질문 생성 시점을 가장 정확히 안다.

단점:

- 고객사 쪽에서 trigger 호출 구현이 필요하다.
- ont_platform 장애 시 재전송/retry 정책이 필요하다.

권장 역할:

- primary

## 6. Trigger API 초안

이 API는 `11_REQUIREMENTS_ONT_PLATFORM.md`의 고객 문의 이벤트 수신 요구사항을 구현하기 위한 설계 초안이다.

```http
POST /api/extn/customer-questions/events
```

Request:

```json
{
  "event_id": "evt-001",
  "event_type": "question.created",
  "question_id": "q-001",
  "thread_id": "thread-001",
  "post_id": "q-001",
  "title": "비밀번호 초기화 요청",
  "content": "비밀번호 초기화 부탁드립니다.",
  "author": "customer-user",
  "created_at": "2026-06-12T10:00:00Z",
  "mode": "dry_run"
}
```

Response:

```json
{
  "event_id": "evt-001",
  "request_id": "uuid",
  "status": "accepted",
  "workflow_status": "started",
  "duplicate": false
}
```

## 7. Idempotency

필수 규칙:

- 같은 `event_id`가 다시 오면 새 댓글을 달지 않는다.
- 같은 `question_id`에 이미 성공 댓글이 있으면 기본적으로 재처리하지 않는다.
- 강제 재처리는 별도 `force=true` 또는 새 event type으로만 허용한다.

상태 저장 후보:

```text
storage/{company_id}/{project_id}/events/customer_question_events.jsonl
storage/{company_id}/{project_id}/events/customer_question_state.json
```

## 8. 구현 순서

1. Scenario 1-2 trigger API
2. event idempotency store
3. trigger API에서 `generate-and-post` 호출
4. Scenario 1-1 batch polling
5. missed-event reconciliation report
