# ont_platform v2.0 — 전체 요구사항 정의서

> **기준일**: 2026-05-13  
> **v1.0 기준**: Sprint 06 완료 (archive/v1.0)  
> **v2.0 목표**: 물리 격리 + 범용 온톨로지 + 서비스 레이어 분리

---

## 1. 배경 및 목적

### 1.1 v1.0 완성 기능

v1.0(Sprint 01~06)은 다음을 구현했다:

| 기능 영역 | 내용 |
|-----------|------|
| 인증 & 세션 | JWT 기반 로그인, 사용자 컨텍스트 |
| 멀티테넌트 | company / project / user 계층, role + permission_override |
| 온톨로지 관리 | 내장 8개 타입 + 도메인 타입 확장, 엔티티/관계 CRUD |
| 문서 & 벡터 검색 | PDF 업로드 → Chroma 벡터화, 단일 인스턴스 |
| 복합 질의 | /api/ask (온톨로지+RAG), /api/hybrid/ask (질문 분류), /api/rag/ask |
| 권한 & 마스킹 | 역할별 플래그, 민감 필드 마스킹, 지역 기반 접근 |
| 워크플로우 | 주문 상태 전환 5액션 7전환, 워크플로우 그래프 SSE 실행 |
| 감시 & 로깅 | AuditService, 이벤트 코드 체계 |

v1.0은 교육 목적 프로토타입으로 설계되어, 54~58개 엔드포인트가 `app_context.py` 단일 객체에 집중되어 있다.

### 1.2 v1.0의 구조적 한계

| 코드 | 한계 | 영향 |
|------|------|------|
| L-01 | 단일 Chroma 인스턴스 — `backend/vector_db/` 하나 | 테넌트 간 물리 격리 불가, 대용량 시 병목 |
| L-02 | `app_context.py`에 워크플로우 도메인 로직과 범용 온톨로지 혼재 | 다른 도메인 적용 불가 |
| L-03 | 스토리지 경로 하드코딩 — 모든 모듈에 분산 | 경로 변경 시 전파 범위 파악 불가 |
| L-04 | 물리 스토리지 미격리 — 모든 테넌트가 동일 디렉토리 공유 | GDPR/계약 위반 가능성 |

### 1.3 v2.0 목표

1. **물리 격리 완성**: company/project 단위 독립 스토리지, V-ID 샤딩
2. **범용 온톨로지**: 도메인 고정 로직(`app_context.py`)을 서비스 레이어로 분리해 어떤 도메인에도 적용 가능
3. **테스트 가능한 구조**: 서비스 단독 테스트, `app_context.py` 의존 없음
4. **v1.0 기능 완전 보존**: 기존 `/api/workflow/*`, `/api/objects/*` 엔드포인트 회귀 없음

## 3. 기능 요구사항

### 3.1 물리 스토리지 격리 (FR-STOR)

| ID | 요구사항 |
|----|----------|
| FR-STOR-01 | 모든 파일 경로는 `storage_config.py`의 함수만으로 결정한다 |
| FR-STOR-02 | PDF 업로드 파일은 `storage/{company_id}/{project_id}/uploads/`에 저장한다 |
| FR-STOR-03 | 벡터 DB는 `storage/{company_id}/{project_id}/vector_db/V{shard_id}/`에 Chroma 인스턴스로 생성한다 |
| FR-STOR-04 | 온톨로지 JSON은 `storage/{company_id}/{project_id}/ontology/`에 저장한다 |
| FR-STOR-05 | company A의 Chroma 인스턴스로 company B 문서가 검색되어선 안 된다 (물리 격리) |
| FR-STOR-06 | 특정 V-ID 지정 검색과 전체 샤드 순회 검색을 모두 지원한다 |

### 3.2 서비스 레이어 (FR-SVC)

| ID | 요구사항 |
|----|----------|
| FR-SVC-01 | `TenantContext(user_id, company_id, project_id, role, permissions)` 단일 실행 컨텍스트를 정의한다 |
| FR-SVC-02 | `OntologyService` — 엔티티/관계 CRUD, TenantContext 기반 scope 주입 |
| FR-SVC-03 | `DocumentService` — 업로드/벡터화/삭제, storage_config 경유 |
| FR-SVC-04 | `VectorSearchService` — V-ID 샤드 기반 검색, score 재정렬 |
| FR-SVC-05 | 세 서비스 모두 `app_context.py` 의존 없이 단독 테스트 가능해야 한다 |
| FR-SVC-06 | FastAPI의 `Depends`로 세 서비스를 라우터에 주입한다 |

### 3.3 백엔드 API (FR-API)

#### v2.0 신규 엔드포인트

| Method | Path | 설명 |
|--------|------|------|
| POST | `/api/documents/upload` | DocumentService 경유, 물리 경로에 저장 |
| GET | `/api/documents` | company/project 필터, 물리 격리 보장 |
| DELETE | `/api/documents/{doc_id}` | 벡터 + 파일 삭제 |
| POST | `/api/documents/extract-ontology` | PDF → 온톨로지 추출 (OntologyService 저장) |
| GET | `/api/ontology/{doc_id}/entities` | OntologyService 경유, TenantContext 필터 |
| POST | `/api/ontology/{doc_id}/entities` | 엔티티 추가 |
| PUT | `/api/ontology/{doc_id}/entities/{entity_id}` | 엔티티 수정 |
| DELETE | `/api/ontology/{doc_id}/entities/{entity_id}` | 엔티티 삭제 |
| GET | `/api/ontology/{doc_id}/relationships` | 관계 조회 |
| POST | `/api/ontology/{doc_id}/relationships` | 관계 추가 |
| DELETE | `/api/ontology/{doc_id}/relationships/{rel_id}` | 관계 삭제 |
| GET | `/api/ontology/{doc_id}/graph` | React Flow 형식 그래프 |

| POST | `/api/ask` | 온톨로지 + RAG 복합 질의 |

| POST | `/api/rag/ask` | RAG 전용 질의 |

## 5. 도메인 모델

### 5.1 핵심 엔티티

```
TenantContext
  ├── user_id: str
  ├── company_id: str
  ├── project_id: str
  ├── role: str          # Viewer|Analyst|AccountManager|FinanceManager|Admin
  └── permissions: dict  # role_defaults + permission_override 결합

Document
  ├── doc_id: str        # doc-{uuid8}
  ├── filename: str
  ├── company_id: str
  ├── project_id: str
  ├── shard_id: str      # V-ID (default or numeric)
  ├── chunk_count: int
  └── created_at: datetime

OntologyEntity
  ├── id: str            # E{uuid6.upper()}
  ├── doc_id: str
  ├── type: str          # 내장 8개 + 도메인 타입
  ├── name: str
  └── properties: dict

OntologyRelationship
  ├── id: str            # R{uuid6.upper()}
  ├── doc_id: str
  ├── from_id: str
  ├── relation: str
  └── to_id: str
```

### 5.2 내장 엔티티 타입 (v1.0에서 보존)

| 타입 | 설명 |
|------|------|
| PERSON | 인물, 직책, 역할 |
| ORGANIZATION | 회사, 기관 |
| PRODUCT | 제품, 서비스 |
| METRIC | 수치, 지표 (value, unit, period) |
| CONCEPT | 개념, 방법론 |
| CATEGORY | 분류, 그룹 |
| EVENT | 사건, 일정 (date) |
| LOCATION | 지역, 리전 |

## 6. 용어 정의

| 용어 | 정의 |
|------|------|
| V-ID / shard_id | Chroma 인스턴스 식별자. `V{shard_id}` 형태의 디렉토리명 |
| TenantContext | 요청 1건당 1개 생성되는 실행 컨텍스트. 서비스가 scope 판단에 사용 |
| 물리 격리 | 파일시스템 레벨에서 테넌트 간 데이터 디렉토리가 분리된 상태 |
| 범용 온톨로지 | 특정 도메인(주문/고객)에 의존하지 않는 엔티티/관계 CRUD 시스템 |
| 소프트 격리 | company_id 필드로 필터링하지만 물리 파일은 공유하는 v1.0 방식 |

## 7. 범위 외 (v2.0)

다음은 v2.0에 포함하지 않는다:

- LLM 제공자 교체 또는 멀티 LLM 라우팅
- 실시간 협업 편집 (WebSocket)
- 외부 스토리지(S3, GCS) 연동
- 사용자 직접 가입/초대 (JSON 기반 사용자 관리 유지)
- 온톨로지 버전 관리 (스냅샷/롤백)
- 워크플로우 도메인 로직 교체 (Sprint 09 이후)
