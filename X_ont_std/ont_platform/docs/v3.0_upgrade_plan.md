## 1. 배경 및 목적

### 1.1 v2.0 현황

v2.0은 12개 메뉴를 갖춘 완성형 MVP 프론트엔드와 FastAPI 백엔드를 갖추고 있으나, **핵심 지능 엔진이 미완성**이다.

| 컴포넌트 | v2.0 실제 상태 |
|---------|--------------|
| `HybridSynthesizer` | LLM 없이 템플릿 문자열만 반환 (`"Found N document result(s)."`) |
| `QueryPlanner.classify_intent()` | 키워드 매칭 휴리스틱 (정확도 측정 없음) |
| `OntologyEntity` | 출처(provenance) 필드 없음 |
| 저장소 | JSON 파일 직접 읽기/쓰기 (동시성 미처리) |
| 인증 | HTTP 헤더 직접 신뢰 (스푸핑 가능) |
| Workflow 실행 | 시뮬레이션 SSE, 실행 이력 미저장 |

### 1.2 v3.0 목표

```
v2.0: 구조를 갖춘 교육/시연용 MVP
v3.0: LLM이 실제로 동작하는 production-oriented MVP
```

세 가지 핵심 목표:
1. **실제 AI 답변**: Gemini API 연동으로 의미 있는 답변 생성
2. **신뢰 가능한 온톨로지**: 출처와 근거가 있는 엔티티/관계
3. **추적 가능한 워크플로우**: 실행 이력이 남는 workflow run 모델

## 2. 버전 전략

### 2.1 v3.0으로 올리는 이유 (v2.1이 아닌 이유)

| 변경 항목 | v2.1 범위 | v3.0 범위 |
|----------|----------|----------|
| 합성기 | 템플릿 개선 | LLM API 교체 (엔진 교체) |
| 쿼리 플래너 | 키워드 추가 | LLM 기반 intent 분류 (방식 교체) |
| 엔티티 모델 | 필드 추가 | Provenance 서브모델 신설 |
| 저장소 | JSON 유지 | Repository 인터페이스 추상화 |

→ 세 개의 핵심 서비스가 구조적으로 교체되므로 v3.0

### 2.2 브랜치 전략

```
ont_platform/
  master      ← v2.0 운영 (현재)
  v3.0-dev    ← v3.0 개발 브랜치
  v3.0-phase1 ← Phase 1 완료 후 병합 준비
```

- v2.0은 master에서 계속 운영 가능
- v3.0-dev에서 독립 개발 후 단계별 master 병합
- 별도 폴더 분리 없음 (git 브랜치로 충분)

## 3. Phase별 계획

### Phase 1 — LLM 엔진 교체 (가장 즉각적 효과)

**목표**: "Found 0 document result(s)" → 실제 AI 답변

**기간 목표**: 1~2일

| 작업 | 대상 파일 | 변경 내용 |
|------|----------|----------|
| Gemini LLM 클라이언트 | `services/llm_client.py` (신규) | Gemini API 래퍼, 재시도 로직 |
| HybridSynthesizer 교체 | `services/hybrid_synthesizer.py` | LLM 호출로 실제 답변 합성 |
| LLM 기반 intent 분류 | `services/query_planner.py` | Gemini로 query 분류, 키워드 fallback 유지 |
| Prompt 템플릿 | `prompts/` (신규 폴더) | 합성·분류용 프롬프트 파일 분리 |
| dependencies 업데이트 | `dependencies.py` | LLM 클라이언트 DI 추가 |

**DoD**:
- [ ] "snowflake 장점은?" 질의 시 LLM 생성 답변 반환
- [ ] GEMINI_API_KEY 없을 때 graceful fallback (템플릿 답변)
- [ ] 로그에 `[LLM]` prefix로 API 호출 여부 확인 가능

---

### Phase 2 — 데이터 모델 강화

**목표**: 온톨로지 엔티티에 출처·신뢰도·버전 추가

**기간 목표**: 2~3일

| 작업 | 대상 파일 | 변경 내용 |
|------|----------|----------|
| Entity Provenance 모델 | `models/ontology.py` (신규) | `source_doc_id`, `source_page`, `confidence`, `status`, `version` |
| OntologyService 갱신 | `services/ontology.py` | 신규 필드 CRUD 지원 |
| Repository 패턴 | `repositories/` (신규 폴더) | `BaseRepository` 인터페이스 + `JsonRepository` 구현 |
| 구조화 QueryPlan | `models/query_intent.py` | `ontology_filters[]`, `needs_vector`, `doc_ids` 필드 추가 |
| QueryPlan Validator | `services/query_plan_validator.py` (신규) | 스키마 기반 plan 검증 |
| API 응답 갱신 | `api/hybrid.py` | `ontology_evidence[]` 필드 추가 |

**DoD**:
- [ ] 엔티티 생성 시 `source_doc_id`, `confidence` 저장 가능
- [ ] `GET /api/ontology/{doc_id}/entities` 응답에 provenance 포함
- [ ] Repository 교체 시 비즈니스 로직 수정 불필요 (인터페이스 분리 검증)

---

### Phase 3 — 워크플로우 · 운영 신뢰성

**목표**: 실행 이력 저장, 인증 강화, 품질 평가 기반

**기간 목표**: 3~5일

| 작업 | 대상 파일 | 변경 내용 |
|------|----------|----------|
| Workflow Run 모델 | `models/workflow_run.py` (신규) | Run/Step 상태 저장 (PENDING→RUNNING→DONE/FAILED) |
| Workflow Run API | `api/workflow.py` 확장 | `GET /api/workflow-graphs/{id}/runs` 이력 조회 |
| 인증 미들웨어 | `middleware/auth.py` (신규) | 헤더 기반 → 서명 검증 (HMAC 또는 JWT) |
| 평가 데이터셋 | `tests/eval/` (신규) | 질의 유형별 20개씩 정답셋 + 자동 평가 스크립트 |
| 품질 메트릭 API | `api/metrics.py` (신규) | fallback rate, no-answer rate 집계 |

**DoD**:
- [ ] Workflow 실행 후 `/runs` 에서 이력 조회 가능
- [ ] `x-user-id: admin` 헤더 스푸핑 시 401 반환
- [ ] eval 스크립트 실행 시 분류 정확도 수치 출력
