# v4 PostgreSQL 성능 기준선

본 문서는 `ont_platform v4.0` 아키텍처의 핵심인 PostgreSQL(Neon) 도입에 따른 성능 기준선(Baseline)을 분석하고, 시스템이 충족해야 하는 성능 SLA(Service Level Agreement)를 수립합니다.

---

## v3 vs v4 성능 비교

### 1. 엔티티 조회 (GET /api/entities/{id})
v3의 JSON 파일 저장 구조는 엔티티 수가 증가함에 따라 메모리 적재 및 파일 탐색 비용이 선형적으로 증가합니다. 반면 v4는 PostgreSQL 인덱스와 Redis 캐싱을 결합하여 대규모 엔티티 상황에서도 O(1)에 가까운 안정적인 성능을 보장합니다.

* **v3 (JSON 파일 기반)**:
  * 50K 엔티티: ~150ms
  * 100K 엔티티: ~300ms
  * 500K 엔티티: ~1,500ms
* **v4 (PostgreSQL + Index + Redis Cache)**:
  * 50K 엔티티: < 50ms (Cache Hit) / < 100ms (DB)
  * 100K 엔티티: < 50ms (Cache Hit) / < 150ms (DB)
  * 500K 엔티티: < 50ms (Cache Hit) / < 300ms (DB)
* **예상 개선**: 데이터 규모에 따라 **3 ~ 5배 성능 개선** 및 부하 시 지연 시간 증가 억제.

### 2. 감시 로그 쿼리 (GET /api/audit/logs)
v3는 감시 로그가 파일 기반으로 분산되어 대용량 조회 시 심각한 파일 I/O 병목이 발생했습니다. v4에서는 PostgreSQL에 단일 테이블로 구조화하고 다중 복합 인덱스를 적용하여 응답성을 개선합니다.

* **기준선 측정 (PostgreSQL)**:
  * 10K 로그: < 50ms
  * 100K 로그: < 150ms
  * 1M 로그: < 500ms (인덱스 적극 활용)
* **주요 인덱스 전략**:
  * `PRIMARY KEY`: `audit_id`
  * `COMPOSITE INDEX`: `(entity_id, performed_at DESC)`
  * `PARTIAL INDEX`: `(status = 'success')`

### 3. 혈통 조회 (GET /api/entities/{id}/lineage)
엔티티 간의 관계 데이터(Lineage) 체인을 추적하기 위해 복잡한 재귀 연산이 수반됩니다. v4에서는 캐싱 레이어를 적극 활용하여 조회 오버헤드를 제어합니다.

* **기준선 측정 (DB + Cache)**:
  * 3단계 혈통 체인: < 300ms
  * 10단계 혈통 체인: < 800ms
  * 100+ 파생 엔티티 체인: < 1,000ms
* **캐싱 전략**:
  * 혈통 해석 결과: Redis 1시간 TTL 설정 (빈번한 쓰기가 없는 특성 반영)
  * 메타데이터 필드: Redis 30분 TTL 설정

## v4 성능 SLA

### Tier 1: Critical (필수 지표)
시스템의 핵심 사용자 경험 및 기본적인 작동 신뢰성을 보장하기 위해 반드시 달성해야 하는 지표입니다.

1. **메타데이터 단건 조회**: < 100ms (평균 응답 속도)
2. **감시 로그 쿼리**: < 200ms (100K 로그 조건 하)
3. **혈통 체인 해석**: < 500ms (10단계 깊이 체인 조건 하)

### Tier 2: Important (중요 지표)
원활한 관리 작업 및 기능 편의성을 위해 요구되는 성능 기준입니다.

4. **버전 롤백 처리**: < 500ms
5. **감시 로그 내보내기**: < 3.0초 (100K 로그 기준 CSV 다운로드 완료)
6. **순환 참조 감지 및 차단**: < 1,000ms (100개 파생 관계 그래프 기준)

### Tier 3: Goal (이상적 목표)
장기적인 서비스 안정성과 리소스 효율성을 보장하기 위해 권장되는 엔지니어링 목표입니다.

7. **캐시 히트율(Cache Hit Rate)**: 메타데이터 단건 조회 기준 **≥ 70%** 유지
8. **DB 인덱스 효율(Index Scan Ratio)**: 핵심 트랜잭션 쿼리 계획 기준 **≥ 95%** 유지

## PostgreSQL vs v3 JSON 비교 요약

| 메트릭 | v3 JSON 기반 | v4 PostgreSQL (Neon) | 예상 개선도 |
| :--- | :--- | :--- | :--- |
| **엔티티 단건 조회** | 150ms ~ 1,500ms | 50ms ~ 300ms | **3 ~ 5배 단축** |
| **감시 로그 쿼리** | N/A (동적 파일 조회 불가) | < 200ms (100K 로그) | **신규 지원 (측정 불가)** |
| **혈통(Lineage) 조회** | N/A (수동 파일 크롤링 필요) | < 500ms (10단계) | **신규 지원 (측정 불가)** |
| **동시성 쓰기 실패율** | ~45% 실패 (Windows File Lock 경합) | **< 1% 미만 실패** | **약 45배 신뢰성 개선** |
| **스토리지 디스크 크기** | JSON 텍스트 그대로 선형 증가 | PostgreSQL JSONB 압축 적용 | **스토리지 공간 약 30% 절감** |
