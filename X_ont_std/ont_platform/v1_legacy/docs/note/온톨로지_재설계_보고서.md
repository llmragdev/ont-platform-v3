## 1. 한 줄 결론

**claud_통합의 온톨로지는 "이름만 온톨로지일 뿐 사실상 정적 객체-관계 모델"이다.** 진짜 온톨로지의 정의(*스키마와 데이터의 분리, 동적 확장, 관계 우선*)를 만족하지 못한다. Antigravity의 지적은 대체로 정확하다. 다만 해결 방향은 코드 작성자(claud) 입장에서 **3단계 점진 마이그레이션**이 가장 안전하다.

## 2. 안티그래피티 평가서 요약 + 사실관계 점검

평가서가 지적한 5가지 영역과 그 정확성:

| 영역 | 지적 | 사실관계 | 정당성 |
| --- | --- | --- | --- |
| **모델 정의** | Python 코드에 하드코딩, YAML/JSON으로 동적 정의 불가 | [`ontology.py:84-95`](../../backend/app/ontology.py)에 ObjectType/관계가 코드 안 | ✅ 정확 |
| **관계 탐색** | `get_order_context` 같은 고정 함수만, generic graph traversal 없음 | `get_order_context`는 Order 중심 한정. Customer/Product 중심 함수 없음 | ✅ 정확 |
| **지능형 추론** | 속성값 단순 조회, 규칙 기반 추론 부재 | 맞음. 모든 정책 로직은 PolicyEngine에 코드로 | ✅ 정확 (다만 우선순위 낮음) |

| **RAG 결합도** | 문서와 객체를 단순 텍스트로 합침, semantic link 부재 | `evidence`는 score+text. 객체 ID로 cross-link 안 됨 | ⚠ 부분 정확. 다만 evidence에 `related_objects` 필드는 있음 |

**과장된 부분**: "Inference Engine 도입 + 시공간 온톨로지"는 솔루션 1차 출시 범위를 넘는 학술적 제안. 채택해도 좋지만 다른 항목보다 우선순위 낮음.

### 3.3 두 구현의 공통점

1. **schema.json 외부 분리** — 코드 수정 없이 새 객체 타입/관계 타입 추가
2. **양방향 탐색** — incoming/outgoing 둘 다 다루는 generic 함수
3. **속성 메타데이터** — `sensitive`, `searchable`, `id_prefix` 등이 데이터 자체에 부착
4. **액션을 스키마에 포함** (Codex만) — 워크플로우와 온톨로지가 한 모델 안

## 4. claud_통합 온톨로지의 구체적 잘못 (코드 라인 단위)

### 4.1 ❌ 객체/관계 타입이 Python 코드 안

[backend/app/ontology.py:78-95](../../backend/app/ontology.py):
```python
def _build_registry(self) -> None:
    customer_type = ObjectType("Customer")
    customer_type.add_property("name", str, required=True)
    customer_type.add_property("risk_tier", str, required=True)
    # ... 9개 속성을 모두 Python으로 add_property
    self.registry.register_relationship_type(
        RelationshipDefinition("PLACED_ORDER", customer_type, order_type)
    )
```
**문제**: 새 객체 타입(예: `Warehouse`, `Contract`) 추가하려면 코드 수정 + 재배포. 관리자는 손도 못 댐.
**대안 (외부 구현 패턴)**: `config/ontology.json` 로드.

### 4.2 ❌ `get_order_context`만 있음, 다른 객체 타입 중심 함수 없음

[backend/app/ontology.py:155-172](../../backend/app/ontology.py):
```python
def get_order_context(self, order_id: str, customer_id: str | None = None) -> dict:
    order = self.get_object(order_id)
    if order.object_type.name != "Order":
        raise AppError("OBJECT_NOT_FOUND", ...)
    # ... Customer-PLACED_ORDER-Order, Order-ORDER_CONTAINS_PRODUCT-Product 만 따라감
```
**문제**: "이 고객의 주문들"은 되지만 "이 제품을 주문한 고객들"은 새 함수가 필요. "고객 ↔ 어떤 관계가 있는 모든 객체"라는 generic traversal 없음.
**대안**: Antigravity의 `find_related(object_id, rel_type_id?)` — 방향과 타입 모두 옵션.

### 4.3 ❌ 액션이 온톨로지 외부 (WorkflowEngine)

- 우리: `workflow.py`의 `ApproveOrder` 액션이 OntologyService와 별개 클래스 (WorkflowEngine)
- 우리 WG-3에서 `approve_order` 노드를 만들었지만 — **이 노드 종류 자체가 코드에 박혀 있음** ([workflow_graph_engine.py:6-15](../../backend/app/workflow_graph_engine.py)의 `NODE_TYPE_POLICY`)
- Codex는 `action_types`가 ontology 스키마의 한 필드. `exposed_as_graph_node: true`만 켜면 자동 노출

### 4.4 ❌ 관계 생성/삭제 API 없음

`/api/workflow-graphs` (그래프) 와 `/api/objects/orders/{id}/context` (조회)는 있지만:
- ❌ `POST /api/ontology/relationships` (관계 추가)
- ❌ `DELETE /api/ontology/relationships/{id}`
- ❌ `GET /api/ontology/graph` (전체 그래프)

→ 새 관계 인스턴스 추가하려면 `data.py` 코드 수정.

### 4.6 ❌ 속성 마스킹이 Customer 한정 if-else

[backend/app/policy.py:28-38](../../backend/app/policy.py):
```python
def mask_object(self, user: dict, obj: dict) -> dict:
    if obj["type"] == "Customer":

            masked["risk_tier"] = "Restricted"
```

### 4.7 ❌ 온톨로지 그래프 시각화 화면 없음

- 우리: "워크플로우 그래프" 메뉴는 있지만 — **노드가 워크플로우 단계** (Start/End/LLM 등)
- 우리에 없음: **객체 자체를 노드로** (Customer C001 / Order O001 / Product P001) 그리고 관계를 엣지로 시각화하는 화면
- Antigravity는 `/api/ontology/graph` + `GraphWorkspace.tsx`로 정확히 이를 구현

### 4.8 ❌ "객체 탐색" 화면이 표 + 우측 패널만

- 현재 [Explorer.tsx](../../frontend/src/components/Explorer.tsx): 고객/주문 표 2개 + 클릭 시 우측 컨텍스트 패널
- 부족: 관계가 텍스트로만 표시. 시각적 그래프 없음.
- 부족: 객체 클릭 → 연결된 객체 "확장" 같은 인터랙티브 탐색 없음

### Phase 2 — Generic Graph Traversal
**목표**: `get_order_context` 같은 객체 타입별 함수 제거, 범용 함수로 대체.

**작업 (사람 기준 4시간 / 제 기준 ~30분)**:
1. [backend/app/ontology.py](../../backend/app/ontology.py)에 추가:
   ```python
   def object_context(self, object_id: str) -> dict:
       """범용 객체 컨텍스트 — 어떤 객체 타입이든 동일하게 작동."""
       obj = self.get_object(object_id)
       incoming = self.find_relationships(target_id=object_id)
       outgoing = self.find_relationships(source_id=object_id)
       documents = [d for d in self.documents if obj.type in d.related_objects]
       actions = [a for a in self.action_types if a.target_type == obj.type]
       return {"object": obj, "incoming": incoming, "outgoing": outgoing, "documents": documents, "available_actions": actions}
   ```
2. `get_order_context`는 하위호환을 위해 남기되 내부적으로 `object_context` 호출
3. [backend/app/rag.py](../../backend/app/rag.py) `extract_object_ids` 수정:
   - 정규식 하드코딩 제거 → 스키마의 모든 `id_prefix`로 동적 생성
4. [backend/app/app_context.py](../../backend/app/app_context.py) `ask()`에서 Order 중심 분기 제거, 어떤 객체 ID든 처리

**완료 조건**: `evaluate.py`의 케이스 10개 모두 통과 + Customer 중심 질문도 답변 가능 (예: "C003 고객의 모든 주문은?").

### Phase 3 — 관계 CRUD API + 액션 스키마 통합
**목표**: 관리자가 관계를 추가/삭제, 액션이 스키마에서 자동 노출.

**작업 (사람 기준 1일 / 제 기준 ~1.5시간)**:
1. 새 라우트:
   - `POST /api/ontology/relationships` (관계 추가)
   - `DELETE /api/ontology/relationships/{rel_id}`
   - `GET /api/ontology/schema` (스키마 전체)
   - `GET /api/ontology/graph` (전체 노드+엣지)
2. [backend/app/workflow_graph_engine.py](../../backend/app/workflow_graph_engine.py)의 `NODE_TYPE_POLICY` 하드코딩 제거:
   - 스키마의 `action_types` 중 `exposed_as_graph_node: true`인 것을 자동으로 노드 팔레트에 추가
3. 권한: 관계 추가는 Admin/AccountManager+, 삭제는 Admin
4. 감사 로그: `ONTOLOGY_RELATIONSHIP_CREATED`, `*_DELETED`

**완료 조건**: 프론트에서 새 관계 인스턴스 생성 가능. 새 액션 타입 JSON 추가만으로 그래프 노드 등장.

### Phase 4 — 온톨로지 그래프 캔버스 (UI)
**목표**: 객체-관계 자체를 시각화. 워크플로우 그래프와 별개 메뉴.

**작업 (사람 기준 1일 / 제 기준 ~1.5시간)**:
1. 좌측 메뉴에 "온톨로지 그래프" 신규 메뉴 추가 (워크플로우 그래프와 별개)
2. 신규 컴포넌트 `OntologyExplorerCanvas.tsx`:
   - `/api/ontology/graph` 호출 → React Flow로 표시
   - 노드 클릭 → 우측에 객체 상세 + 관계 목록 (incoming/outgoing 양쪽)
   - 노드 더블클릭 → 1-hop 확장 (연결된 객체 그래프에 자동 추가)
   - 빈 캔버스에서 "관계 추가" 버튼 → 두 객체 선택 + 관계 타입 선택 → POST
3. Antigravity 스타일 참고하되 우리 디자인 시스템(Tailwind)으로 통일

**완료 조건**: 시연에서 "객체 그래프 보기" 1분 시연이 가능.

### Phase 5 — sensitive 자동 마스킹
**목표**: `mask_object` if-else 제거, 스키마 메타데이터로 자동.

**작업 (사람 기준 4시간 / 제 기준 ~30분)**:
1. [backend/app/policy.py](../../backend/app/policy.py) `mask_object` 재작성:
   - 객체 타입의 property 중 `sensitive: true` 항목을 role × type 매트릭스(외부 JSON)에 따라 마스킹
2. 신규 파일 `backend/app/config/policy.default.json` — role × type × sensitive_field → mask_strategy 매핑
3. 기존 5종 시나리오(특히 시나리오 5 마스킹)가 그대로 통과해야 함

**완료 조건**: 새 객체 타입에 `sensitive: true` 속성 추가만으로 자동 마스킹.

### Phase 6 (선택) — 추론 규칙 엔진
Antigravity 평가서가 강력 권장했으나 1차 솔루션 범위는 아님. 후속 항목으로 백로그에만 등록.

## 7. 권장 진행 순서 + 위험

```
Phase 0 (baseline)
   ↓
Phase 1 (스키마 외부화)         ← 회귀 위험 큼: 59/59 pytest 다 영향
   ↓
Phase 2 (Generic traversal)    ← 중간 위험: ask() 변경
   ↓
Phase 3 (관계 CRUD + 액션)     ← 중간 위험: 새 API + workflow_graph_engine 수정
   ↓
Phase 4 (그래프 캔버스)         ← 낮은 위험: 새 UI 추가만
   ↓
Phase 5 (sensitive 마스킹)     ← 낮은 위험: policy 한 함수 교체
   ↓
Phase 6 (추론 엔진, 선택)
```

**총 예상 소요**: 사람 기준 4~5일 / 제 기준 ~5시간 (Phase 1~5).

**가장 큰 위험**: Phase 1에서 `_build_registry()` 교체 시 기존 테스트가 깨질 가능성. 완화책 — JSON의 초기 내용을 현재 Python 코드와 정확히 동일하게 만들면 회귀 없이 시작.
