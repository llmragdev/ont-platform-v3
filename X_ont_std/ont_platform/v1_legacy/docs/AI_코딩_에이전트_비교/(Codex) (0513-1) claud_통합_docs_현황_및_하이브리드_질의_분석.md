## 4. "하이브리드"라는 단어의 두 의미

문서에서 가장 조심해야 할 부분은 "하이브리드"가 두 의미로 쓰인다는 점이다.

### 4.1 이미 완료된 하이브리드

이미 완료된 것은 다음이다.

> BM25 + Vector 하이브리드 RAG

이는 문서 검색 품질을 높이기 위해 키워드 기반 검색과 벡터 검색을 섞는 구조다. `PROGRESS.md`의 완료 요약에 들어가는 항목이다.

### 4.2 새로 설계 중인 하이브리드

새로 설계 중인 것은 다음이다.

> Vector RAG + Ontology 하이브리드 질의

이 구조는 질문 유형에 따라 답변 경로를 나눈다.

| 질문 유형 | 적합한 처리 |
| --- | --- |
| 설명형 질문 | 벡터 RAG |
| 필터/분류 | 온톨로지 질의 |
| 엔티티 비교 | 온톨로지 질의 |
| 수치 계산/집계 | 온톨로지 질의 |
| 복합 질문 | 온톨로지 + 벡터 RAG 병합 |

따라서 앞으로 문서에서는 두 용어를 구분하는 것이 좋다.

- `BM25+Vector 하이브리드 RAG`: 이미 구현된 검색 방식
- `Ontology+Vector 하이브리드 질의`: 새로 구현할 고도화 기능

## 5. 하이브리드 질의 설계 평가

`hybrid_query_design.md`의 방향은 타당하다.

좋은 점은 다음과 같다.

- 설명형 검색과 구조형 질의를 분리했다.
- 온톨로지 저장소를 Chroma와 분리해 책임을 나눴다.
- 범용 엔티티 유형과 도메인 config를 분리했다.
- 사용자가 추출 결과를 UI에서 교정할 수 있는 HITL 구조를 고려했다.
- 통합 질의 화면에서 서술형 답변과 구조형 결과를 함께 보여주려는 방향이 좋다.

다만 현재 설계는 PoC에는 적합하지만, 운영형 정확도를 원한다면 보완이 필요하다.

핵심은 다음이다.

> LLM이 답을 직접 만들게 하지 말고, LLM은 계획을 만들고, 코드는 결정적으로 실행해야 한다.

즉 질문을 단순히 `descriptive/filter/compare/calculate/hybrid`로 분류하는 것만으로는 부족하다. 실제 실행 가능한 Query Plan이 필요하다.

예:

```json
{
  "intent": "filter",
  "ontology_filters": [
    {
      "entity_type": "PRODUCT",
      "property": "billing_model",
      "op": "contains",
      "value": "Serverless"
    }
  ],
  "vector_queries": ["Serverless 과금 방식 설명"],
  "needs_vector": true
}
```

이 구조라면 LLM은 "무엇을 찾아야 하는지"만 정하고, 실제 필터/비교/계산은 `ontology_query_engine.py`가 수행한다.

## 6. 구현 우선순위

다음 단계는 `hybrid_query_design.md`의 전체 범위를 한 번에 구현하기보다, 검증 가능한 얇은 경로부터 만드는 것이 좋다.

권장 순서는 다음과 같다.

| 순서 | 작업 | 이유 |
| --- | --- | --- |
| 1 | `ontology_query_engine.py` 구현 | 필터/비교/계산/관계 탐색의 결정적 기반 |
| 2 | `/api/hybrid/ask` 추가 | 프론트에서 통합 질의 흐름을 바로 검증 |
| 3 | 벡터 검색 `doc_ids` 필터 추가 | 선택 문서와 답변 근거가 섞이는 문제 방지 |
| 4 | 온톨로지 추출 결과에 `source_*`, `confidence` 추가 | 구조형 결과의 신뢰성과 추적 가능성 확보 |
| 5 | 질문 분류기를 Query Planner로 확장 | 단순 라벨보다 실행 가능성이 높음 |
| 6 | 청크별 추출 + 병합으로 전환 | 긴 문서에서 엔티티 누락 방지 |

가장 먼저 구현해야 할 것은 추출기가 아니라 질의 엔진이다. 이유는 간단하다. 수동 JSON 샘플만 있어도 질의 엔진은 검증할 수 있지만, 추출기만 먼저 만들면 결과가 맞는지 판단할 실행 기반이 약하다.

## 7. 기존 온톨로지 보완 이후에도 남은 과제

0512 보완으로 온톨로지는 "하드코딩된 업무 데모"에서 "설정 기반 온톨로지 관리 MVP"로 올라왔다.

하지만 아직 완전한 범용 온톨로지 플랫폼은 아니다.

남은 과제는 다음이다.

| 영역 | 현재 상태 | 남은 과제 |
| --- | --- | --- |
| 객체 타입 | 스키마 외부화 완료 | 새 타입의 인스턴스 저장/로딩 일반화 |
| 객체 컨텍스트 | 내부 서비스 일부 범용화 | 공개 REST API 추가 |
| 관계 관리 | 관계 CRUD 가능 | system-derived/user-created/tombstone 구분 |
| 워크플로우 액션 | 백엔드 일부 동적화 | 프론트 팔레트와 실행 핸들러 동적화 |
| 문서 정합성 | 최신 문서와 구버전 흔적 공존 | 수치와 완료 상태 일괄 정리 |

따라서 다음 진짜 목표는 "스키마 외부화"가 아니다. 그것은 이미 상당 부분 완료됐다.

다음 목표는 다음 문장으로 정리된다.

> 데이터, 관계, 액션, 질의까지 완전히 범용화하는 것.

## 8. 문서 정합성 이슈

`PROGRESS.md`와 `NEXT_STEPS.md`는 최신 상태에 가깝다. 반면 일부 보고서에는 이전 검증 수치가 남아 있다.

특히 다음 항목은 정리 대상이다.

- `FINAL_REPORT.md`의 `59/59 PASS`
- `FINAL_REPORT.md`의 `36 passed` 언급
- `README.md`에 남아 있을 수 있는 `17 passed`, `36 passed` 흔적
- `DEMO_SCENARIO.md`의 구버전 테스트 수치
- `CLICK_TEST_CHECKLIST.md`의 회귀 검증 수치

이는 기능 품질 문제는 아니지만, 비교 평가와 전달용 문서에서는 혼동을 만든다.

권장 원칙:

- 최신 수치의 단일 출처는 `PROGRESS.md`로 둔다.
- `FINAL_REPORT.md`는 특정 날짜의 최종 보고서라면 "작성 당시 수치"인지 "현재 최신 수치"인지 명시한다.
- 전달용 문서에는 오래된 수치를 직접 박아두기보다 `PROGRESS.md` 참조로 돌리는 편이 낫다.

## 9. 네이밍 정리 제안

현재 비교 폴더의 문서명은 사람이 읽기에는 좋지만, 시간이 지나면 순서가 헷갈릴 수 있다.

앞으로는 다음 규칙을 권장한다.

```text
(작성자) (MMDD-N) 주제.md
```

예:

```text
(Codex) (0513-1) claud_통합_docs_현황_및_하이브리드_질의_분석.md
(Codex) (0513-2) ontology_vector_hybrid_query_구현_우선순위.md
(Codex) (0513-3) 문서_정합성_정리_체크리스트.md
```

이 규칙을 쓰면 같은 날 여러 문서가 생겨도 순서가 유지되고, 기존 `(0512보완)` 문서와도 충돌하지 않는다.

## 10. 최종 판정

현재 `claud_통합/docs`는 한 문장으로 이렇게 볼 수 있다.

> 기존 통합 프로젝트는 완료 상태이고, 지금 문서의 중심은 "검색형 RAG"에서 "결정적 온톨로지 질의 + RAG 근거 합성"으로 넘어가는 2차 고도화 설계 단계다.

기술적으로는 이미 교육/시연용 완성도를 넘겼고, 운영형 MVP의 기반도 갖췄다. 다음 단계의 가치는 단순히 UI를 더 붙이는 것이 아니라, 온톨로지와 벡터DB를 역할 분리해서 결합하는 데 있다.

따라서 다음 작업 지시는 다음처럼 주는 것이 가장 명확하다.

```text
claud_통합에서 Ontology+Vector 하이브리드 질의를 구현해줘.
우선 ontology_query_engine.py와 /api/hybrid/ask를 만들고,
LLM은 Query Plan 생성과 최종 설명에만 사용하며,
필터/비교/계산은 코드가 결정적으로 실행하게 해줘.
벡터 검색과 온톨로지 검색은 doc_ids 범위를 공유하게 해줘.
```

이 방향이 현재 문서들이 가리키는 다음 자연스러운 단계다.
