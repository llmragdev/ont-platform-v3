## 1. 총평

현재 설계의 방향은 타당하다. 벡터 RAG는 설명형 답변과 원문 근거 검색에 강하고, 온톨로지는 필터링, 비교, 계산, 관계 탐색에 강하다. 따라서 “서술형은 벡터, 구조형은 온톨로지, 복합형은 둘 다”라는 라우팅 전략은 좋은 출발점이다.

다만 현재 설계는 PoC에는 적합하지만, 정확도와 재현성을 높이려면 LLM이 모든 판단을 직접 수행하는 구조에서 벗어나야 한다. LLM은 추출, 질의 계획, 최종 설명에 쓰고, 실제 필터·비교·계산은 코드가 결정적으로 수행하는 편이 더 안정적이다.

## 2. 좋은 점

| 항목 | 평가 |
| --- | --- |
| 질문 유형 분리 | RAG와 온톨로지의 역할을 명확히 나눴다. |
| 구조형 결과 표시 | 표/목록 형태 응답을 별도로 두는 방향이 좋다. |
| 근거 표시 | 벡터 청크와 온톨로지 노드 근거를 함께 보여주려는 점이 중요하다. |
| JSON 저장소 선택 | 초기 규모에서는 의존성 없이 빠르게 검증 가능하다. |
| 범용 유형 + 도메인 config | Snowflake 문서에만 묶이지 않도록 한 점이 좋다. |

## 3. 핵심 위험

### 3-1. 전체 텍스트 1회 추출의 누락 위험

설계는 “전체 텍스트를 LLM에 1회 전달”하는 방식을 택했다. 하지만 실제 구현에서는 토큰 제한 때문에 문서 앞부분만 들어갈 가능성이 높고, 긴 PDF의 뒤쪽 엔티티와 관계가 누락될 수 있다.

권장 방식:

```text
청크별 엔티티/관계 후보 추출
  → canonical name 기준 병합
  → 중복 제거
  → 관계 검증
  → source page/chunk/confidence 포함 저장
```

청크별 추출은 중복을 만들지만, 중복은 병합할 수 있다. 반대로 누락은 나중에 복구하기 어렵다.

### 3-2. 출처 메타데이터 부족

온톨로지 엔티티에 다음 메타데이터가 필요하다.

| 필드 | 목적 |
| --- | --- |
| `source_doc_id` | 어떤 문서에서 추출됐는지 추적 |
| `source_page` | 사용자에게 근거 페이지 표시 |
| `source_chunk_id` | 벡터 청크와 연결 |
| `source_text` | 추출 근거 원문 |
| `confidence` | 자동 추출 결과 검토 우선순위 |

구조형 결과도 근거가 없으면 신뢰하기 어렵다. 특히 교육용 데모에서는 “왜 이 답이 나왔는지”를 보여주는 것이 중요하다.

### 3-3. 질문 분류보다 질의 계획이 필요

`descriptive/filter/compare/calculate/hybrid` 라벨만으로는 실행에 필요한 정보가 부족하다. 더 좋은 출력은 질의 계획이다.

```json
{
  "intent": "filter",
  "ontology_filters": [
    {
      "entity_type": "PRODUCT",
      "property": "billing_model",
      "op": "contains",
      "value": "Serverless"
    }
  ],
  "vector_queries": ["Serverless 과금 방식 설명"],
  "needs_vector": true
}
```

이렇게 하면 LLM은 “무엇을 찾아야 하는지”만 계획하고, 실제 검색과 계산은 코드가 수행한다.

### 3-4. 문서 범위 필터 필요

하이브리드 질의에는 `doc_ids` 범위가 있어야 한다. 선택한 문서의 온톨로지를 쓰면서 벡터 검색은 전체 문서에서 가져오면 답변 근거가 섞일 수 있다.

권장:

```text
ontology_query(doc_ids=[...])
vector_search(query, doc_ids=[...])
```

### 3-5. JSON 저장은 가능하지만 인덱스가 필요

초기 저장소는 JSON으로 충분하다. 다만 질의 엔진 내부에는 다음 인덱스를 만들어야 한다.

```text
by_id
by_name
by_type
by_property_key
relations_by_from
relations_by_to
```

파일 저장소는 단순하게 두되, 실행 시 인덱스를 만들어 결정적 질의를 빠르게 처리하는 방식이 적절하다.

## 4. 개선된 권장 아키텍처

```text
PDF 업로드
  → 청크 분할
  → 벡터 임베딩 저장
  → 청크별 엔티티/관계 후보 추출
  → 엔티티 정규화 및 병합
  → 관계 검증
  → source/confidence 포함 온톨로지 저장

질문 입력
  → Query Planner가 실행 계획 생성
  → 온톨로지 필터/비교/계산 실행
  → 필요한 경우 doc_id로 제한한 벡터 검색 실행
  → 구조형 결과 + 벡터 근거 + 온톨로지 경로 병합
  → LLM은 최종 설명 생성
```

## 5. 구현 우선순위

| 순서 | 작업 | 이유 |
| --- | --- | --- |
| 1 | `ontology_query_engine.py` 구현 | 필터/비교/계산/관계 탐색의 결정적 기반 |
| 2 | `/api/hybrid/ask` 추가 | 프론트에서 통합 질의를 바로 검증 가능 |
| 3 | 벡터 검색 `doc_ids` 필터 추가 | 선택 문서와 근거 혼선을 방지 |
| 4 | 추출 결과에 `source_*`, `confidence` 추가 | 구조형 답변의 추적 가능성 확보 |
| 5 | 질문 분류기를 Query Planner로 확장 | 단순 라벨보다 실행 가능성이 높음 |
| 6 | 청크별 추출 + 병합으로 전환 | 긴 문서 누락 방지 |

## 6. 한 줄 결론

현재 설계는 좋은 PoC다. 더 나은 구현은 “LLM이 답을 직접 만들게 하는 구조”가 아니라 “LLM이 계획하고, 코드는 온톨로지와 벡터DB를 결정적으로 실행하며, LLM은 마지막 설명만 맡는 구조”다.
