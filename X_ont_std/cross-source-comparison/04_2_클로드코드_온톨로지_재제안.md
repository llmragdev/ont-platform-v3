## 1. Antigravity의 진단 검증 및 수용

### ✅ 합의한 기술 현실

**1.1 RDF/SPARQL의 한계는 구조적**

```
성능 벽: 100K 트리플 근처에서 급격히 악화

Current Implementation (JSONL + rdflib):
├─ 10K 엔티티: 0.1초 ✅ (테스트 통과)
├─ 50K 엔티티: 2-5초 ⚠️ (쿼리 응답 저하)
├─ 100K 엔티티: 20-60초 ❌ (사용 불가)
└─ 1M 엔티티: 분 단위 ❌ (실용 불가)

원인: Self-Join 폭발 + 메모리 GIL + 전체 그래프 스캔
```

이는 **구현의 문제가 아니라 아키텍처의 한계**다.
- rdflib은 이미 최적화된 순수 파이썬 구현
- 트리플 스토어 자체의 조인 문제 회피 불가
- 따라서 저장소 계층 전환 필수

**1.2 글로벌 솔루션의 현실**

✅ **확인됨**: Palantier, Neo4j 모두 W3C 표준을 완벽히 준수하지 않음
- **팔란티어**: RDF/SPARQL 미지원 (Object-Link-Action 모델 사용)
- **Neo4j**: SPARQL 미지원 (Cypher 강제, n10s 플러그인도 결국 LPG로 변환)

❌ **기존 설명 오류 수정**:
- ~~"팔란티어가 네이티브 SPARQL 지원"~~ → 실제로는 NOT 지원
- ~~"Neo4j가 완벽한 SPARQL 준수"~~ → Cypher 전용, SPARQL 호환 X

### 2.2 설계의 유연성 평가

✅ **유지된 유연성**:
- Entity-Relationship 모델은 여전히 추상적 (OntologyRepository)
- Triple Store는 분리된 레이어 (교체 가능)
- Service 계층은 Index 선택적 사용 (fallback 지원)
- V1 정규식 엔진과 V2 rdflib 엔진 병행 가능

❌ **잃어버린 유연성**:
- 메타데이터 저장이 JSON 기반 (관계형 쿼리 불가)
- 동시 쓰기가 파일 기반 (트랜잭션 격리 없음)
- 인덱싱이 SQLite 별도 (메인 저장소와 동기화 문제)

### 3.2 핵심 컴포넌트: SPARQL→SQL 번역기

**목표**: 사용자는 SPARQL 작성, 시스템은 SQL 실행

#### 예시 1: 기본 엔티티 조회

```sparql
입력 (사용자 작성):
PREFIX ex: <http://example.org/>
SELECT ?person ?name
WHERE {
  ?person ex:type "Person" ;
          ex:name ?name ;
          ex:age ?age
  FILTER (?age > 25)
}

↓ Translator 변환:

출력 (시스템 실행):
SELECT 
  e1.id AS person,
  e1.properties->>'name' AS name
FROM entities e1
WHERE e1.entity_type = 'Person'
  AND (e1.properties->>'age')::INTEGER > 25
```

#### 예시 2: 관계를 포함한 쿼리

```sparql
입력:
PREFIX ex: <http://example.org/>
SELECT ?person ?company
WHERE {
  ?person ex:works_at ?company ;
          ex:type "Employee"
  ?company ex:type "Company"
}

↓ Translator 변환:

출력:
SELECT DISTINCT
  e1.id AS person,
  e2.id AS company
FROM entities e1
INNER JOIN relationships r ON e1.id = r.from_entity_id
INNER JOIN entities e2 ON r.to_entity_id = e2.id
WHERE e1.entity_type = 'Employee'
  AND r.relation_type = 'works_at'
  AND e2.entity_type = 'Company'
```

#### 구현 구조

```python

    """SPARQL→SQL 번역 엔진"""
    
    def translate(self, sparql_query: str) -> SQLStatement:
        """
        SPARQL 쿼리를 SQL로 변환
        
        입력: SELECT ?x WHERE { ?x ex:type "Person" }
        출력: SELECT id FROM entities WHERE entity_type = 'Person'
        """
        # 1. SPARQL 파싱 (rdflib 사용)
        parsed = self._parse_sparql(sparql_query)
        
        # 2. 패턴 분석
        patterns = self._extract_triple_patterns(parsed)
        
        # 3. SQL JOIN 생성
        sql = self._generate_sql(patterns)
        
        # 4. 최적화 (인덱스 힌트, 카디널리티)
        optimized = self._optimize(sql)
        
        return optimized
```

### 3.3 PostgreSQL 스키마 설계

```sql
-- 1. 엔티티 테이블
CREATE TABLE entities (
    id VARCHAR(255) PRIMARY KEY,
    entity_type VARCHAR(100) NOT NULL,
    domain_id VARCHAR(100) NOT NULL,
    doc_id VARCHAR(255),
    properties JSONB DEFAULT '{}',
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    version INT DEFAULT 1
);

CREATE INDEX idx_entities_type ON entities(entity_type);
CREATE INDEX idx_entities_domain ON entities(domain_id);
CREATE INDEX idx_entities_doc ON entities(doc_id);
CREATE INDEX idx_entities_properties ON entities USING GiST(properties);

-- 2. 관계 테이블
CREATE TABLE relationships (
    id VARCHAR(255) PRIMARY KEY,
    from_entity_id VARCHAR(255) NOT NULL REFERENCES entities(id),
    to_entity_id VARCHAR(255) NOT NULL REFERENCES entities(id),
    relation_type VARCHAR(100) NOT NULL,
    domain_id VARCHAR(100) NOT NULL,
    doc_id VARCHAR(255),
    properties JSONB DEFAULT '{}',
    weight DECIMAL(10,2),
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    version INT DEFAULT 1
);

CREATE INDEX idx_relationships_from ON relationships(from_entity_id);
CREATE INDEX idx_relationships_to ON relationships(to_entity_id);
CREATE INDEX idx_relationships_type ON relationships(relation_type);
CREATE INDEX idx_relationships_domain ON relationships(domain_id);

-- 3. 메타데이터 테이블
CREATE TABLE ontology_metadata (
    id SERIAL PRIMARY KEY,
    domain_id VARCHAR(100) NOT NULL UNIQUE,
    ontology_version VARCHAR(50),
    last_updated TIMESTAMP DEFAULT NOW(),
    entity_count INT DEFAULT 0,
    relationship_count INT DEFAULT 0,
    metadata JSONB
);

-- 4. 감사 추적 테이블
CREATE TABLE audit_log (
    id SERIAL PRIMARY KEY,
    domain_id VARCHAR(100) NOT NULL,
    operation VARCHAR(50),
    entity_id VARCHAR(255),
    old_state JSONB,
    new_state JSONB,
    actor VARCHAR(100),
    timestamp TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_audit_domain ON audit_log(domain_id);
CREATE INDEX idx_audit_timestamp ON audit_log(timestamp);

-- 5. Triple View (읽기 용도)
CREATE VIEW ontology_triples AS
SELECT 
    CONCAT('entity:', e.id) AS subject,
    CONCAT('property:', key) AS predicate,
    value AS object,
    'entity_property' AS type,
    e.domain_id
FROM entities e, JSONB_EACH_TEXT(e.properties)
UNION ALL
SELECT
    CONCAT('entity:', r.from_entity_id) AS subject,
    CONCAT('relation:', r.relation_type) AS predicate,
    CONCAT('entity:', r.to_entity_id) AS object,
    'relationship' AS type,
    r.domain_id
FROM relationships r;
```

```
├─ JSONL → PostgreSQL 동기화
├─ 읽기는 양쪽에서 검증
└─ 상태: Dual-Write

Phase B: 쓰기 전환 (3일)
├─ 신규 쓰기는 PostgreSQL로
├─ 기존 데이터는 계속 JSONL 읽기
├─ AsyncIO로 백그라운드 마이그레이션
└─ 상태: PostgreSQL Primary

Phase C: JSONL 폐기 (1주)
├─ 마이그레이션 검증
├─ JSONL → 백업으로 아카이브
├─ 코드에서 TripleStore 제거
└─ 상태: PostgreSQL Only
```

### 5.2 필요한 코드 변경

## 8. 동시성 문제 해결

### 8.1 Atomic Rename의 한계

```
현재 (JSONL):
├─ 동시 쓰기 5개 → 파일 잠금 (일부 실패 허용)
├─ 일관성 보장 없음 (Lost Update 가능)
├─ 격리 레벨 없음 (Dirty Read 가능)
└─ 복구 메커니즘 없음

실제 프로덕션에서 발생 가능한 버그:
1. 스레드 A와 B가 동시에 같은 파일 업데이트
2. A가 끝나고 B가 끝나면 → B의 쓰기만 남음 (A의 결과 손실)
3. 감사 추적에는 A의 변경이 기록됨 (불일치)
```

### 8.2 PostgreSQL 트랜잭션 솔루션

```sql
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- 트랜잭션 A
UPDATE entities SET properties = ... WHERE id = '123';

-- 동시에 트랜잭션 B가 같은 행을 수정하려 함
-- → PostgreSQL이 자동으로 감지하고 B를 Rollback
-- → 애플리케이션이 재시도 로직 수행

COMMIT;
```

**이점**:
- 원자성 (Atomicity)
- 일관성 (Consistency)
- 격리성 (Isolation) SERIALIZABLE
- 내구성 (Durability) 디스크에 기록
