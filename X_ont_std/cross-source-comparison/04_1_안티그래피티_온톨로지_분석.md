## 1. 현재 선택지: RDFLib vs Graph DB

### A. RDFLib + SPARQL (메모리 기반)

#### ✅ 장점
- **표준화**: W3C SPARQL 1.1 완벽 준수
  - 향후 상용 Graph DB로 전환해도 쿼리 코드 재사용 가능
  - 시맨틱 웹 에코시스템 접근 가능
  
- **경량성**: 인프라 최소화
  - Docker/분산 DB 서버 불필요
  - 초기 PoC에 최적
  
- **표현력**: 복잡한 그래프 쿼리
  - Property Path: `?person foaf:knows+/foaf:name ?result`
  - 전이 관계 추적 (Transitive Closure)
  - OWL 추론 규칙

#### ❌ 단점
```
성능 벽: 100K 트리플에서 급격히 악화

┌─────────────────────┐
│ 10K 트리플: 실시간 ✅ │
│ 50K 트리플: 느려짐  ⚠️ │
│ 100K+ : 분 단위    ❌ │
└─────────────────────┘

원인:
- GIL 제약 (Python 싱글 프로세스)
- 메모리 기반 (디스크 I/O 병목)
- 쿼리마다 전체 그래프 스캔
```

## 2. 그래프 DB의 구조적 성능 문제

### A. 조인 폭발 (Join Explosion) 🔴

```
[ LPG/RDBMS: 효율적 ]
SELECT * FROM ships WHERE id = 101
→ 1회 조회로 이름, 무게, 길이 등 10개 속성 모두 획득

[ RDF: 비효율적 ]
SELECT ?name ?weight ?length
WHERE {
  <ship:101> foaf:name ?name ;
             ship:weight ?weight ;
             ship:length ?length ;
             ... (10개 속성)
}
→ 10번의 자기 조인(Self-Join) 강제
→ 트리플 수 증가 시 O(N²) 성능 악화
```

**실제 영향:**
- 1M 트리플 × 10개 속성 조회 = 10M 쿼리 결과 중복 처리
- 병렬 처리 불가 (트리플 간 강한 의존성)

### B. 인덱스 비대화 (Index Bloat) 🟡

```
모든 트리플 저장소의 인덱스 전략:
SPO, SOP, PSO, POS, OSP, OPS (6가지 순열 모두)

결과:
- 원본 데이터: 100GB
- 인덱스 크기: 300~500GB
- 디스크 낭비: 3~5배

부작용:
- 쓰기(INSERT/UPDATE) 성능 급감
- 50K 트리플 이상: 쓰기 속도 관리 필요
```

### C. 분산 처리 어려움 🔴

```
RDF 특성: 엔티티 관계가 글로벌
→ 샤딩 어려움 (경계 불명확)

분산 쿼리 비용:
┌─────────────────────────┐
│ RDBMS 분산: 네트워크 홉 2~3 │
│ Graph DB 분산: 홉 10~20   │
│ 속도: RDBMS가 10배 빠름  │
└─────────────────────────┘
```

## 3. 글로벌 솔루션의 실제 선택

### A. Palantir Foundry: "표준을 버림"

```
공식 지원: RDF ❌ / SPARQL ❌
대신: Object-Link-Action 독자 모델
```

**왜 RDF를 안 쓸까?**

1. **성능**: Petabyte 규모 데이터
   - 트리플 스토어의 조인 폭발 문제 회피
   - Parquet/Iceberg 포맷으로 직접 처리
   
2. **쓰기 성능**: Write-back 특성화
   - 분석 결과 → 소스 시스템 역반영
   - RDF는 이 워크플로우에 부적합
   
3. **독자 기술**:
   - Ontology SQL (Spark SQL 기반)
   - TypeScript 함수형 쿼리
   - 자체 형식화 언어

**결론**: 팔란티어는 표준을 포기했지만 **성능 극대화 + 쓰기 최적화 달성**

### B. Neo4j: "표준을 변환함"

```
공식 지원: RDF ⚠️ (neosemantics 플러그인)
쿼리 언어: Cypher (RDF와 다름)
```

**실제 동작:**
1. RDF 임포트 시: LPG로 자동 변환
2. 쿼리: Cypher로만 가능
3. W3C SPARQL 표준: **미지원**

```
문제: SPARQL 쿼리를 쓸 수 없음
SPARQL:  SELECT ?x WHERE { ?x a Person }
↓ 변환 필요 (수동 또는 번역기)
Cypher:  MATCH (x:Person) RETURN x

→ 표준 호환성 유지 불가
```

## 4. ont_platform v3의 결정적 문제

### A. 이중 계약 위반

**문제 1: 요구사항 미달**
- Phase 4 명세: "표준 RDF/SPARQL API 제공"
- 현 구현: 정규식 기반 Mock SPARQL
- 수준: 프로토타입 (프로덕션 불가)

```python
# 현재 구현 (문제)
class SPARQLEngine:
    def _detect_query_type(self, query_string):
        upper_query = query_string.upper().strip()
        if upper_query.startswith("SELECT"):
            return "SELECT"  # ❌ 단순 문자열 매칭
        # FILTER, UNION, 서브쿼리 등 미지원
```

**문제 2: 생태계 접근 불가**

팔란티어의 선택 (자체 엔진 개발 가능) vs ont_platform의 현실:
```
팔란티어:
└─ 자체 Ontology SQL + TypeScript 엔진
   → 1000명 엔지니어 투입 가능
   → 독자 생태계 구성

ont_platform:
└─ 표준을 가짜로 흉내냄
   → W3C SPARQL 생태계 접근 불가
   → Wikidata, DBpedia 등 연동 불가
   → 기존 SPARQL 도구 사용 불가
```

**결과**: 최악의 상황
- 팔란티어처럼 성능 좋은 독자 엔진도 없음
- Neo4j처럼 표준 생태계 접근도 없음
- 정규식 Mock 엔진으로 시간 낭비 중

## 5. 올바른 아키텍처 전략

### A. 단기 (현재~1개월): 표준 준수

```
현황: 가짜 SPARQL ❌
↓
개선: rdflib 통합 + SPARQL 1.1 완벽 준수

목표: 
├─ Turtle/N-Triples 파싱 ✅
├─ FILTER/UNION/OPTIONAL 지원 ✅
├─ 외부 온톨로지 연동 ✅
└─ SPARQL 쿼리 검증 ✅

기간: 2-3주
테스트: SPARQL 쿼리 50개 표준 준수 검증
```

### B. 중기 (1~3개월): 성능 개선

```
문제: RDF 100K 트리플 넘으면 느려짐
해결책: 데이터는 PostgreSQL/Neo4j, API는 표준

아키텍처:
┌─────────────────────────────────────┐
│ API Layer (표준 W3C SPARQL 인터페이스) │
├─────────────────────────────────────┤
│ SPARQL → SQL/Cypher 변환 레이어 ⭐  │
├─────────────────────────────────────┤
│ Backend (PostgreSQL 또는 Neo4j)     │
└─────────────────────────────────────┘

핵심: 변환 레이어
- 사용자: 표준 SPARQL 쿼리 작성
- 시스템: 내부적으로 SQL/Cypher 실행
- 반환: RDF 트리플 형식

예시:
입력 SPARQL:
  SELECT ?person ?name 
  WHERE { ?person foaf:name ?name; rdf:type foaf:Person }

↓ 변환

출력 SQL:
  SELECT id as person, properties->>'name' as name
  FROM entities
  WHERE entity_type = 'Person'
```

### C. 장기 (3개월+): 쓰기 최적화

```
팔란티어 급의 Write-back 지원
├─ 트랜잭션 보장
├─ 원자적 쓰기 (Atomic)
├─ 감사 추적 (Audit Log)
└─ 버전 관리

현재 상태: Priority 3 (Atomic Rename) 부분 구현 ✅
추가 필요: 트랜잭션 격리 + 동시성 제어
```

## 6. 의사결정 기준

### "RDF/SPARQL을 진짜로 쓸 것인가?"

| 시나리오 | 선택 | 이유 |
|---------|------|------|
| **표준 준수 필요** | rdflib ✅ | W3C 생태계 접근 |
| **성능 우선** | PostgreSQL + Cypher 변환 | Palantier 방식 |
| **팀 규모 < 50명** | PostgreSQL (관계형) | 운영 단순함 |
| **연구/교육 목적** | rdflib 단독 | 표준 학습 최고 |
| **엔터프라이즈급** | Neo4j + 변환 | 그래프 최적화 |
