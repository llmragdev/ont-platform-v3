## 5. ont_platform v4 (Team4) 성능 분석

### 5.1 원본 vs 수정본 비교

| 카테고리 | 원본 | 수정 후 | 변화 |
|---|---:|---:|---:|
| Advanced RAG | 68.75% | 68.75% | = |
| Ontology | 75.62% | 75.62% | = |
| **Snowflake** | **58.12%** | **31.25%** | **-26.87%p** |
| **전체** | **67.50%** | **58.54%** | **-8.96%p** |

### 5.2 원인 분석

**Snowflake 약점의 근본 원인:**

1. **온톨로지 모델의 한계**
   - 온톨로지는 존재하는 개념과 관계만 표현 가능
   - Snowflake 문서 부재 = 온톨로지 상에 표현 불가
   - 따라서 "문서 부재 감지" 기능 약함

2. **하이브리드 검색의 과잉 신뢰**
   - 벡터 검색 + 온톨로지 검색 병렬 실행
   - 하나라도 결과 반환하면 답변 시도
   - "관련 없음"을 명확히 판단하지 못함

3. **Gemini LLM Judge 오류**
   - 기술적 설명이 있으면 높은 점수 부여
   - "관련 없음"을 판단하는 기준 약함
   - 추정답변과 실제답변의 유사도 계산에 편향

### 6.2 결론

**원본 평가의 문제점 해결:**

✅ **Snowflake 예상답변 수정 완료**
- "해당 카테고리 문서와 관련이 없습니다"로 통일

- Team1의 간단한 접근이 "문서 부재 감지"에 가장 효과적
- 복잡한 온톨로지 시스템이 edge case 처리에 약함
- Snowflake 같은 예외 케이스가 성능 수렴점 결정

**향후 개선 방향:**

1. **ont_platform v4 개선**
   - 온톨로지에 "문서 부재" 개념 추가

   - Snowflake 같은 제외 카테고리 명시적 처리

2. **평가 기준 개선**
   - 예상답변이 질문과 일관되는지 검증
   - 평가 대상 문서 범위와 예상답변 정렬

3. **장기 계획**
   - 다른 "문서 부재" 케이스 식별
   - 온톨로지 기반 시스템의 edge case 처리 전략 수립
