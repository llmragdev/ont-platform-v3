# 클로드 코드 완성 지시 가이드

작성일: 2026-05-12  
대상 프로젝트: `E:\ontology_edu\claud_통합`  
목적: 현재 구현된 교육용 통합 콘솔을 온톨로지 기반 워크플로우 플랫폼에 더 가깝게 완성하기 위한 작업 지시서

## 1. 현재 판정

현재 `claud_통합`은 단순 목업이 아니라 실제 API, 정책, 워크플로우, RAG 평가, E2E 테스트가 붙은 통합 프로토타입이다.

확인된 강점:
- FastAPI + Next.js 통합 구조가 잡혀 있다.
- 온톨로지, 정책, 검색, RAG, 워크플로우, 감사 로그가 서비스 단위로 분리되어 있다.
- 백엔드 테스트, 학습 시나리오, RAG 평가, Playwright E2E가 존재한다.
- `Customer`, `Order`, `Product` 관계를 이용해 승인 정책과 AI 질의 컨텍스트를 구성한다.
- JWT 백엔드, Repository 계층, Docker, Telemetry 보강 흔적이 있다.

현재 한계:
- 온톨로지 스키마가 `backend/app/ontology.py`에 하드코딩되어 있다.
- 워크플로우 전이와 액션도 `backend/app/workflow.py`에 하드코딩되어 있다.
- 정책 조건이 코드 중심이라 관리자가 규칙을 수정하기 어렵다.
- Gemini 실제 호출 성공률과 답변 품질 검증은 아직 운영 수준으로 충분하지 않다.
- 프론트 JWT 통합은 남은 작업으로 보인다.
- 문서 일부는 루트 기준과 `docs/` 기준이 섞여 있어 정리가 필요하다.

완성 목표는 "교육용 데모"를 넘어서 "설정 가능한 온톨로지 기반 워크플로우 콘솔"이 되는 것이다.

## 2. 클로드 코드에게 지시할 작업 원칙

아래 원칙을 반드시 지켜라.

1. 기존 구조를 유지하면서 확장하라.
   - `OntologyService`, `WorkflowService`, `PolicyEngine`, `RAGService`, `Repository`, `AuditService` 경계를 유지한다.
   - 큰 리라이트보다 설정화, 테스트 보강, 문서 정합성 개선을 우선한다.

2. 코드 하드코딩을 줄이고 선언형 설정으로 이동하라.
   - 온톨로지 타입, 속성, 관계를 JSON 또는 YAML로 분리한다.
   - 워크플로우 상태, 액션, 전이, 조건을 JSON 또는 YAML로 분리한다.
   - 정책도 가능한 범위에서 설정 파일 기반으로 이동한다.

3. 모든 변경은 테스트로 검증하라.
   - 기존 테스트를 깨지 않는다.
   - 새 설정 로더, 스키마 검증, 워크플로우 전이 검증 테스트를 추가한다.
   - E2E는 핵심 5개 학습 시나리오가 계속 통과해야 한다.

4. 문서를 코드 상태와 맞춰라.
   - 현재 문서 위치는 `claud_통합/docs/` 기준으로 정리한다.
   - README에는 실행 방법과 데모 방법만 남긴다.
   - 진행 상태는 `docs/PROGRESS.md`, 변경 이력은 `docs/CHANGELOG.md`, 남은 작업은 `docs/NEXT_STEPS.md`로 분리한다.

## 3. 최우선 작업

### 3.1 온톨로지 스키마 외부화

목표:
- `Customer`, `Product`, `Order` 타입과 속성 정의를 코드 밖으로 분리한다.
- `PLACED_ORDER`, `ORDER_CONTAINS_PRODUCT` 관계 정의를 코드 밖으로 분리한다.
- 서비스는 설정을 읽어 Registry를 구성하도록 바꾼다.

권장 파일:
- `backend/config/ontology.schema.json`
- `backend/config/ontology.default.json`

완료 조건:
- `OntologyService`가 하드코딩된 타입 정의 없이 설정 파일로 Registry를 구성한다.
- 필수 속성 누락, 타입 불일치, 관계 source/target 불일치에 대한 테스트가 있다.
- 기존 API 응답과 학습 시나리오는 유지된다.

검증:
```powershell
cd E:\ontology_edu\claud_통합\backend
$env:PYTHONIOENCODING="utf-8"
pytest
python -m eval.scenarios --json
python evaluate.py --json
```

### 3.2 워크플로우 정의 외부화

목표:
- 주문 승인 상태, 액션, 전이를 설정 파일로 분리한다.
- `ApproveOrder`, `RejectOrder`, `HoldOrder`, `FulfillOrder`, `CloseOrder`의 전이 조건을 선언적으로 관리한다.

권장 파일:
- `backend/config/workflow.schema.json`
- `backend/config/workflow.order.json`

권장 방향:
- 상태 목록: `Submitted`, `Review`, `Approved`, `Rejected`, `Fulfilled`, `Closed`
- 액션 목록: `ApproveOrder`, `RejectOrder`, `HoldOrder`, `FulfillOrder`, `CloseOrder`
- 전이 목록: from, action, to, condition_key 형태
- 조건 구현은 우선 `PolicyEngine`의 named condition으로 연결한다.

완료 조건:
- `WorkflowService._build_engine()`의 전이 하드코딩이 설정 로딩으로 대체된다.
- 잘못된 상태명, 액션명, 중복 전이, 존재하지 않는 조건에 대한 테스트가 있다.
- 기존 워크플로우 API와 E2E가 유지된다.

### 3.3 정책 규칙 정리

목표:
- 현재 정책을 문서화하고, 가능한 부분을 설정화한다.
- 금액 기준, 위험 등급 차단, 역할별 액션 권한, 지역 필터를 명확히 분리한다.

권장 파일:
- `backend/config/policy.default.json`
- `backend/docs/policy_rules.md` 또는 `docs/policy_rules.md`

완료 조건:
- `PolicyEngine`이 최소한 금액 임계값, 역할별 권한, 고위험 고객 차단 조건을 설정에서 읽는다.
- 정책 변경 시 테스트 데이터나 코드 수정 없이 기준값을 바꿀 수 있다.
- 기존 5개 학습 시나리오가 계속 통과한다.

## 4. 두 번째 우선순위

### 4.1 프론트 JWT 통합 완성

목표:
- `?user=` 쿼리 기반 데모 모드를 유지하되, 실제 사용 흐름은 JWT 로그인으로 전환한다.

작업:
- `frontend/src/app/login/page.tsx` 추가
- `POST /api/auth/login` 호출
- access token을 저장하고 API 요청에 `Authorization: Bearer` 자동 첨부
- 사용자 선택 드롭다운은 "데모 모드"임을 명확히 하거나 로그인 계정 전환 방식으로 교체
- E2E에 로그인 시나리오 추가

완료 조건:
- 쿼리스트링 없이 JWT만으로 주요 API가 동작한다.
- 기존 데모 시나리오도 깨지지 않는다.
- 잘못된 토큰, 만료 토큰, 로그아웃 흐름을 검증한다.

### 4.2 Gemini 실제 응답 평가

목표:
- rule-based fallback만이 아니라 실제 Gemini 응답의 품질을 별도 평가한다.

작업:
- `LLM_EVAL.md` 생성
- 실제 Gemini 연결 성공 시 5~10개 질문을 실행하고 응답 품질을 기록
- 답변의 근거 문서 인용, 정책 판단, 환각 여부, latency를 평가
- `evaluate.py`에 실제 LLM 품질 체크 항목을 선택적으로 추가

완료 조건:
- `GEMINI_API_KEY`가 있을 때와 없을 때의 동작이 모두 문서화된다.
- fallback이 발생해도 사용자에게 명확한 warning이 전달된다.
- 실제 Gemini 응답에서 정책 위반 액션을 추천하지 않는지 검증한다.

### 4.3 문서 정합성 정리

목표:
- 문서 상태와 실제 코드 상태가 다르게 보이지 않도록 정리한다.

작업:
- `README.md`의 테스트 개수, 문서 경로, Next Steps 설명 최신화
- `docs/PROGRESS.md`의 `17 passed` 같은 오래된 문구를 `36 passed` 등 현재 상태로 통일
- `docs/NEXT_STEPS.md`에서 완료된 작업과 미완료 작업을 분리
- `CHANGELOG.md` 위치를 README와 일치시킴

완료 조건:
- README만 읽어도 실행, 테스트, 데모 흐름을 따라갈 수 있다.
- `docs/PROGRESS.md`는 현재 상태만 말한다.
- `docs/NEXT_STEPS.md`는 실제 남은 작업만 말한다.

## 5. 세 번째 우선순위

### 5.1 Repository 운영성 보강

목표:
- InMemory, JsonFile, Postgres Repository의 역할을 명확히 한다.

작업:
- Postgres 연결 성공/실패 로그 개선
- Docker compose에서 Postgres 실제 연결 검증
- 데이터 초기화/마이그레이션 명령 추가
- Repository별 테스트 분리

완료 조건:
- `DATABASE_URL`이 있으면 Postgres 사용, 없으면 InMemory 또는 JsonFile 사용이 명확히 동작한다.
- Docker compose 실행 후 API와 E2E가 통과한다.

### 5.2 운영 관측성 보강

목표:
- 감사 로그, latency, LLM provider, 검색 evidence를 추적 가능하게 만든다.

작업:
- `/api/health`에 설정 로딩 상태, repository 종류, ontology/workflow config version 표시
- OpenTelemetry span 이름 정리
- 감사 로그 필터 API 추가: event_type, actor, object_id, date

완료 조건:
- 장애 분석 시 "누가, 어떤 객체에, 어떤 정책 때문에, 어떤 액션을 실패했는지" 확인 가능하다.
