## 🔴 로드맵의 부실한 부분

### 1. **Phase 3 (비즈니스 액션) — 가장 중요한데 부실**

#### 현황
- 구체적인 **비즈니스 액션 정의 불완전**
- AI바우처 도메인의 실제 필요한 액션 미파악
  - "ApproveProject, RejectProject, ChangeStatus" — 너무 일반적
  - 실제 사용자 워크플로우 미매핑

#### 필요한 정보 (현재 없음)
```
□ AI바우처 도메인의 의사결정 프로세스
  - 누가 승인하나? (1단계 vs 다단계?)
  - 어떤 조건에서 승인/반려? (금액? 절차?)
  - 변경 대상은 무엇? (예산, 일정, 담당자?)

□ 상태 기계 구체화
  - PROJECT 상태값이 정확히 무엇인가?
  - 상태 간 전이 규칙이 몇 개?
  - 원자적(atomic) 전이인가?

□ Write-back 대상 시스템
  - ERP/SAP 어느 버전?
  - API 명세 확보됐나?
  - 필드 매핑 정의 필요
```

#### 위험도
🔴 **High** — Phase 3이 전체 ROI의 핵심인데, 아직 요구사항 수집 단계

---

### 2. **Phase 4 (다중 도메인) — 일정 미확정**

#### 현황
- 도메인 3개 (조선, 제조, 구매) 나열됨
- 우선순위 표시 (조선 🔴 High)
- 하지만 **시간/예산/리소스 미정**

#### 문제점
```
□ 각 도메인 설계 기간: "4주", "3주", "3주"
  - 누가 설계? (데이터 엔지니어? 도메인 전문가?)
  - 테스트 데이터는? (샘플 vs 실제?)

□ 조선 도메인 (가장 큼)
  - 블록, 자재, 센서, 워커 — 엔티티 많음
  - 공정 지연 감지 → 자재 발주 → ERP 동기화 — 복잡
  - 현중과의 협의 필요 여부 불명

□ 비용 추정 없음
  - 각 도메인 개발 비용?
  - API 연동 비용?
  - 테스트 비용?
```

#### 위험도
🟠 **Medium-High** — 8월 시작 예정인데 지금부터 준비 필요

---

### 3. **Phase 5 (운영형 하드닝) — 너무 일반적**

#### 현황
- 보안, 성능, 모니터링, 배포, 문서화 나열됨
- 하지만 **구체적인 수준/기준 미정**

#### 문제점
```
□ 보안 기준 불명확
  - 데이터 분류 (공개/내부/기밀)?
  - 암호화 레벨 (AES-256?)?
  - 감시 법규 (GDPR? 국내법?)

□ 성능 목표 부실
  - "응답 시간 < 500ms" — p50, p95, p99?
  - "1000 QPS" — 동시 사용자는?
  - 캐시 기준 불명

□ 배포 전략 미정
  - 프로덕션 환경은? (AWS? On-prem?)
  - SLA "99.5%" — 유지 가능?
  - 모니터링 도구 (DataDog) — 예산 반영됐나?
```

#### 위험도
🟠 **Medium** — 4~5개월 후지만 지금부터 인프라 준비 필요

### 4. **통합 테스트 기준의 불명확성**

#### 현황 (Phase 2)
- 목표: "25개 테스트 케이스 80% 이상 통과" (20/25)
- 현황: 1/25 (2026-05-19 기준)

#### 문제점
```
□ "통과"의 정의가 모호
  - 정확도만 보나? (precision/recall?)
  - 응답 속도도 포함? (avg/max/p95?)
  - 할루시네이션 없음도 확인? (수동?)

□ 25개 케이스가 대표성 있나?
  - 어떻게 선정? (도메인별? 의도별?)
  - 실제 사용자 질문과 매핑됐나?

□ 테스트 데이터는 고정?
  - 온톨로지 데이터가 바뀌면 재실행?
  - 예정: "온톨로지 데이터 보완" — 그럼 테스트 재실행?
```

#### 위험도
🔴 **High** — 20/25 목표가 "금주" (2026-05-18)인데 불명확

### 5. **버전 관리 & 롤백 전략 부재**

#### 현황

  - 데이터 검증 프로세스?
  - 롤백 계획?

□ 버전 호환성
  - API 버전 (v1, v2?) 관리?
  - 클라이언트 호환성 깨지면?

□ 데이터 스키마 진화
  - 온톨로지 타입 추가 시 기존 데이터는?
  - 마이그레이션 스크립트?

🟠 **Medium** — 장기(1년+) 이슈지만 구조가 필요

## 🚨 v3 지속 vs v4 신규 결정

### 현재 상황 평가

#### v3의 현재 상태
- **완성도**: ~42% (Phase 1 완료, Phase 2 진행 중)
- **안정성**: 단위 테스트 29/29 통과 ✅
- **확장성**: 아키텍처 설계 양호 ✅
- **문제점**: 
  - Phase 3이 부실 (가장 중요한데!)
  - 도메인 확장 계획 미흡
  - 운영 준비 미흡

#### v4 신규의 고려사항
- **이점**: 깔끔한 시작, 새 기술 도입 (e.g., Python 3.13, FastAPI 최신)
- **비용**: 6개월 개발 손실, 마이그레이션 비용
- **위험**: 현재 Phase 2 진행 중 중단 위험

---

### 🎯 **권장 방향: v3 지속 + Phase 3 보완**

#### 근거
1. **Phase 1~2가 충분히 진행됨** (42% 완성)
   - 롤백 비용 > 보완 비용
   
2. **아키텍처가 건전함**
   - JSON → PostgreSQL 마이그레이션 경로 설계됨
   - 멀티테넌트 지원 설계 명확
   
3. **v4는 나중에 가능**
   - Phase 5 (운영형 하드닝)에서 Python 버전업 + 정리 가능
   - 장기 전략: Python 3.13, FastAPI 0.115+ 도입

#### 단, 즉시 시작해야 할 3가지

```
1️⃣ Phase 3 요구사항 수집 (이번주)
   - 비즈니스 액션 정의서 (AI바우처)
   - 상태 기계 설계
   - Write-back 대상 확인

2️⃣ Phase 4 도메인별 온톨로지 설계 (다음주)
   - 조선 도메인 (우선순위 High)
   - 제조, 구매 도메인 (스케치)
   - 비용 추정

3️⃣ Phase 5 운영 준비 로드맵 (5월 말)
   - 인프라 선정 (AWS 또는 On-prem?)
   - 성능 기준 상세화
   - 배포 전략 (Docker/K8s) 사전 구성

예상 추가 시간: 3~4주
```
