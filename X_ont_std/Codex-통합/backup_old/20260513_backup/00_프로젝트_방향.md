## 1. 결론

기존 `claud_통합`을 직접 확장하지 않고, `Codex-통합`을 별도 프로젝트로 두는 방향이 적절하다.

이유:
- `claud_통합`은 이미 교육/데모/검증 중심으로 안정화되어 있다.
- 기존 구조에 온톨로지 관리 기능을 크게 얹으면 워크플로우 데모와 온톨로지 플랫폼 실험이 섞인다.
- 팔란티어식 유연한 온톨로지를 목표로 하면 데이터 모델, API, UI의 중심축이 달라진다.
- 새 프로젝트는 처음부터 객체 타입, 관계 타입, 액션 타입, 정책, 뷰 구성을 설정/관리 가능한 구조로 잡는 편이 낫다.

## 2. 기존 claud_통합의 역할

`claud_통합`은 참조 구현으로 사용한다.

참조할 것:
- FastAPI + Next.js 분리 구조
- `AppContext` 중심 서비스 조립 방식
- `OntologyService`, `PolicyEngine`, `WorkflowService`, `RAGService`, `AuditService`의 경계
- React Flow 기반 `WorkflowGraph`
- SSE 기반 그래프 실행
- `pytest`, `eval.scenarios`, `evaluate.py`, Playwright 검증 흐름

그대로 가져오지 않을 것:
- `Customer`, `Order`, `Product` 하드코딩 온톨로지
- `PLACED_ORDER`, `ORDER_CONTAINS_PRODUCT` 전용 관계 조립
- `get_order_context()` 중심 도메인 고정 컨텍스트
- 코드 기반 정책/액션 정의
