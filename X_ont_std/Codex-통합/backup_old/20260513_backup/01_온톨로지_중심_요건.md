# 온톨로지 중심 요건

## 1. 목표

사용자가 코드 수정 없이 업무 객체, 속성, 관계, 액션을 정의하고, 그 정의가 화면/검색/AI/워크플로우에 반영되는 구조를 만든다.

## 2. 핵심 원칙

- 온톨로지 정의는 코드가 아니라 설정/저장소에 둔다.
- 객체 타입과 관계 타입은 화면에서 조회 가능해야 한다.
- 관계 인스턴스를 사용자가 추가할 수 있어야 한다.
- AI 질의는 하드코딩된 `Order` 컨텍스트가 아니라 범용 객체 컨텍스트를 사용해야 한다.
- 워크플로우 그래프는 Action Type을 노드로 사용할 수 있어야 한다.
- 모든 변경은 검증되고 감사 로그에 남아야 한다.

## 3. 데이터 모델

### Object Type

```json
{
  "name": "Customer",
  "display_name": "고객",
  "id_prefix": "C",
  "properties": [
    {"name": "name", "type": "string", "required": true, "searchable": true},
    {"name": "region", "type": "string", "required": true},
    {"name": "risk_tier", "type": "enum", "values": ["Low", "Medium", "High"], "sensitive": true}
  ]
}
```

### Relationship Type

```json
{
  "name": "PLACED_ORDER",
  "display_name": "주문함",
  "source_type": "Customer",
  "target_type": "Order",
  "cardinality": "one_to_many"
}
```

### Relationship Instance

```json
{
  "relationship_type": "PLACED_ORDER",
  "source_id": "C001",
  "target_id": "O001",
  "properties": {}
}
```

### Action Type

```json
{
  "name": "ApproveOrder",
  "display_name": "주문 승인",
  "target_type": "Order",
  "parameters": [
    {"name": "comment", "type": "string", "required": false}
  ],
  "preconditions": [
    {"type": "status_in", "values": ["Submitted", "Review"]},
    {"type": "policy", "name": "can_approve_order"}
  ],
  "effects": [
    {"type": "set_property", "property": "status", "value": "Approved"}
  ]
}
```

## 4. 필수 기능

### 온톨로지 스키마 조회

- 객체 타입 목록
- 속성 목록
- 관계 타입 목록
- 액션 타입 목록
- 권한 규칙 요약

### 객체/관계 탐색

- 객체 타입별 목록 조회
- 객체 상세 조회
- incoming/outgoing 관계 조회
- 관계 그래프 표시
- 관련 문서 표시
- 가능한 액션 표시

### 관계 관리

- 관계 타입 선택
- source 객체 선택
- target 객체 선택
- 관계 속성 입력
- 관계 생성
- 관계 삭제

### AI 질의

- 질문에서 객체 ID 추출
- 범용 객체 컨텍스트 생성
- 관계를 따라 관련 객체 수집
- 권한/마스킹 적용
- BM25/RAG 문서 검색
- 답변과 근거 표시

## 5. 완료 기준

- `Customer`, `Order`, `Product`를 JSON 스키마에서 로딩한다.
- `PLACED_ORDER`, `ORDER_CONTAINS_PRODUCT`를 JSON 스키마에서 로딩한다.
- 코드 수정 없이 새 관계 타입을 추가할 수 있다.
- 객체 상세 화면에서 관계가 자동 표시된다.
- AI 질의가 범용 객체 컨텍스트를 사용한다.
