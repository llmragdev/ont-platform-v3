## 상세 테스트 결과

### 🧪 시나리오 1: 다중 워커 중복 실행률 검증
* **목표**: `FOR UPDATE SKIP LOCKED` 구문 도입 후 다중 워커 가동 시 동일 아이템의 중복 실행 방지 검증.
* **테스트 조건**: 100개 PENDING 아이템 적재, 2개 워커 병렬 가동 (50ms 대기 간격, 10회 반복).
* **결과 로그**:
  ```
  [Scenario 1] Multiple Workers Duplicate Execution Rate Verification...
  -> Total Processed: 100
  -> Unique Processed: 100
  -> Duplicate Processed: 0
  -> Duplicate Execution Rate: 0.00%
  [PASS] Scenario 1: Duplicate execution rate is 0%
  ```
* **분석**: 워커가 `with_for_update(skip_locked=True)`로 조회를 수행하여, 동일 시점에 경쟁하는 워커들이 잠겨있지 않은 고유 행만 선점해 처리하여 중복 처리가 완벽히 방지되었습니다.

### 🧪 시나리오 2: 지수 백오프 준수율 검증
* **목표**: API 실패 시 다음 재시도 예정 시각(`next_retry_at`)의 지수 백오프 승수 계산 적합성 및 4회 실패 시 DLQ 격리 동작 확인.
* **테스트 조건**: 무조건 실패하는 SAP API Mock, 60초 기본 딜레이, 2배 백오프 승수 조건.
* **결과 로그**:
  ```
  [Scenario 2] Exponential Backoff Compliance Verification...
  -> Attempt 1 Next Retry: 2026-05-25 05:20:20.629652 (Delay: 120.0s)
  -> Attempt 2 Next Retry: 2026-05-25 05:22:20.633038 (Delay: 240.0s)
  -> Attempt 3 Next Retry: 2026-05-25 05:26:20.634675 (Delay: 480.0s)
  -> Attempt 4 Final Status: DLQ
  [PASS] Scenario 2: Exponential backoff compliant at 100%
  ```
* **분석**: 실패 회수가 증가함에 따라 지연 시각이 지수(120초 → 240초 → 480초)로 완벽하게 누적되었고, `max_retries`에 도달한 4회차에는 정상적으로 `DLQ` 상태 및 격리 시각/사유가 기록되었습니다.

### 🧪 시나리오 3: 트랜잭션 유실률 검증
* **목표**: 워커 루프 도중 불시의 프로세스 크래시 시, 개별 커밋 구조로 처리 완료 건의 상태 저장이 완벽히 보장되는지 확인.
* **테스트 조건**: 20개 PENDING 아이템, 10번째 아이템 처리 시 `os._exit(1)`로 인위적 강제 종료 프로세스 구동.
* **결과 로그**:
  ```
  [Scenario 3] Transaction Loss Rate Verification...
  -> Post-Crash CONFIRMED items count: 10
  -> Post-Crash PENDING items count: 10
  [PASS] Scenario 3: Transaction loss rate is 0%
  ```
* **분석**: 크래시 이전 성공한 10개(0~9)의 트랜잭션이 루프 완료와 무관하게 즉각 DB에 반영되어 유실률 0%를 기록했으며, 나머지 10개는 정상적으로 `PENDING`으로 복구되었습니다.

### 🧪 시나리오 4: 성능 메트릭 측정
* **목표**: 대량 500개 대기 큐 항목을 배치 처리할 때의 처리량(Throughput) 및 단건 지연(Latency) 속도 측정.
* **테스트 조건**: SQLite 인메모리 조건 하 500개 PENDING 아이템 일괄 처리 루프 시간 계측.
* **결과 로그**:
  ```
  [Scenario 4] Performance Metrics Calculation (500 items)...
  -> Processed Count: 500
  -> Total Elapsed Time: 0.44s
  -> Throughput: 68140.86 items/min
  -> Average Latency: 0.88 ms
  [PASS] Scenario 4: Target performance metrics met
  ```
* **분석**: 분당 68,140개 아이템 처리 속도 및 평균 0.88ms의 레이턴시를 달성하여 성공 조건(처리량 ≥ 50/분, 지연 ≤ 1000ms)을 압도적으로 달성하였습니다.

## 권장사항

1. **상용 DB 벤치마킹 연계**: 본 검증은 SQLite 인메모리 환경에서 수행되었습니다. 실제 PostgreSQL(Neon Cloud) 환경에서는 네트워크 지연 및 DB 락킹 메커니즘으로 인해 단건 Latency가 증가할 수 있으므로, PostgreSQL 환경에서 추가 프로파일링을 진행하는 것을 권장합니다.
2. **DLQ 모니터링 경보**: DLQ 상태로 격리되는 항목은 외부 수신 시스템 장애가 해소된 후 Replay되어야 하므로, DLQ 전환 건수 누적 시 관리자 대시보드 경보(Alert) 시스템을 도입할 것을 제안합니다.
