### 3. 아키텍처 영향

**WriteBackWorker 처리 흐름**:
```
PENDING 조회 (FOR UPDATE SKIP LOCKED + 시간 필터)
    ↓
개별 아이템 처리
    ├─ 성공 → CONFIRMED 상태 (즉시 커밋)
    ├─ TimeoutError
    │   ├─ retry_count < MAX_RETRIES → PENDING 유지 + next_retry_at 설정 (즉시 커밋)
    │   └─ retry_count >= MAX_RETRIES → DLQ 격리 (즉시 커밋)
    └─ 기타 예외 → DLQ 격리 (즉시 커밋)

DLQ 모니터링 → Replay API → PENDING 복구
```

## 🔧 기술 규격

### 모델 확장
```python
# WriteBackQueue 모델 추가 필드
dlq_reason: Text        # DLQ 이유
dlq_at: DateTime        # DLQ 전환 시간
next_retry_at: DateTime # 다음 재시도 시간

# Status 제약 업데이트
status IN ('PENDING', 'SENT', 'CONFIRMED', 'FAILED', 'DLQ')
```

### API 스펙
| 엔드포인트 | 메서드 | 목적 | 응답 |
|-----------|--------|------|------|
| `/api/writeback/dlq/items` | GET | DLQ 목록 | `{items: [...], count: int}` |
| `/api/writeback/dlq/items/{id}` | GET | DLQ 상세 | `{id, payload, dlq_reason, ...}` |
| `/api/writeback/replay/{id}` | POST | Replay | `{status: "replayed", queue_id}` |
| `/api/writeback/statistics` | GET | 통계 | `{pending, confirmed, dlq, failed}` |

### 지수 백오프 공식
```
delay_seconds = INITIAL_RETRY_DELAY * (RETRY_BACKOFF_MULTIPLIER ^ retry_count)
next_retry_at = now + timedelta(seconds=delay_seconds)

예시 (INITIAL_DELAY=60s, MULTIPLIER=2):
- retry_count=1: 60 * 2^1 = 120초 (2분)
- retry_count=2: 60 * 2^2 = 240초 (4분)
- retry_count=3: 60 * 2^3 = 480초 (8분) → DLQ
```
