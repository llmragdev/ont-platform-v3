## 🔍 **겹치는 부분 vs 다른 부분**

### 겹치는 부분 (❌ 중복)

```
1. Snowflake 정답 = "관련 없습니다"
   PHASE 6: 정의함 (정답표에 기록)
   PHASE 7: 구현함 (시스템이 자동 반환)
   → 결과적으로 같은 정답

2. 카테고리 검증
   PHASE 6: 범위 외 질문 "감지" (평가 시)
   PHASE 7: 범위 외 질문 "차단" (서빙 시)
   → 같은 로직이지만 다른 시점

3. "근거 없으면 답하지 않기"
   PHASE 6: 평가 기준으로 반영
   PHASE 7: EvidenceGate로 강제
   → 같은 정책이지만 다른 실행 위치
```

### 다른 부분 (✅ 구분됨)

```
1. PHASE 6만:
   - Stage 3 대화형 CLI (사용자가 정답 입력)
   - 영향도 분석 (변경점 추적)
   - 평가 재실행 (개선도 검증)
   
2. PHASE 7만:
   - EvidenceGate 모듈 (실시간 검증)
   - Question Analyzer (카테고리 자동 분류)
   - Grounding Verifier (근거 검증)
   - Answer Policy (정책 기반 판정)
   
3. 보정 루프:
   - PHASE 6: 정답 → 메타데이터 변경
   - PHASE 7: 정답 → 시스템 로직 변경
```

## 📍 **실제 동작 흐름**

```

  ↓
Retrieval: RAG 관련 문서 검색
  ↓
LLM: "RAG는 검색을..." 생성
  ↓
Evaluation:
  expected: "관련 없습니다" (PHASE 6에서 정의)
  actual: "RAG는..."
  score: 0% (불일치)
  
결과: 평가 상 오류 감지 ✓ (하지만 시스템은 여전히 잘못 답변)

```

```
  ↓

  question_category = Snowflake
  retrieved_categories = [Ontology, NLP]
  → category_mismatch = TRUE
  → answer_allowed = FALSE
  ↓
Answer Policy (← NEW):
  "관련 없습니다" 자동 반환
  (LLM 호출 차단)
  
결과: 
  expected: "관련 없습니다"
  actual: "관련 없습니다"
  score: 100% (일치)
  
시스템이 올바른 답변 ✓
```

## 🚫 **겹침 문제: 구체적 분석**

### 문제 1: 정답 정의 vs 구현

```
PHASE 6 (정의):
  "Snowflake 질문에 대해 이렇게 정답하면 맞다"
  → evaluation_config.json에 기록:
     {
       "problem_id": "STD-S-01",
       "expected_answer": "해당 카테고리 문서와 관련이 없습니다"
     }

PHASE 7 (구현):
  "시스템이 Snowflake 질문을 이렇게 처리한다"
  → EvidenceGate에서 자동 실행:
     if category_mismatch:
       return "해당 카테고리 문서와 관련이 없습니다"

겹침? NO
  PHASE 6: 정답표에 뭐가 정답인지 기록
  PHASE 7: 시스템이 그 정답을 자동으로 생성
  (정의와 구현의 차이)
```

### 문제 2: 평가 vs 서빙

```
PHASE 6 (평가):
  Q: "Snowflake RAG에서..."
  A (시스템): "RAG는..."
  E (정답): "관련 없습니다" ← 정의함
  → 평가: 틀림 (0%)
  → 목적: 평가 데이터 정확화

PHASE 7 (서빙):
  Q: "Snowflake RAG에서..."
  A (시스템): EvidenceGate 검증
           → "관련 없습니다" ← 자동 생성
  → 실제 사용자가 받는 답변
  → 목적: 시스템 동작 개선

겹침? 약간 있음
  같은 최종 답변 ("관련 없습니다")
  하지만 목적과 시점이 다름
```

## ⚠️ **겹침이 생길 수 있는 실수**

### 실수 1: "PHASE 6이면 충분하지 않나?"

```
❌ 잘못된 생각:
   PHASE 6에서 STD-S 정답을 "관련 없음"으로 정의했으니
   → 평가 정확도 개선 완료
   → 시스템은 여전히 잘못된 답변

✅ 맞는 생각:
   PHASE 6: 평가 기준 정의 (무엇)
   PHASE 7: 시스템 구현 (어떻게)
   → 둘 다 필요
```

### 실수 2: "PHASE 7이면 PHASE 6 불필요?"

```
❌ 잘못된 생각:
   EvidenceGate를 만들면
   → 자동으로 "관련 없음" 반환
   → PHASE 6 불필요

✅ 맞는 생각:
   PHASE 6: 정답 정의 (평가 기준 명확화)
   PHASE 7: 시스템 구현 (실제 동작)
   → PHASE 6이 먼저 필요
   → PHASE 7이 그걸 구현
```

### 실수 3: "둘 다 동일한 코드인가?"

```
❌ 잘못된 생각:
   PHASE 6과 PHASE 7에서
   같은 "관련 없습니다" 문구를 쓰므로
   → 코드 중복

✅ 맞는 생각:
   PHASE 6: evaluation_config.json에 저장
           {expected_answer: "관련 없습니다"}
           
   PHASE 7: evidence_gate.py에 구현
           if category_mismatch:
             return "관련 없습니다"
           
   → 저장소 / 타이밍 / 목적 다름
   → 중복이 아니라 상호 보완
```

## 🎯 **명확한 역할 분담**

### PHASE 6의 역할

```
"평가 시스템을 정확하게 만든다"

1. 문제 정의
   → Snowflake 범위 외 기술이다
   → 따라서 정답은 "관련 없습니다"

2. 평가 기준 설정
   → STD-S-01~08의 기대값 = "관련 없습니다"

3. 평가 검증
   → 실제 시스템 답변 vs 기대값 비교
   → 오류 감지

결과: 평가가 정확해짐 (신뢰도 ↑)
```

### PHASE 7의 역할

```
"실제 QA 시스템을 개선한다"

1. 문제 해결
   → EvidenceGate로 범위 외 질문 감지
   → "관련 없습니다" 자동 반환

2. 로직 구현
   → 카테고리 검증
   → LLM 호출 제어

3. 성능 향상
   → 실제 서빙 개선
   → 사용자가 받는 답변 품질 ↑

결과: 시스템이 올바르게 작동함 (신뢰도 ↑)
```

## 🎓 **정리**

### 겹침 여부: **겹치지 않음 (다른 계층)**

| 항목 | PHASE 6 | PHASE 7 |
|---|---|---|
| 계층 | 평가 (Offline) | 서빙 (Online) |
| 목적 | 정답 정의 | 시스템 구현 |
| 변경점 | 평가 기준 | 로직 및 정책 |
| 검증 | 평가 점수 | 실제 답변 |
| 의존성 | 독립적 | PHASE 6 결과 의존 |

### 권장사항: **순차적 실행**

```
1. ✅ PHASE 6 완료 (정답 정의)
   → Snowflake 정답 = "관련 없습니다"
   
2. → PHASE 7 시작 (시스템 구현)
   → EvidenceGate 추가
   → 정책 기반 답변
   
3. 최종 결과
   → 평가도 정확, 시스템도 올바름
```
