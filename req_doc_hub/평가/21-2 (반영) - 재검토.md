# 21-2 반영 내역 재검토

## 1. 재검토 기준

검토 대상:
- 반영 보고서: `21-2 (반영).md`
- 원 평가 문서: `21 -2 anti_평가 .md`
- 실제 소스: `src_anti`

검토 방식:
- 테스트 실행 결과는 판단 기준에서 제외했습니다.
- `21-2 (반영).md`에 적힌 조치 내용이 실제 소스 파일에 반영되어 있는지 확인했습니다.
- “반영됨”, “부분 반영”, “미흡/과장”으로 나누어 판단했습니다.

## 2. 전체 판단

`21-2 (반영).md`의 반영 보고서는 **큰 방향은 맞지만, 표현이 실제 구현보다 많이 강합니다.**

실제로 `src_anti`에는 다음 개선이 들어가 있습니다.

- 백엔드 서비스 파일 분리
- `requirements.txt` 추가
- 객체 ID 탐지와 관계 검증 추가
- 검색 점수 기반 문서 검색 추가
- 워크플로우 상태 전이 테이블 추가
- 감사 로그 저장소와 조회 API 추가
- 프론트엔드 공통 API 호출 함수 추가
- 하드코딩된 API 주소 제거
- 반응형 CSS 일부 추가

다만 다음 표현은 실제 소스 기준으로 과장입니다.

- “명시적 객체 및 관계 관리”
- “BM25 스코어링 도입”
- “검색 기반 RAG 파이프라인 구현”
- “RBAC 및 민감 데이터 마스킹 구현”
- “비즈니스 로직을 기능별 서비스 레이어로 완전히 분리”
- “전 구간 이벤트 로깅”

현재 구현은 `src_codex` 수준의 운영형 구조라기보다는, 기존 `src_anti` MVP에 운영형 요소를 **얇게 추가한 개선판**에 가깝습니다.

## 3. 항목별 재검토

### 3.1 실행 환경 미비

보고서 주장:
- `backend/requirements.txt` 생성
- `README.md` 가이드 보완

실제 확인:
- `src_anti/backend/requirements.txt`가 존재합니다.
- FastAPI, Uvicorn, Pydantic, Pytest, HTTPX 등이 명시되어 있습니다.
- `src_anti/README.md`에도 `pip install -r requirements.txt` 실행 절차가 추가되어 있습니다.

판단:
- **반영됨**

보완 의견:
- 현재 문서에는 가상환경 활성화 예시가 Unix와 Windows를 함께 적고 있어 교육용으로는 충분합니다.
- 다만 설치 위치가 `src_anti/backend` 기준이라는 점을 더 강조하면 초보자가 덜 헷갈립니다.

### 3.2 온톨로지 모델링

보고서 주장:
- `models.py`, `ontology.py`를 통해 명시적 객체 및 관계 관리

실제 확인:
- `models.py`에는 `Customer`, `Order`, `Product`, `Document`, `AskRequest`, `WorkflowRequest`, `AskResponse`, `AuditEvent` 같은 Pydantic DTO가 있습니다.
- `ontology.py`에는 `detect_objects`, `verify_relationship`, `get_order_context`가 있습니다.
- 그러나 `ObjectType`, `ObjectInstance`, `RelationshipDefinition`, `RelationshipInstance`, `ActionDefinition` 같은 명시적 온톨로지 모델은 없습니다.
- 관계도 별도 관계 인스턴스로 관리되지 않고, `order["customerId"]`, `order["productIds"]`를 직접 따라갑니다.

판단:
- **부분 반영**

보완 의견:
- “명시적 객체 및 관계 관리”라고 하기에는 부족합니다.
- 더 정확한 표현은 “주문-고객-제품 컨텍스트 조회와 간단한 관계 검증을 서비스로 분리”입니다.

### 3.3 관계 검증 부족

보고서 주장:
- Regex 기반 ID 추출
- `verify_relationship` 로직 추가

실제 확인:
- `ontology.py`의 `detect_objects()`가 `C\d{3}`, `O\d{3}`, `P\d{3}`, `D\d{3}` 패턴을 탐지합니다.
- `verify_relationship(customer_id, order_id)`가 주문의 `customerId`와 고객 ID를 비교합니다.
- `rag.py`에서 질문 속 고객 ID와 주문 ID가 함께 있으면 관계 검증을 수행합니다.

판단:
- **반영됨**

보완 의견:
- 관계 불일치가 HTTP 오류 코드로 반환되지는 않습니다.
- 현재는 정상 응답 안의 답변 문장으로 “관계를 확인할 수 없습니다”라고 말하는 방식입니다.
- 원 평가의 `RELATION_MISMATCH` 오류 반환 수준까지는 아닙니다.

### 3.4 BM25/RAG 미흡

보고서 주장:
- `SearchService`에 BM25 스코어링 도입
- 검색 기반 RAG 파이프라인 구현

실제 확인:
- `search.py`에 토크나이저와 문서 점수 계산이 추가되어 있습니다.
- 하지만 구현은 실제 BM25가 아니라, 질의 토큰이 문서 토큰에 포함되면 등장 횟수를 더하는 단순 count 기반 점수입니다.
- BM25의 핵심인 IDF, 문서 길이 보정, `k1`, `b` 파라미터는 없습니다.
- `rag.py`는 검색 결과를 evidence로 반환하지만, 프롬프트 생성이나 실제 LLM 호출은 없습니다.
- 답변 생성은 여전히 휴리스틱 규칙 기반입니다.

판단:
- **부분 반영**

보완 의견:
- “BM25 스코어링”이라는 표현은 부정확합니다.
- “간단한 토큰 매칭 기반 문서 검색”으로 낮춰 쓰는 것이 맞습니다.
- “RAG 파이프라인”도 엄밀히는 검색 결과를 답변 근거로 첨부하는 수준입니다.

### 3.5 워크플로우 검증

보고서 주장:
- `WorkflowService`에 상태 전이 테이블 적용

실제 확인:
- `workflow.py`에 `TRANSITIONS` 딕셔너리가 있습니다.
- `Submitted -> ApproveOrder -> Approved`
- `Submitted -> RejectOrder -> Rejected`
- `Submitted -> HoldOrder -> Review`
- `Review -> ApproveOrder -> Approved`
- `Review -> RejectOrder -> Rejected`
- 허용되지 않는 액션은 실패 메시지를 반환합니다.

판단:
- **반영됨**

보완 의견:
- 상태 전이 검증 자체는 들어갔습니다.
- 다만 액션 권한과 상태 전이가 느슨하게 분리되어 있어, 운영형 워크플로우 엔진이라고 부르기에는 아직 단순합니다.

### 3.6 권한/거버넌스

보고서 주장:
- `PolicyService` 도입
- RBAC 및 민감 데이터 마스킹 구현

실제 확인:
- `policy.py`에 `ROLES`와 `check_permission()`이 있습니다.
- `main.py`에는 `CURRENT_USER = "AdminUser"`, `CURRENT_ROLE = "Admin"`이 하드코딩되어 있습니다.
- 사용자 선택, 인증, 요청별 사용자 컨텍스트, 객체별 권한 필터링은 없습니다.
- 마스킹 로직은 `get_customers()`에서 `riskTier`에 대해 조건부로 적용되지만, 현재 역할이 항상 `Admin`이라 실제로는 마스킹이 동작하지 않습니다.
- 문서 권한 필터링도 없습니다.

판단:
- **부분 반영, 보고서 표현은 과장**

보완 의견:
- “RBAC 구현”보다는 “역할/권한 규칙의 기초 골격 추가”가 정확합니다.
- “민감 데이터 마스킹 구현”도 현재는 예시 수준입니다.
- 운영형 권한 체계로 보려면 최소한 요청별 사용자 식별, 객체 권한, 문서 권한, 액션 권한을 일관되게 적용해야 합니다.

### 3.7 감사 로그

보고서 주장:
- `AuditService`를 통한 전 구간 이벤트 로깅
- 조회 API 추가

실제 확인:
- `audit.py`에 `AuditService.log_event()`가 있습니다.
- `data.py`에 `audit_events` 저장소가 있습니다.
- `main.py`에 `/api/audit/events` API가 있습니다.
- 고객 목록 조회, 주문 목록 조회, 주문 컨텍스트 조회, AI 질의, 워크플로우 실행/실패, 시스템 리셋에 로그가 남습니다.

판단:
- **부분 반영**

보완 의견:
- 감사 로그 기능은 실제로 추가되었습니다.
- 하지만 “전 구간 이벤트 로깅”은 과장입니다.
- 예를 들어 검색 단계, 관계 검증 실패, 문서 검색 결과, 권한 필터링 상세, 객체별 접근 거부 상세까지 모두 구조화되어 남는 수준은 아닙니다.

### 3.8 API 오류 처리

보고서 주장:
- `app.js`에 공통 `apiCall` 래퍼 및 에러 UI 표시 로직 추가

실제 확인:
- `app.js`에 `apiCall(endpoint, options)` 함수가 있습니다.
- `response.ok`를 확인하고 오류 메시지를 throw합니다.
- `showError()`로 화면 상단에 오류 메시지를 표시합니다.
- AI 질의 실패와 워크플로우 실패도 사용자 메시지로 표시됩니다.

판단:
- **반영됨**

보완 의견:
- `updateContext()` 일부는 아직 직접 `fetch()`를 사용합니다.
- 공통 처리 일관성을 위해 이 부분도 `apiCall()`로 통일하면 더 좋습니다.

### 3.9 하드코딩된 주소

보고서 주장:
- `window.location.origin` 기반 상대 경로 전환

실제 확인:
- `app.js`의 `API_BASE`가 `${window.location.origin}/api`로 바뀌어 있습니다.

판단:
- **반영됨**

보완 의견:
- `index.html`을 파일로 직접 열면 `window.location.origin`이 `file://` 기준이 되어 API 호출이 깨질 수 있습니다.
- README에서 프론트엔드도 같은 서버에서 서빙하거나 Live Server 사용 시 API 경로 설정을 명확히 안내해야 합니다.

### 3.10 테스트 오염

보고서 주장:
- `/api/system/reset` 엔드포인트
- fixture 리셋 로직 적용

실제 확인:
- `main.py`에 `/api/system/reset`이 있습니다.
- `test_main.py`에 `reset_state()` fixture가 있고, 각 테스트 전에 reset API를 호출합니다.

판단:
- **반영됨**

보완 의견:
- 전역 `repo` 자체는 그대로입니다.
- 더 운영형으로 가려면 FastAPI dependency로 repository를 주입받는 구조가 좋습니다.

### 3.11 프론트엔드 자동 테스트

보고서 주장:
- 향후 과제로 남김

실제 확인:
- Playwright나 Selenium 테스트는 없습니다.

판단:
- **미반영, 보고서와 일치**

보완 의견:
- 보고서가 이 항목을 향후 과제로 둔 것은 적절합니다.

### 3.12 반응형 UI

보고서 주장:
- CSS Media Queries를 통한 모바일/태블릿 대응 레이아웃 구현

실제 확인:
- `style.css`에 `@media (max-width: 1200px)`, `992px`, `768px` 규칙이 있습니다.
- 좁은 화면에서는 grid를 flex column으로 바꾸고 sidebar/context 배치를 조정합니다.
- `body`의 `overflow`도 모바일 구간에서 `auto`로 바뀝니다.

판단:
- **반영됨**

보완 의견:
- 기본 디자인은 여전히 카드/패널 중심이고, 일부 테이블은 좁은 화면에서 넘칠 수 있습니다.
- 그래도 원 평가의 “고정 3열 레이아웃” 문제는 분명히 개선되었습니다.

## 5. 최종 결론

`21-2 (반영).md`는 실제 반영 방향을 대체로 잘 짚고 있지만, 구현 수준을 설명하는 표현은 상당히 낙관적입니다.

소스 기준 최종 평가는 다음과 같습니다.

- 실행 환경 정리: **반영됨**
- 서비스 파일 분리: **부분 반영**
- 온톨로지 모델링: **부분 반영**
- 관계 검증: **반영됨**
- BM25/RAG: **부분 반영**
- 워크플로우 상태 전이: **반영됨**
- 권한/거버넌스: **부분 반영**
- 감사 로그: **부분 반영**
- 프론트엔드 오류 처리: **반영됨**
- API 주소 하드코딩 제거: **반영됨**
- 테스트 상태 초기화 구조: **반영됨**
- 반응형 UI: **반영됨**

따라서 `src_anti`는 평가 문서의 문제를 꽤 많이 보완했지만, 아직 “운영형 아키텍처 구현 완료”라고 보기보다는 **운영형 요소를 추가한 교육용 개선판**으로 보는 것이 정확합니다.
