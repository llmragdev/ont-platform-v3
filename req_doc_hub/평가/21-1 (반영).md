### 2.2 데이터 영속성 레이어 도입

관련 평가 항목:
- `4.3 데이터 영속성 레이어 도입`

조치:

- JSON 저장 시 임시 파일에 먼저 쓰고 교체하는 방식으로 저장 안정성을 높였습니다.

### 2.3 운영 환경 전환 가능성 강화

관련 평가 항목:
- 운영 확장성
- 실제 DB/LLM 연동으로 전환 가능한 구조

조치:
- `AppContext`가 Repository를 주입받을 수 있도록 변경했습니다.
- `ONTOLOGY_DATA_PATH` 환경변수가 있으면 JSON 파일 저장소를 사용하도록 했습니다.
- 환경변수가 없으면 기존처럼 메모리 저장소를 사용하도록 했습니다.

변경 파일:
- `src_codex/backend/app_context.py`

- `src_codex/backend/ontology.py`

## 3. 주요 변경 파일 설명

### 3.1 `src_codex/backend/repository.py`

새로 추가한 데이터 저장소 계층입니다.

- `DataRepository`: 저장소 인터페이스 역할
- `InMemoryDataRepository`: 기존 데모 동작을 유지하는 메모리 저장소
- `JsonFileDataRepository`: JSON 파일에 데이터를 저장하고 다시 로드하는 파일 기반 저장소

이 변경으로 나중에 `PostgreSQL`, `Snowflake`, 기타 DB 저장소를 붙일 때 `AppContext`와 비즈니스 로직을 크게 흔들지 않고 Repository 구현만 교체할 수 있습니다.

### 3.2 `src_codex/backend/app_context.py`

기존에는 `fresh_raw_data()`를 직접 호출해 매번 메모리 데이터를 만들었습니다.

반영 후에는 다음 흐름으로 변경했습니다.

1. `ONTOLOGY_DATA_PATH` 환경변수가 있으면 `JsonFileDataRepository` 사용
2. 환경변수가 없으면 `InMemoryDataRepository` 사용
3. 외부에서 Repository를 직접 주입하면 해당 Repository 사용

또한 질문 처리 실패 시에도 `ASK_FAILED` 감사 로그를 남기도록 보강했습니다.

### 3.3 `src_codex/backend/ontology.py`

`OntologyService`가 상태 변경을 감지할 수 있도록 `on_change` 콜백을 받게 했습니다.

특히 `update_order_status()`에서 주문 상태를 변경한 뒤 저장 콜백을 호출하므로, 워크플로우 액션 실행 결과가 JSON 저장소에 반영됩니다.

### 3.4 `src_codex/tests/test_services.py`

운영 보강 사항이 실제로 동작하는지 테스트를 추가했습니다.

- 알 수 없는 주문 질문 시 `ASK_FAILED` 로그가 남는지 확인
- JSON 저장소 사용 시 `ApproveOrder` 실행 후 새 `AppContext`에서도 주문 상태가 `Approved`로 유지되는지 확인

## 5. 사용 방법

기존처럼 실행하면 메모리 기반 데모로 동작합니다.

```powershell
python .\src_codex\server.py
```

JSON 파일에 상태를 저장하려면 다음처럼 환경변수를 지정한 뒤 실행합니다.

```powershell
$env:ONTOLOGY_DATA_PATH='E:\ontology_edu\src_codex\data\ontology-data.json'
python .\src_codex\server.py
```

이 모드에서는 워크플로우로 변경된 주문 상태가 JSON 파일에 저장됩니다.
