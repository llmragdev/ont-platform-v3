# RAG 평가와 운영 설계

## 1. 목표

RAG 시스템은 답변이 그럴듯하게 보인다고 해서 운영 가능한 것이 아닙니다. 검색이 맞는지, 객체 식별이 맞는지, 답변이 근거에 충실한지, 권한이 지켜졌는지 평가해야 합니다.

이 문서는 BM25/RAG/온톨로지 융합 시스템을 운영하기 위한 평가와 모니터링 설계를 정리합니다.

## 2. 평가 대상

평가 대상은 LLM 답변만이 아닙니다.

| 단계 | 평가 항목 |
| --- | --- |
| 질문 이해 | 객체 ID 추출, 의도 분류 |
| 온톨로지 조회 | 객체 존재 여부, 관계 검증 |
| 문서 검색 | 관련 문서 검색 여부 |
| 컨텍스트 구성 | 권한 필터링, 중복 제거 |
| 답변 생성 | 근거 충실도, 환각 여부 |
| 액션 연결 | 실행 가능 액션의 정확성 |

## 3. 테스트 질문 세트

운영 전에는 고정된 테스트 질문 세트를 만들어야 합니다.

예시:

```text
Q1. C001 고객의 O001 주문을 승인해도 될까?
Q2. C002 고객의 O002 주문은 왜 재무 승인이 필요해?
Q3. O999 주문 상태를 알려줘.
Q4. C001 고객과 O002 주문은 연결되어 있어?
Q5. 고위험 고객 주문을 자동 승인해도 돼?
```

각 질문에는 기대 결과를 붙입니다.

```text
Q4 기대 결과:
- C001과 O002의 관계가 맞지 않음을 알려야 한다.
- 임의로 답변을 생성하지 않아야 한다.
- 관련 액션을 제안하지 않아야 한다.
```

## 4. 객체 식별 평가

질문에서 객체를 잘 찾는지 평가합니다.

| 질문 | 기대 객체 | 평가 |
| --- | --- | --- |
| C001 고객의 O001 주문 | Customer C001, Order O001 | 정확 |
| Alpha의 최근 주문 | Customer 후보 필요 | 부분 |
| O999 주문 | 존재하지 않는 Order | 오류 처리 |

객체 식별 실패 시에는 LLM 답변을 바로 만들지 말고, 사용자에게 확인 질문을 던지는 것이 좋습니다.

## 5. 관계 검증 평가

온톨로지의 장점은 관계 검증입니다.

예시:

```text
질문: C001 고객의 O002 주문을 승인해도 될까?
실제 데이터: O002.customer_id = C002
기대 답변: C001과 O002는 연결되어 있지 않습니다.
```

이 케이스에서 문서 검색이나 LLM 답변으로 넘어가면 안 됩니다.

## 6. 검색 평가

검색 평가는 다음 지표를 사용할 수 있습니다.

| 지표 | 설명 |
| --- | --- |
| Recall@K | 정답 문서가 상위 K개 안에 있는가 |
| Precision@K | 상위 K개 문서 중 관련 문서 비율 |
| MRR | 첫 번째 관련 문서의 순위 |
| NDCG | 관련도 점수를 반영한 순위 품질 |

교육용으로는 먼저 `Recall@3`부터 보는 것이 좋습니다.

예시:

```text
질문: O001 주문 승인 기준은?
정답 문서: Order Approval Policy
검색 결과 Top 3에 포함되면 Recall@3 성공
```

## 7. 답변 평가

답변은 다음 기준으로 평가합니다.

| 기준 | 설명 |
| --- | --- |
| Groundedness | 제공된 근거에 기반하는가 |
| Correctness | 업무 규칙과 맞는가 |
| Completeness | 필요한 조건을 빠뜨리지 않았는가 |
| Refusal Quality | 근거 부족 시 적절히 거절하는가 |
| Action Safety | 위험한 액션을 잘못 제안하지 않는가 |

답변 평가 체크리스트:

```text
- 답변에 사용된 객체가 실제 존재하는가
- 질문 속 객체 간 관계가 검증되었는가
- 답변 근거 문서가 함께 표시되는가
- 근거 없는 계약 조건을 만들어내지 않는가
- 권한 없는 정보가 답변에 노출되지 않는가
```

## 8. 운영 로그

운영 중에는 다음 로그를 남깁니다.

```json
{
  "question_id": "Q-20260507-001",
  "actor": "analyst@example.com",
  "question": "C001 고객의 O001 주문을 승인해도 될까?",
  "detected_objects": ["C001", "O001"],
  "search_query": "C001 O001 approval policy low risk",
  "retrieved_documents": ["D001", "D002", "D003"],
  "answer_status": "ANSWERED",
  "latency_ms": 820,
  "occurred_at": "2026-05-07T10:40:00"
}
```

로그는 품질 개선, 비용 관리, 보안 감사에 모두 필요합니다.

## 9. 실패 유형

주요 실패 유형을 미리 분류합니다.

| 실패 유형 | 예시 대응 |
| --- | --- |
| 객체 없음 | 존재하지 않는 객체라고 안내 |
| 관계 불일치 | 객체 간 관계가 맞지 않다고 안내 |
| 문서 없음 | 근거 문서가 부족하다고 안내 |
| 권한 없음 | 접근 권한이 없다고 안내 |
| 액션 불가 | 현재 상태에서 실행 불가 안내 |
| LLM 오류 | 재시도 또는 규칙 기반 답변 사용 |

## 10. 모니터링 지표

운영 지표:

- 일별 질문 수
- 평균 응답 시간
- 검색 실패율
- 객체 식별 실패율
- 관계 검증 실패율
- 권한 거부 건수
- 액션 실행 성공률
- 사용자 피드백 점수
- LLM 호출 비용

## 11. 사용자 피드백

답변마다 피드백을 받을 수 있게 합니다.

```text
정확함
근거 부족
객체 인식 오류
검색 결과 부정확
액션 제안 부적절
```

피드백은 다음 개선에 사용합니다.

- 검색 질의 강화
- 문서 청크 수정
- 프롬프트 개선
- 객체 식별 로직 개선
- 권한 정책 보완

## 12. 배포 전 체크리스트

```text
- 테스트 질문 세트가 있는가
- 객체 식별 실패 케이스를 처리하는가
- 관계 불일치 케이스를 처리하는가
- 권한 없는 문서가 검색되지 않는가
- RAG 프롬프트에 민감 정보가 들어가지 않는가
- 답변에 근거 문서가 표시되는가
- 액션 실행 전 권한과 상태를 검증하는가
- 운영 로그가 남는가
```

## 13. 요약

RAG 운영 설계의 핵심은 LLM 답변만 평가하지 않는 것입니다. 객체 식별, 관계 검증, 문서 검색, 권한 필터링, 답변 생성, 액션 실행까지 전체 체인을 평가해야 합니다.
