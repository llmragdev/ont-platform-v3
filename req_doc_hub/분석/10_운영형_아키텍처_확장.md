# 운영형 아키텍처 확장

## 1. 목표

앞 장에서는 온톨로지, 워크플로우, BM25/RAG, Next.js 화면을 각각 구현했습니다. 이 문서는 교육용 구현을 실제 운영형 아키텍처로 확장할 때 필요한 설계를 정리합니다.

## 2. 전체 아키텍처

```text
Next.js 업무 화면
  -> API Gateway 또는 Backend API
  -> Auth / Policy Engine
  -> Ontology Service
  -> Workflow Service
  -> Search / RAG Service
  -> LLM Gateway
  -> Event / Audit Log
  -> Data Warehouse / Object Store
```

처음부터 모든 서비스를 분리할 필요는 없습니다. 단일 애플리케이션에서 시작하더라도 경계를 명확히 두는 것이 중요합니다.

## 3. 서비스 경계

| 서비스 | 책임 |
| --- | --- |
| Frontend | 업무 화면, 상태 표시, 사용자 액션 |
| Auth Service | 로그인, 사용자, 역할 |
| Policy Engine | 객체/속성/액션 권한 판단 |
| Ontology Service | 객체, 속성, 관계 조회 |
| Workflow Service | 상태 전이, 액션 실행, 이력 |
| Search Service | BM25, 벡터 검색, 하이브리드 검색 |
| RAG Service | 컨텍스트 구성, 프롬프트 생성 |
| LLM Gateway | 모델 호출, 비용/토큰 관리 |
| Audit Service | 로그, 감사, 모니터링 |

## 4. 요청 처리 흐름

사용자 질문 처리 흐름:

```text
1. 사용자가 질문 입력
2. Auth에서 사용자 확인
3. 질문에서 객체 후보 추출
4. Policy Engine에서 객체 접근 권한 확인
5. Ontology Service에서 객체와 관계 조회
6. Search Service에서 권한 필터링된 문서 검색
7. RAG Service에서 컨텍스트와 프롬프트 구성
8. LLM Gateway에서 답변 생성
9. Audit Service에 로그 기록
10. Frontend에 답변, 근거, 가능한 액션 반환
```

워크플로우 액션 처리 흐름:

```text
1. 사용자가 ApproveOrder 클릭
2. Auth에서 사용자 확인
3. Policy Engine에서 액션 권한 확인
4. Workflow Service에서 현재 상태와 전이 검증
5. Ontology Service에서 대상 객체 조회
6. 액션 실행
7. 상태 변경 저장
8. 이벤트와 감사 로그 기록
9. 화면에 변경 결과 반환
```

## 5. 데이터 저장소

추천 저장소:

| 데이터 | 저장소 예 |

## 6. 상태 관리

프론트엔드 상태는 다음처럼 나눕니다.

| 상태 | 위치 |
| --- | --- |
| 선택된 메뉴 | 클라이언트 상태 |
| 선택된 객체 | 클라이언트 상태 |
| 객체 목록 | 서버 상태 |
| AI 질의 결과 | 서버 상태 + 클라이언트 캐시 |
| 워크플로우 실행 결과 | 서버 상태 |
| 권한 정보 | 서버 상태 |

실제 구현에서는 React Query, SWR 같은 서버 상태 관리 도구를 사용할 수 있습니다.

## 7. 캐시 전략

캐시 가능한 데이터:

- 객체 타입 메타데이터
- 관계 타입 메타데이터
- 문서 검색 결과
- 정적 정책 문서

캐시를 조심해야 하는 데이터:

- 주문 상태
- 액션 가능 여부
- 권한 정보
- 민감 속성
- 최신 워크플로우 이벤트

워크플로우 액션 실행 후에는 관련 객체와 큐 데이터를 반드시 재조회하거나 캐시 무효화해야 합니다.

## 8. API 설계

예시 API:

```text
GET  /api/me
GET  /api/ontology/object-types
GET  /api/objects/customers
GET  /api/objects/orders/:id
GET  /api/objects/orders/:id/context
POST /api/search
POST /api/ask
GET  /api/workflow/queue
POST /api/workflow/execute
GET  /api/audit/events
```

`/api/ask` 응답 예:

```json
{
  "answer": "승인 가능성이 높습니다.",
  "detected_objects": ["C001", "O001"],
  "ontology_context": {
    "customer_id": "C001",
    "order_id": "O001"
  },
  "evidence": [
    {
      "document_id": "D001",
      "title": "Order Approval Policy",
      "score": 3.82
    }
  ],
  "available_actions": ["ApproveOrder", "RejectOrder"]
}
```

## 9. 오류 처리

운영형 시스템에서는 오류를 사용자에게 명확히 보여줘야 합니다.

| 오류 | 사용자 메시지 |
| --- | --- |
| 객체 없음 | 요청한 객체를 찾을 수 없습니다. |
| 관계 불일치 | 고객과 주문의 연결 관계가 일치하지 않습니다. |
| 권한 없음 | 이 정보에 접근할 권한이 없습니다. |
| 문서 없음 | 답변에 필요한 근거 문서를 찾지 못했습니다. |
| 액션 불가 | 현재 상태에서는 이 액션을 실행할 수 없습니다. |
| 모델 오류 | 답변 생성 중 문제가 발생했습니다. 다시 시도하세요. |

## 10. 보안 체크리스트

```text
- 모든 API에서 사용자 인증을 확인한다.
- 객체 조회 전 권한을 확인한다.
- 속성 마스킹을 서버에서 적용한다.
- 문서 검색에 권한 필터를 적용한다.
- RAG 프롬프트 생성 전 민감 정보를 제거한다.
- 액션 실행 전 권한과 상태를 다시 확인한다.
- 클라이언트에서 보낸 상태 값을 신뢰하지 않는다.
- 감사 로그를 남긴다.
```

## 12. 요약

운영형 아키텍처의 핵심은 책임 분리입니다. 화면은 업무 흐름을 보여주고, 온톨로지 서비스는 객체와 관계를 관리하며, 워크플로우 서비스는 상태 전이를 책임지고, RAG 서비스는 권한이 적용된 근거 기반 답변을 생성해야 합니다.

## 13. 실전 운영 최적화 가이드 (Best Practice)

실제 엔터프라이즈 환경에서 시스템을 안정적으로 운영하기 위해 다음의 최적화 방안을 추가로 반영합니다.

### 1) 환경 불가지론적(Environment Agnostic) 구조
로컬 개발과 클라우드 운영 환경 간의 코드 수정 없는 전환을 위해 세션/연결 관리 로직을 중앙화합니다.
- **연결 관리 모듈**: 로컬 설정 파일과 클라우드 환경의 활성 세션을 자동 감지하여 연결을 생성하는 공통 함수를 표준으로 사용합니다.

### 2) 성능 최적화: 병렬화 및 부분 업데이트
온톨로지 질의와 RAG 검색의 지연 시간을 최소화하기 위한 UX/성능 전략을 적용합니다.
- **I/O 병렬화**: 비동기 처리 또는 멀티스레딩을 활용하여 객체 조회와 문서 검색을 동시에 수행합니다.
- **부분 렌더링(Fragments)**: 전체 페이지 리로딩 없이 필요한 부분(예: AI 답변 영역, 근거 패널)만 독립적으로 업데이트하여 체감 속도를 높입니다.

### 3) 자동화된 배포 파이프라인 및 체크리스트
수동 배포 리스크를 줄이기 위해 단계별 체크리스트와 자동화 도구를 결합합니다.
- **배포 전·중·후 체크리스트**: PR 리뷰 여부, 단위 테스트 통과, 운영 승인 완료, 배포 후 서비스 검증 등을 표준화된 양식으로 관리합니다.
- **배포 순서 표준화**: 1) 데이터 객체(Schema/View) -> 2) 비즈니스 로직 -> 3) UI 소스 -> 4) 권한 설정 순으로 진행하여 정합성을 유지합니다.

### 4) 장애 대응 및 롤백(Rollback) 전략
배포 실패나 운영 장애 시 즉각적인 복구를 위한 우선순위를 설정합니다.
- **롤백 우선순위**: 1) 이전 정상 버전 재배포 -> 2) 객체 단위 복구 -> 3) 데이터 플랫폼의 타임머신 기능을 활용한 데이터 복구 순으로 대응합니다.
- **사후 조치**: 롤백 사유와 원인을 기록하고, 재발 방지를 위한 회귀 테스트(Regression Test) 케이스를 반드시 추가합니다.

### 5) 엔터프라이즈 운영 전략
엔터프라이즈 보안 및 시스템 환경을 고려한 단계적 배포 전략입니다.
- **형상관리 중심**: 모든 소스(SQL, 코드, 환경 파일)는 버전 관리 시스템으로 일원화합니다.
- **도구 연계**: 배포 자동화는 클라우드 네이티브 CI/CD 도구를 우선 검토하되, 기업 내 보안 정책에 따라 기존 운영 도구와 연계하는 하이브리드 방식을 채택할 수 있습니다.
- **단계적 확산**: 개발/검증 환경에서 먼저 자동화를 검증한 후, 운영 환경은 보안 승인 절차를 거쳐 단계적으로 확산합니다.
